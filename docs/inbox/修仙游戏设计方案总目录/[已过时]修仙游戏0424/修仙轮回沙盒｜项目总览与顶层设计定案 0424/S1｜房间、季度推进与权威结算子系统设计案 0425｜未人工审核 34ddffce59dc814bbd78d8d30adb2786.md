## 1. 子系统定位

S1 是所有季度回合的调度层和结算总线。

一句话定位：

> S1 决定一个房间如何开始、如何推进季度、何时收集玩家决策、何时由服务器统一结算，以及结算结果如何回写世界状态。
> 

S1 不设计具体玩法收益，而是保证 S3、S4、S7、S10、S11、战斗事件链等子系统能在同一条权威时间轴上运行。

## 2. MVP 最小目标

MVP 中，S1 必须支持：

1. 本地单人测试房间。
2. 私人服务器部署房间。
3. 至少 3 名玩家共玩。
4. 可保存、暂停、恢复、续开。
5. 无人在线时世界不自动推进。
6. 所有玩家锁定或超时后，由权威服务器统一结算。
7. 结算过程可回放、可调试、可写入日志。

## 3. 房间状态模型

最小房间状态包含：

```
RoomState {
  room_id
  world_seed
  current_year
  current_quarter
  current_phase
  player_slots
  active_players
  ai_controlled_factions
  world_state_version
  pending_decisions
  settlement_status
  save_version
}
```

房间不是实时持续世界。季度推进只发生在明确的回合提交与服务器结算过程中。

## 4. 标准季度阶段机

MVP 标准阶段：

```
加载 / 创建房间
→ 季度开始
→ 世界刷新
→ 宗门行动决策阶段
→ 宗门行动即时反馈
→ 角色行动决策阶段
→ 玩家锁定 / 超时等待
→ 服务器统一结算
→ 插入事件链处理
→ 结果回写与日志生成
→ 下一季度
```

阶段说明：

- 世界刷新：生成本季度节点事件、秘境窗口、宗门动向、资源波动、传闻候选。
- 宗门行动决策阶段：玩家基于身份与权限提交宗门建议或决策。
- 宗门行动即时反馈：只给预估，不代表最终结算。
- 角色行动决策阶段：玩家基于 S3 规划 6 个朔望行动格。
- 服务器统一结算：所有最终状态以服务器结果为准。
- 插入事件链处理：突破、战斗、死亡、后手、节点危机等可暂停普通结算。

## 5. 权威服务器原则

MVP 采用客户端 + 权威服务器架构。

规则：

1. 客户端只提交意图，不直接改写世界状态。
2. 服务器校验所有宗门行动、角色行动、资源消耗、位置、权限与事件触发。
3. 客户端显示的预估收益、预估消耗、预计结束位置均不是最终结果。
4. 结算结果必须包含足够的摘要，用于调试、玩家日志和世界日志。
5. 本地单人测试也应走同一套权威结算流程，只是服务器可在本地进程中运行。

## 6. 玩家锁定、超时与托管

玩家在角色行动决策阶段提交后进入锁定状态。

### 6.1 已确定决策：结算触发方式

**人工决策：采用“全员锁定或超时后自动结算”。**

默认规则：

- 所有玩家均锁定后，房间自动进入服务器统一结算。
- 存在玩家超时时，S1 请求 S12 托管系统为超时玩家生成稳健托管计划，然后自动进入服务器统一结算。
- 默认不要求房主手动确认进入结算，避免多人房间被房主单点阻塞。
- 房主手动确认可以作为后续房间设置预留，但不作为 MVP 默认规则。

### 6.2 最小规则

- 所有在线玩家锁定后，房间可进入结算。
- 如果存在超时玩家，S1 请求托管系统生成稳健托管计划。
- 托管不得主动突破、主动叛宗、主动发动战争、主动暴露核心后手或做高风险不可逆选择。
- 玩家在所有人锁定前可以解锁修改；一旦进入服务器统一结算，不再允许修改。

## 7. 结算主循环

服务器结算采用固定顺序，避免跨系统互相抢改状态。

```
读取本季度锁定决策
→ 校验宗门行动意图
→ 校验角色行动计划
→ 生成 S3 tick 时间轴
→ 按 tick 推进行动、移动、持续行动与事件判定
→ 遇到插入事件链则暂停普通时间轴
→ 接收事件链结果包
→ 回写角色、宗门、节点、资源、日志
→ 处理季度结束状态
→ 写入存档
```

## 8. 插入事件链接口

S1 只负责调度，不负责事件内部规则。

事件请求包建议包含：

```
EventRequest {
  event_type
  source_system
  trigger_tick
  trigger_location
  involved_players
  involved_factions
  parent_timeline_context
  visibility_context
  rng_namespace
}
```

事件结果包建议包含：

```
EventResult {
  continue_original_plan
  consumed_ticks
  interrupt_quarter_plan
  character_state_changes
  location_changes
  faction_state_changes
  node_state_changes
  inventory_changes
  ledger_entries
  visible_logs
  hidden_world_logs
}
```

## 9. 随机与可回放

为支持调试和私人服务器复盘，S1 应要求所有随机结果可追踪。

最小原则：

- 房间使用世界种子。
- 每个季度、事件链、战斗、节点判定使用独立随机命名空间。
- 日志记录随机入口、结果摘要和关键修正来源。
- 不要求玩家看到完整随机细节，但调试日志需要能复盘。

## 10. 与其他系统的接口

- S2：读取玩家真灵、当世角色、死亡 / 转世状态。
- S3：读取并结算角色行动时间轴。
- S4：在突破触发时接管或中断季度计划。
- S5 / S6 / S7：处理宗门身份、宗门库存和宗门行动执行。
- S8：读取节点图、位置、通行、节点状态。
- S9：处理物品、资源、库存消耗。
- S10：处理节点事件与世界事件。
- S11：处理前世后手、隐藏层、后手感应与回收。
- S12：生成离线 / 超时托管行动。
- S13：处理多人可见性、间接竞争和资源名额冲突。
- S14：承接存档、数据结构、日志、Debug 和部署实现。

## 11. MVP 验收标准

S1 最小可验收闭环：

1. 创建本地单人房并跑通一个季度。
2. 私人服务器房间支持 3 名玩家提交并统一结算。
3. 支持玩家超时后托管继续推进。
4. 支持 S3 行动时间轴生成与回写。
5. 支持至少一种插入事件链暂停结算并返回结果。
6. 支持保存、退出、恢复后继续下一季度。
