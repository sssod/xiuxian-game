# v2.2 系统方案最小化修剪稿｜可玩性测试 Demo → MVP 兼容版

**文档版本**：demo-scope-v0.1

**依据版本**：v2.2 当前项目设计方案

**生成目的**：在不推翻 v2.2 架构口径的前提下，将系统方案修剪为可开发、可测试、可扩展的可玩性测试 demo 范围。

**核心策略**：削减内容广度、AI 深度、多人强度和 UI 动效复杂度；保留 v2.2 的结算总线、字段口径、行动经济、地图工作台、资源输入、宗门 AI 和日志 / 存档骨架。

---

## 0. 一句话结论

可玩性测试 demo 不应被定义为“缩小版完整 MVP”，而应定义为：

```
本地单人可跑通
+ 大地图回合行动工作台可用
+ 1–3 条线性行动指令可规划、锁定、结算、回放
+ M0 → M1 / 压缩突破体验可玩
+ 至少一次移动事件、一次资源输入修炼、一次宗门资源 / 宗门 AI 反馈、一次节点变化
+ 所有状态与日志使用 v2.2 MVP 兼容字段
```

demo 的主要验证对象不是数值平衡，也不是完整内容量，而是玩家是否能理解并愿意继续玩以下五件事：

1. **我在地图上规划一回合，而不是在菜单里堆按钮。**
2. **我的行动都在竞争同一个时间预算。**
3. **计划会被事件、移动、资源、状态和宗门变化打断或改写。**
4. **修炼、资源输入、突破准备和宗门身份能形成成长压力。**
5. **宗门和世界不是背景文本，而是在回合结算中真实变化。**

## 1. 修剪原则

### 1.1 只修剪“内容宽度”，不破坏“系统骨架”

允许缩小：

- 地图节点数量。
- 宗门数量。
- 事件模板数量。
- 修炼阶段数量。
- 物品种类。
- NPC 持久化层级。
- UI 动画和视觉细节。
- 多人真实接入强度。

不允许破坏：

- `turn_id / world_day / world_hour / macro_period_id` 时间字段口径。
- S1 权威结算总线。
- 客户端只提交意图，服务端校验并回写。
- 个人线性行动指令。
- 天级预算条 + 小时级内部结算。
- 事件 / 战斗 / 突破 / 宗门 AI 统一输出 `ResultPackage`。
- 行动资源输入不是独立行动。
- 宗门由 AI 自行维护唯一持续行动，玩家只间接影响。
- 资产容器、资源使用接口、日志和存档骨架。
- `MethodCarrierItem → MethodState` 的功法学习边界。
- 轮回账本 / 后手 / 可见性等未来 MVP 系统的字段预留。

### 1.2 demo 采用“窄内容、真流程”

demo 可以只有 1 个主宗门、约 10 个节点、少量行动和事件，但每一个核心流程必须走真接口：

```
玩家输入行动意图
→ 服务端校验
→ 小时级时间线推进
→ 触发事件 / 宗门 AI / 节点变化
→ 子系统输出结果包
→ S1 合并回写
→ 生成日志 / 原计划 vs 实际报告
→ 存档
```

不能为了 demo 临时做一套“按钮直接改状态”的假流程，否则后续扩展 MVP 时会发生大规模返工。

### 1.3 demo 允许“内容脚本化”，但不允许“架构脚本化”

允许：

- 新手路线预设。
- 第一次宗门入门事件脚本化。
- 第一次突破资源获取链脚本化。
- 宗门 AI 前几回合使用固定策略。
- 资源节点变化使用固定模板。
- 事件随机表较小。

不允许：

- 事件直接改角色最终状态。
- 宗门 AI 直接改库存和节点，不产出结果包。
- 资源消耗绕过统一接口。
- 修为丹药即时加修为。
- UI 直接写世界状态。
- 存档只保存 UI 临时状态。
- 临时使用旧字段如 `quarter / action_slot / tick`。

## 2. Demo 范围定义

### 2.1 推荐 demo 边界

推荐将可玩性测试 demo 定义为：

```
本地单人
+ 1 名真实玩家
+ 1 个主宗门
+ 1 个弱化竞争压力来源：AI rival faction 或荒野压力
+ 8–12 个地图节点
+ 默认每回合 5 天
+ 手动锁定推进，倒计时可配置但默认关闭或弱化
+ 约 8–15 个回合的游玩闭环
+ M0 → M1，并提供一次压缩式关键突破体验
```

其中“压缩式关键突破体验”不要求完整 M1 → M2 数值曲线，但需要使用未来大境界突破的事件链接口：

```
达到瓶颈
→ 准备突破资源
→ 选择突破行动
→ 消耗关键突破物
→ 进入突破事件链
→ 成功 / 失败存活 / 重伤中断
→ 写入角色日志与轮回账本占位
```

### 2.2 demo 最小玩家旅程

推荐玩家旅程如下：

```
1. 创建本地房间与真灵
2. 生成第一世角色，出生于青禾村
3. 打听宗门与路线
4. 前往镇集，触发一次移动或节点事件
5. 在镇集武馆获得轻身功法 / 路线帮助
6. 前往云麓宗山门，完成入门事件链
7. 获得外门身份与基础道功载体
8. 使用回合预算安排吐纳 / 研习 / 探索 / 休整
9. 绑定一次修炼资源输入，例如清灵丹
10. 看到残余药性或资源消耗日志
11. 向宗门申请一次资源或使用设施
12. 宗门 AI 推进一个节点相关持续行动
13. 前往资源节点探索 / 采集，触发资源槽变化或传闻
14. 达到压缩式瓶颈，进行一次突破事件链
15. 回合结束报告展示原计划 vs 实际结果，并保存
```

### 2.3 demo 成功标准

demo 成功不以“内容很多”为标准，而以以下验证成立为标准：

- 玩家能在不看设计文档的情况下理解“本回合要做什么”。
- 玩家能感知 5 天时间预算的稀缺性。
- 玩家能理解移动、修炼、探索、宗门事务会互相挤占时间。
- 玩家能接受“事件改变原计划”的结算反馈。
- 玩家能理解丹药 / 灵材 / 符箓是行动资源输入，而不是单独的即时收益按钮。
- 玩家能看到宗门 AI 与节点状态在回合间变化。
- 玩家能从回合报告中解释“为什么结果和计划不同”。
- 开发团队能通过 Debug / TurnReplay 复盘一次结算。
- 存档读取后能继续下一回合。
- demo 所有核心字段可自然扩展到 MVP，而不是重写。

## 3. 系统保留 / 降级 / 暂缓总表

| 系统 | demo 处理 | MVP 兼容要求 | 备注 |
| --- | --- | --- | --- |
| S1 房间回合 / 权威结算 | **完整保留骨架** | 保留 `RoomState / TurnConfig / ResultPackage / TurnReplay` | 这是 demo 与 MVP 的共同地基 |
| S2 真灵 / 当世角色 / 修炼 | **保留核心** | 保留真灵、角色、境界、主修道功、资源输入、日志 | 阶段数量可压缩 |
| S2A 功法 / 资源输入 / 残余效果 | **保留最小可玩** | 保留 `MethodCarrierItem / MethodState / ActionResourceInputBinding / ActiveResourceEffect` | 内容只做 1–2 个道功和资源 |
| S3 个人行动经济 / 移动 | **完整保留玩法语义** | 1–3 条线性行动、天级预算、小时级结算 | UI 不允许玩家手排小时 |
| S4 突破事件链 | **做一次压缩链** | 使用未来大境界突破接口 | 可不做完整 M1 → M2 数值深度 |
| S5 宗门组织 / AI | **降级为 1 宗门 + 1 AI 持续行动** | 保留身份、权限、库存、资源申请、AI 行动状态 | 暂不做 5 级身份全量体验 |
| S6 经济 / 物品 / 资产 | **保留资产容器与资源接口** | 物品、资源、关键物必须有容器与日志 | 暂不做完整市场和生产链 |
| S7 后手 / 遗产 | **字段预留，玩法暂缓** | 保留轮回账本 / 后手记录容器 | 可在突破失败或死亡中写入占位日志 |
| S8 地图节点 / 世界演化 | **缩小到 8–12 节点** | 保留节点、路线、资源槽、控制权 / 影响力字段 | 不做 35±10 首图 |
| S10 事件 / 战斗 | **事件保留，战斗抽象化** | 事件统一 `consumed_hours` 与结果包 | 战斗先做选择事件，不做完整斗法链 |
| S13 可见性 / 多人间接竞争 | **保留字段，弱化实现** | 保留 visibility_level / rumor / world_log | demo 单人下只做玩家可见 / 世界日志二层 |
| S14 数据驱动 / 存档 / 调试 | **必须保留最小** | 稳定 ID、配置加载、存档、Debug、回放 | 存档格式待决策 |

## 4. Demo 必做系统切片

### D0：技术底座与结算总线

### 目标

让 demo 从第一天起就跑在 MVP 兼容的权威结算架构上。

### 必做

- 本地单人房间创建。
- `RoomState`。
- `TurnConfig`。
- 回合阶段机。
- 玩家锁定。
- 服务器统一结算入口。
- 结果包接口。
- 基础日志。
- 存档保存 / 读取。
- Debug 状态查看。
- 最小 `TurnReplay`。

### demo 阶段机

```
room_loading
→ turn_start
→ report_review
→ instant_personal
→ personal_action_planning
→ waiting_lock
→ settlement
→ inserted_event
→ writeback
→ turn_end
```

demo 可以将以下阶段合并显示，但不要从数据层删除：

```
report_review + instant_personal
personal_action_planning + waiting_lock
writeback + turn_end
```

### 验收

- 可以创建本地房间。
- 可以进入回合开始。
- 可以配置每回合天数，默认 5 天。
- 可以锁定行动。
- 可以执行空结算进入下一回合。
- Debug 面板显示 `phase / turn_id / world_day / world_hour / player / state_version`。
- 退出后读取存档继续。
- 一次结算能生成 `TurnReplay` 简化记录。

### D1：大地图回合行动工作台

### 目标

让玩家从地图理解行动、地点、时间预算和事件风险。

### 必做 UI

- 顶部：回合阶段条 + 当前角色摘要 + 游戏时间块。
- 中心：可点击 / 可缩放可降级的大地图。
- 左侧：目标追踪 / 重要消息。
- 右侧：节点上下文面板。
- 底部：回合时间预算条 + 行动指令规划器。
- 事件弹层。
- 回合结束报告。
- 简化角色 / 物品 / 功法 / 宗门 / 日志入口。
- Debug 面板，开发版可见。

### demo UI 可降级项

- 地图可以先是 2D 节点图，不需要完整美术地图。
- 战争迷雾先做 `known / hinted / hidden` 三态。
- 结算动画可以先用进度列表，不做日月流动动效。
- 侧栏折叠动画可先无。
- 图层切换可只保留“节点 / 资源 / 宗门影响”三类。

### 验收

- 玩家能从地图选择目标节点。
- 玩家能看到路线预估和风险摘要。
- 玩家能将行动加入 5 天预算条。
- 预算条显示行动编号、占用天数、已占用 / 总天数。
- 点击锁定前能看到硬错误和高风险提醒。
- 结算后能从报告返回地图并继续下一回合。

### D2：角色、新手入门与基本修炼

### 目标

跑通“真灵 → 第一世角色 → 入门 → 获得基础道功 → 主动吐纳成长”。

### 必做

- 真灵创建。
- 当世角色生成。
- 基础属性：体魄、精力。
- 资质子项：根骨、悟性、灵根。
- 状态条：生机、元气、神念。
- 初始村庄节点。
- 已知 / 半知 / 隐藏节点。
- 角色日志。
- 新手任务链。
- 入门事件链。
- 外门身份。
- 基础完整道功载体。
- 学习后生成 `MethodState`。
- 主动吐纳。
- 自动运转简化收益。
- A-1 → A-2 / A-3 压缩成长。
- 主修道功有效上限检查。

### demo 可降级项

- 资质只影响 2–3 个公式，不做完整根骨承载曲线。
- 灵根相性先做标签匹配，不做复杂五行循环。
- 只做 1 个基础道功与 1 个轻身法门。
- 主修锁定只做 UI 提示，不做多道功复杂切换。
- 小境界升级只做条件判定，不做事件链。

### 验收

- 玩家从青禾村出发，能到达山门并入门。
- 入门事件揭示资质子项。
- 玩家获得外门身份和基础道功载体。
- 完整功法载体学习后生成 `MethodState`。
- 主动吐纳占用实际时间并增加修为。
- 自动运转不会与主动吐纳叠加。
- 修为达到条件后可从 A-1 升至 A-2。
- 主修上限不足时，修为推进被限制并提示原因。

### D3：个人行动经济、移动与事件

### 目标

让玩家使用少量线性行动指令规划一回合，并看到事件如何改变原计划。

### 必做行动类型

| 行动 | 类型 | demo 说明 |
| --- | --- | --- |
| 前往节点 | 移动行动 | 计算路线小时，可能触发移动事件 |
| 打听消息 | 短行动 | 可发现节点 / 传闻 / 新手线索 |
| 主动吐纳 | 可选投入持续行动 | 绑定地点灵气、功法、资源输入 |
| 研习功法 | 可选投入持续行动 | 增加掌握度或解锁提示 |
| 探索节点 | 可选投入持续行动 | 触发节点事件、资源发现 |
| 采集资源 | 可选投入持续行动 | 影响资源槽，产出物品或宗门资源 |
| 休整 / 停留 | 可选投入持续行动 | 恢复状态，作为 fallback |
| 突破尝试 | 固定执行时间行动 | demo 中用于压缩突破链 |
| 资源申请 | 个人即时 / 宗门相关行动 | 不直接控制宗门，只请求资源 |

### 必做事件类型

- 移动事件。
- 节点事件。
- 宗门事件。
- 传闻生成事件。
- 突破事件链入口。
- 简化战斗 / 避险选择事件。

### demo 事件结构

```
模板
+ 触发条件
+ 1–3 个主选项
+ 可选资源输入槽
+ 简化检定
+ consumed_hours
+ ResultPackage
```

### 验收

- 玩家可输入 1–3 条主要行动占满默认 5 天。
- 移动会消耗实际小时，并更新位置。
- 事件可消耗小时并推迟后续行动。
- 事件可改变角色状态、库存、节点状态或日志。
- 回合结束报告解释原计划与实际差异。
- 若行动被中断、跳过或跨回合延续，报告必须显示原因。

### D4：行动资源输入与资产容器

### 目标

验证“资源不是即时经验包，而是行动上下文内的输入项”。

### 必做

- `AssetContainerRef`。
- `CharacterInventory`。
- `SectStorage`。
- `ResourcePool`。
- `EventLockedReward`。
- `ItemStack`。
- `ItemInstance`。
- `ResourceUseRequest`。
- `ActionResourceInputBinding`。
- `ActiveResourceEffect`。
- 资源消耗日志。

### demo 资源种类

| 资源 | 类型 | 挂载语境 |
| --- | --- | --- |
| 灵石 | 货币 | 采购、申请、事件代价 |
| 清灵丹 | 修炼资源 | 主动吐纳 |
| 定心散 / 定心符 | 稳定资源 | 研习 / 突破准备 |
| 避瘴符 | 消耗道具 | 毒瘴移动 / 探索事件 |
| 灵草 | 材料 / 修炼资源 | 采集产物或上交宗门 |
| 筑基前置物 / 试炼令 | 关键突破物 | 压缩突破链消耗 |

### demo 可降级项

- 不做背包重量、格子、体积。
- 不做完整装备栏。
- 不做完整商店经济。
- 商店库存可模板生成，但必须是 `ShopStock` 或等价容器。
- 高价值关键物使用实例；普通丹药、符箓、材料使用堆叠。
- 不做复杂炼丹炼器，只保留资源消耗与产出接口。

### 验收

- 行动未开始时，不消耗已绑定资源。
- 行动开始后，按实际兼容小时消耗 / 结算资源效果。
- 主动吐纳短于资源有效时长时，剩余效果进入 `ActiveResourceEffect`。
- 资源消耗记录 `turn_id / world_day / world_hour / consumed_hours`。
- 高价值关键物消耗后可在日志中追溯。
- 物品归属首先指向资产容器，而不是直接写“NPC 身上”。

### D5：宗门资源平台与 AI 最小实现

### 目标

让宗门在 demo 中成为可见的资源平台和自动演化组织，而不是玩家直接控制的经营面板。

### 必做

- 1 个主宗门：云麓宗。
- 身份：外门弟子、内门弟子；其余身份字段预留。
- 权限标签最小实现：
    - `request_resources`
    - `use_training_site`
    - `request_breakthrough_support`
    - `view_sect_ai_summary`
- 宗门库存：
    - 灵石。
    - 修炼资源。
    - 材料库存。
    - 人力。
    - 宗门声望。
- 资源申请。
- 资源预留。
- 每宗门同一时间最多 1 个 `active_continuous_action`。
- 宗门 AI 选择 / 推进 / 完成 / 中止一个持续行动。
- 宗门当前持续行动摘要 UI。
- 玩家通过个人行动或事件间接影响宗门行动。

### demo 宗门 AI 行动模板

| 行动 | 目标 | 结果 |
| --- | --- | --- |

### D7：压缩式突破链

### 目标

用较少内容验证“突破不是升级按钮”，并为 MVP 的大境界突破系统保留接口。

### demo 突破流程

```
1. 修为到达 demo 瓶颈
2. UI 显示瓶颈原因：主修、资源、状态、地点、宗门支持
3. 玩家准备关键突破物
4. 玩家选择固定执行时间的突破行动
5. 行动开始时消耗关键突破物
6. 进入突破事件链
7. 玩家在 1–3 个关键选项中选择
8. 事件链输出成功 / 失败存活 / 重伤中断
9. 写入角色日志、宗门摘要、轮回账本占位
10. 生成回合报告
```

### demo 可降级项

- 不做完整多阶段突破链。
- 不做复杂战斗干扰。
- 不做死亡转世作为默认结局。
- 失败标签只做 3–5 个方向：
    - 根基不稳。
    - 资源不足。
    - 心神动摇。
    - 地点不合。
    - 外扰失控。
- 突破成功后可只进入 B-1 占位或 demo 结束总结。

### 验收

- 玩家不能通过自动运转跨越关键瓶颈。
- 玩家必须主动选择突破。
- 突破显示固定执行时间和不可逆资源消耗。
- 关键突破物在事件链创建时消耗。
- 突破失败不是只显示“失败”，必须有原因标签。
- 突破结果进入日志和回合报告。
- 轮回账本可记录本次突破信息，即使正式转世未启用。

## 10. 主要风险与控制

### 风险 1：demo 过窄，玩家感受不到“修仙轮回沙盒”

控制：

- 必须保留地图、时间预算、修炼、宗门、节点变化、一次突破压力。
- 即使暂缓正式转世，也要保留轮回账本占位和突破失败标签。

### 风险 2：demo 架构过重，开发无法快速完成

控制：

- 数据结构用最小字段落地，不做最终数据库 schema。
- 内容模板数量严格控制。
- 宗门 AI 用固定策略 + 条件判断，不做复杂权重表。
- 战斗抽象成事件选择，不做完整斗法系统。

### 风险 3：为了快而做假流程，后续 MVP 返工

控制：

- S1、行动队列、结果包、资源接口、日志、存档必须从 demo 第一天使用。
- UI 可以简陋，但不能直接改状态。
- 所有高价值变化必须可追溯。

### 风险 4：玩家不理解回合报告

控制：

- 回合报告必须用“原计划 → 实际发生 → 原因 → 下回合注意”结构。
- 每条事件消耗小时都要能解释后续行动为什么推迟或中断。
- 报告优先展示 P0/P1 变化，不堆全量日志。
