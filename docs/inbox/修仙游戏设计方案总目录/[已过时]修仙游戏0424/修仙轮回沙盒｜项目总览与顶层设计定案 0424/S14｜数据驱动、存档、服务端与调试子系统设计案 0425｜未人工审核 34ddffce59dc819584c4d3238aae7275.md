## 1. 子系统定位

S14 将前面所有设计收束为可实现、可存档、可调试、可部署的技术边界。

一句话定位：

> S14 决定规则数据放在哪里、服务器如何权威结算、世界如何保存和恢复，以及开发者如何追踪每一次结算结果。
> 

## 2. 技术路线

已定路线：

```
Godot 客户端 + Godot Headless / Dedicated Server
```

原则：

- 客户端负责 UI、地图展示、行动规划、事件阅读、账本展示和玩家输入。
- 服务器负责房间状态、季度推进、行动结算、宗门 AI、地图节点、事件触发和存档写入。
- 本地单人测试也走同一套规则模型。
- 回合统一结算，避免复杂实时同步。

## 3. 权威服务器边界

客户端只提交意图：

- 宗门建议 / 决策意图。
- 角色行动计划。
- 事件链选择。
- 战斗指令序列。
- 资源使用请求。

服务器校验并写入：

- 资源消耗。
- 位置变化。
- 行动合法性。
- 事件触发。
- 战斗结果。
- 角色状态。
- 宗门库存。
- 节点状态。
- 日志与存档。

## 4. 数据驱动对象

MVP 尽量数据驱动：

- 境界阶段。
- 功法 / 术法 / 技能标签。
- 宗门模板。
- 节点模板。
- 资源槽模板。
- 建筑槽模板。
- 事件模板。
- 突破链模板。
- 战斗指令模板。
- 法宝与道具模板。
- 后手类型模板。
- 托管策略配置。

规则代码读取配置，不把具体数值、文案和世界观包装写死。

## 6. 存档最小要求

存档必须支持：

1. 房间元数据。
2. 世界种子。
3. 当前季度与阶段。
4. 玩家与真灵。
5. 当世角色。
6. 宗门状态与库存。
7. 地图节点、边、槽位、控制权、影响力。
8. 事件状态、秘境窗口、隐藏层。
9. 后手与轮回账本。
10. 可见性与传闻。
11. 随机状态或可复盘随机日志。
12. 版本号与迁移信息。

## 7. 存档格式待定原则

SQLite、资源文件或混合方案暂不在本页定死。

选择原则：

- 能支持私人服务器长期保存。
- 能支持调试查询。
- 能支持版本迁移。
- 能支持本地单人测试。
- 能支持多人房间状态一致性。

MVP 可先采用最容易调试的结构，再在实现评估后确定最终持久化方案。

## 8. 日志体系

最小日志分三类：

1. 玩家可见日志：角色日志、宗门摘要、传闻、轮回账本。
2. 世界日志：系统完整事件记录，默认玩家不可见。
3. Debug 日志：结算输入、随机、校验、结果包、错误。

日志必须能追踪：

- 为什么某行动失败。
- 哪个资源被消耗。
- 哪个事件触发。
- 哪个系统改写了状态。
- 后手为什么暴露或失效。
- 托管为什么选择某行动。

## 9. 结算回放

S3 已要求输出可回放行动时间轴，S14 负责保存与查看。

最小回放内容：

```
quarter
phase
input_decisions
validated_actions
tick_timeline
event_requests
event_results
state_deltas
rng_summary
final_state_hash
```

回放优先服务开发与测试，不一定作为玩家功能开放。

## 10. 版本迁移

所有存档需要版本号。

```
SaveVersion {
  game_rules_version
  content_data_version
  save_schema_version
  migration_history
}
```

MVP 允许破坏性重置测试档，但结构上应从一开始保留版本字段，避免后续迁移完全不可控。

## 11. 私人服务器部署

MVP 部署目标：

- 能启动一个私人服务器。
- 能创建或加载房间。
- 最多至少支持 3 名玩家连接。
- 能提交季度决策并统一结算。
- 能保存房间并下次继续。

房间发现、服务器列表、账号系统、反作弊、商业平台接入均不进入 MVP 核心。

## 12. 配置与文案分离

规则 ID 使用抽象编码，显示文本用 key 映射。

示例：

```
stage.code = C-1
stage.display_name_key = stage.core_3_minor_1
```

不得在规则判断中直接依赖“筑基”“金丹”等包装文本。

## 13. 与其他系统的接口

S14 需要承接所有系统的持久化与调试需求：

- S1：房间阶段、结算总线、存档触发。
- S2：真灵、角色、轮回账本。
- S3：行动时间轴和结束位置。
- S4：突破链结果、失败标签。
- S5–S7：宗门身份、库存、行动。
- S8：地图节点和槽位。
- S9：物品与资产状态。
- S10：事件链与世界日志。
- S11：后手、隐藏层、失效原因。
- S12：托管计划与托管日志。
- S13：多人可见性与传闻。
- 战斗系统：战斗指令、结果包、资源变化。

## 14. MVP 验收标准

1. 本地单人可创建、保存、读取房间。
2. 私人服务器可支持 3 名玩家提交并结算一个季度。
3. 规则与文案不硬绑定修仙包装。
4. 关键配置可从数据表或资源文件读取。
5. 一个季度结算可通过 Debug 日志复盘。
6. 存档包含版本信息。
7. 至少一种事件链、一次战斗或一次突破能产生可追踪结果包。
