# 项目总览、MVP 边界与系统依赖

## 0. 文档定位

本文是开发交付口径下的项目总览，用于替代“先读所有旧文档再理解项目”的工作方式。

本文负责回答：

1. 这款游戏是什么。
2. MVP 到底要做到什么程度。
3. 系统之间的依赖关系是什么。
4. 哪些内容明确不是 MVP。
5. 开发实现时应按什么顺序拆分。

## 1. 一句话定位

本项目是一款支持本地单人测试、私人服务器部署、3 人共玩的房间制多人修仙轮回沙盒。

玩家控制的不是宗门、国家或固定角色，而是一点跨世延续的真灵。每一世的当世角色会修炼、加入宗门、移动探索、争夺资源、突破失败或成功、死亡转世、布置后手，并在共享地图中影响宗门与世界节点演化。

推荐开发用定位：

> 回合制房间 + 跨世角色成长 + 宗门资源平台 + 节点地图沙盒 + 事件链结算。
> 

## 2. MVP 边界

当前 MVP 不按商业化版本、Steam EA 或正式发售内容量定义。

MVP 边界固定为：

```
本地可单人测试
+ 可部署私人服务器
+ 支持 3 人共玩
+ 可保存、暂停、恢复、续开
+ M0 → M3 纵向闭环可跑通
```

最低验证目标不是“玩家抵达 M3 就算成功”，而是在 M0 到 M3 的过程中自然验证：

- 至少一段关键突破链。
- 至少一次宗门中高层影响或等价世界影响。
- 至少一次轮回、前世信息、正式后手或跨世反馈。
- 至少一次节点资源竞争、节点局势变化或控制权相关变化。
- 至少一次多人间接竞争或 AI 宗门造成的等价竞争压力。

## 3. 顶层设计承诺

开发实现必须服务六个核心承诺。

### 3.1 跨世主体感

玩家长期身份来自真灵，而不是某一世的姓名、宗门职位或库存。死亡和转世不是简单重开，而是把前世信息、失败标签、后手、真灵强度和部分初始化选择转化为下一世策略基础。

### 3.2 有压力的修炼选择

游戏以季度推进，每季度有 6 个朔望行动格。玩家不能在同一季度同时完成所有目标。修炼、移动、探索、宗门职责、后手回收、突破准备、事件响应都必须竞争时间预算。

### 3.3 突破风险感

突破不是概率按钮。大境界突破由准备度门槛、关键突破物、风险提示、多阶段事件链、失败标签和轮回账本构成。

### 3.4 后手可信感

玩家正式布置的后手必须可追踪、有日志、有位置、有封存资产、有暴露或失效原因链。正式后手可以受损或被争夺，但不能无理由消失。

### 3.5 宗门平台感

宗门不是玩家本体，而是组织资源平台。玩家通过身份、职位、贡献、声望、权限和关键 NPC 支持影响宗门，但宗门库存、行动和节点控制仍是独立组织状态。

### 3.6 共享世界演化感

地图节点、资源槽、建筑槽、秘境窗口、宗门行动、世界事件、传闻、玩家行动、AI 宗门策略共同改变世界。多人不是强 PvP，而是共享世界中的间接竞争。

## 4. 标准季度流程

当前标准季度流程统一为：

```
季度开始
→ 世界刷新
→ 玩家查看角色、地图、宗门、账本、传闻和风险提示
→ 宗门行动决策阶段
→ 宗门行动即时反馈
→ 角色行动决策阶段
→ 玩家规划 6 个朔望行动格
→ 在线玩家锁定行动
→ 离线 / 超时玩家生成稳健托管
→ 权威服务器统一结算
→ 必要时插入事件链
→ 回写角色、库存、节点、宗门、账本、日志、传闻
→ 进入下一季度
```

开发重点：

- 客户端只提交意图。
- 服务端负责权威校验和最终回写。
- 本地单人也走同一套服务端结算流程。
- 无人在线时世界不自动推进。

## 5. 修炼里程碑与阶段编码

MVP 验证使用 M0 / M1 / M2 / M3 表达玩家流程里程碑。

```
M0：开局与入门阶段。
M1：完成第一阶段修行闭环，具备第一次关键突破准备。
M2：突破到第二大境界，进入宗门中层影响区。
M3：突破到第三大境界起点，进入宗门高层决策体验。
```

规则层境界编码统一使用：

```
A-1, A-2, A-3
B-1, B-2, B-3
C-1, C-2, C-3
```

M3 不是 `C-3`，而是第三大境界起点，通常对应 `C-1`。

开发字段建议：

```
CultivationStage {
  code: "C-1",
  major_code: "C",
  minor_index: 1,
  major_order: 3,
  absolute_order: 301,
  display_name_key: "stage.core_3_minor_1"
}
```

规则代码不得直接判断 `lianqi`、`zhuji`、`jindan` 等世界观包装字符串。包装名只作为本地化显示。

## 6. 顶层非目标

MVP 不做以下内容：

- 实时 MMO。
- 现实时间挂机私服。
- 纯宗门经营游戏。
- 强 PvP 沙盒。
- 玩家直接交易、直接赠予、共同秘境、互相护法。
- 玩家暗杀玩家、直接抢洞府、围杀转世角色、破坏他人突破、离线袭击玩家主体。
- 深度 NPC 生态和所有 NPC 全量经济模拟。
- 完整高境界体系。
- 大规模宗门战争。
- 完整炼丹炼器工业链。
- 创意工坊或商业化运营系统。

## 7. 子系统依赖图

建议以 S1 作为结算总线，其他系统不得绕过 S1 直接改写世界状态。

```

        ↑

        ↑

```

## 8. 推荐开发顺序

### 第一阶段：基础运行闭环

1. 房间创建、本地服务器、季度推进。
2. 玩家真灵与当世角色。
3. 地图节点图与当前位置。
4. 6 个朔望行动格规划。
5. 服务器结算、日志、存档。

### 第二阶段：新手流程闭环

1. 初次投生。
2. 青禾村 / 镇集 / 山门路线。
3. 移动事件与选择事件。
4. 拜入宗门。
5. 初始功法与轻量修炼。

### 第三阶段：成长与突破闭环

1. 修炼收益、主修道功、阶段进度。
2. 小境界升级。
3. 大境界突破准备面板。
4. 关键突破物消耗。
5. M1 → M2 突破事件链。
6. 失败标签与轮回账本。

### 第四阶段：宗门与世界闭环

1. 宗门身份、权限、贡献、声望。
2. 宗门库存五类资源。
3. 每宗门每季度 1 个主行动。
4. 节点资源常态产出与控制权变化。
5. 秘境 / 节点危机 / 资源名额窗口。

### 第五阶段：跨世与多人闭环

1. 死亡与转世。
2. 正式后手布置与回收。
3. 3 人房间、锁定 / 超时 / 托管。
4. 分宗并行、传闻和间接竞争。
5. 存档恢复与调试回放。

## 9. 开发验收原则

每个子系统验收时都要问四个问题：

1. 这是否服务玩家体验闭环？
2. 这是否遵守系统边界？
3. 这是否有可验证的最小闭环？
4. 这是否控制了 MVP 实现成本？

若某功能无法回答上述问题，应推迟到正式版或内容扩展阶段。
