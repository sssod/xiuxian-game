# 系统设计｜随机事件玩法

## 1. 设计定位

随机事件是在共享世界压力下，把玩家、NPC、宗门、节点、路线、资源、后手和世界状态转化为可处理问题、判定、窗口、交锋入口、余波和结果包的系统。它不以“随机讲很多故事”为目标，而是负责让世界变化以玩家可以理解、选择和追溯的方式进入结算。

常规事件的核心玩法类型是选择事件：

```text
系统抛出一个可结算的问题
→ 玩家用一个选项表达解题姿态
→ 系统根据选项、条件、资源和可见性生成后果
→ 结果通过权威结算合并到角色、库存、节点、宗门、日志、传闻和回放
```

事件系统只负责事件框架、候选生成、选择结构、判定和结果请求，不替代战斗、突破、死亡 / 转世、库存、后手、宗门 AI、地图节点或经济系统的内部结算。所有高价值变化必须进入结果包，不能由事件文本直接改写世界状态。

## 2. 当前结论

1. 随机事件运行在 `world_day / world_hour` 与 `hour_tick` 上，不再使用旧式 `quarter / tick / 行动格` 作为事件主时间字段。
2. 事件候选由角色位置、路线、行动、节点风险、宗门状态、NPC 关系、隐藏层、后手、传闻和资源预算共同生成，不能靠刷新 UI 改变结果。
3. 常规事件以“问题 + 解题姿态 + 可解释后果”为核心；选择事件、检定事件、投入事件、交锋事件、探索揭示事件、窗口事件、余波事件和协同 / 仲裁事件分别承接不同玩法压力。
4. 信息事件不打断；普通个人选择事件和轻遭遇使用本人局部时停；正式交锋和突破挑战进入 B1；全局公共事件和同步保护进入 P0。
5. 未知事件选项、重大机缘、心魔、直接冲突、正式交锋轮内策略和突破挑战轮内选择不进入普通行动队列。
6. 显式托管只可保守处理低价值事件；死亡风险、正式交锋、重大心魔、重大机缘、不可逆选择、大境界突破挑战、多人直接冲突和宗门重大事件仍必须进入通知、局部时停、B1 或 P0。
7. 事件奖励、库存变化、宗门资源、NPC 资产、后手资产和遗留设施开启都必须有合法来源、可追溯容器和结果包记录。
8. 事件系统保留概率、候选权重、触发上限、窗口频率、检定公式和托管白名单为待补项，不在本文伪装成定稿。
9. F1 不消除事件；闭关、长期赶路、洞天和宗门低风险职责中的事件按摘要、自动处理、软中断或硬中断进入 F1 批量结果。

## 4. 核心循环或触发入口

### 4.1 事件主循环

事件系统从共享世界推进或明确系统入口中生成上下文，再进入候选、实例、选择和结果包流程：

```text
world_day / world_hour / hour_tick 推进
→ 命中移动、行动、节点、宗门、窗口、后手、死亡 / 转世、传闻或调试触发源
→ 生成 EventContext
→ 读取事件模板与候选条件
→ 生成 EventChain / ChoiceEvent / CheckEvent 等实例
→ 根据 event_time_mode 决定信息记录、局部时停、B1 或 P0
→ 若处于 F1，按事件等级决定摘要、自动处理、软中断或硬中断
→ 玩家选择、系统检定、投入、交锋或窗口处理
→ 输出 EventOutcome 和 ResultPackage
→ 权威结算合并角色、库存、节点、路线、宗门、NPC、后手、日志、传闻和回放
```

事件链可以中断角色当前行动，但中断后果必须通过结果包表达：

```text
是否继续原计划；
是否暂停、跳过、延误或替换当前行动；
是否改变位置、状态、库存、节点、宗门或路线；
是否进入战斗、突破、死亡 / 转世、后手、遗留设施等专用事件链。
```

### 4.2 MVP 事件分类

按触发来源，MVP 事件分为：

| 类型 | 触发来源 | 常见结果 |
| --- | --- | --- |
| 移动事件 | 离开节点、进入节点、途经路线、路线段小时推进、目标节点抵达 | 轻遭遇、路线阻断、延误、资源消耗、线索发现、行踪暴露、安全抵达 |
| 节点事件 | 节点、资源槽、设施、隐藏层、控制权、风险状态 | 资源异变、妖兽袭扰、探索发现、秘境入口波动、设施损坏、宗门冲突、控制权争夺 |
| 宗门事件 | 宗门身份、职位、资源申请、宗门库存、宗门持续行动、宗门 NPC 支持 | 宗门议事、委派、资源审批、宗门清点、节点支援、宗门传闻 |
| 世界演化事件 | 每小时世界推进、宏观周期、区域效果、资源预算、公开局势 | 市场波动、区域灾变、资源批次显现、宗门动向、传闻候选 |
| 秘境 / 窗口事件 | `OpportunityWindow` 的开启、关闭、进入、错过、争夺 | 秘境窗口、节点危机、突破资源名额、短期交易、护法机会 |
| 控制权变化事件 | 节点影响力阈值、宗门行动、玩家处理节点事件、NPC 压力、后手触发 | 控制权变更、路线封锁、驻守加强、资源收益权变化、公开地图变化 |
| 传闻生成事件 | 公开日志、事件结果、宗门动作、节点变化、突破公开影响、后手暴露 | 模糊信息、延迟情报、不完整线索、宗门摘要、世界传闻 |
| 专用事件链入口 | 突破、战斗、死亡 / 转世、后手、遗产、遗留设施 | B1 交锋、突破挑战、死亡结算、宗门清点、破阵争夺、真灵藏宝开启 |

专用事件链包括：

```text
突破；
战斗 / 斗法；
死亡 / 转世；
宗门遗产清点；
宗门外个人洞府 / 普通藏宝 / 旧洞府等无主遗留设施开启；
真灵藏宝跨世感应和开启。
```

### 4.3 事件时间模式

MVP 事件按时间处理分为：

| 类型 | `event_time_mode` | 时间处理 | 示例 |
| --- | --- | --- | --- |
| 信息事件 | `info` | 不打断，进入日志 / 传闻 | 坊市价格、宗门传闻、节点局势 |
| 普通个人选择事件 | `local_time_stop` | 本人局部时停，外部 N1，gap≤1 日，结束后 C1 | 同门邀约、个人机缘、资源反馈、小境界选择 |
| 轻遭遇 | `light_encounter` | 按普通个人选择事件处理 | 低阶妖兽、小型陷阱、外门挑衅 |
| 正式交锋 | `formal_encounter_b1` | 世界 B1，按交锋轮结算 | 强敌斗法、玩家直接冲突、秘境关键战斗 |
| 突破挑战 | `breakthrough_b1` | 世界 B1，按交锋轮结算 | 筑基挑战、结丹挑战 |
| 全局公共事件 | `global_pause_p0` | 世界 P0 | 宗门大会、全员决策、世界级灾变 |

F1 批量结算中的事件等级：

| 等级 | 处理 |
| --- | --- |
| `silent` | 后台记录或仅影响数值 |
| `summary` | 写入 F1 摘要，不中断 |
| `auto` | 按玩家预设、托管策略或安全默认处理，并写入摘要 |
| `soft_interrupt` | 有预设可自动处理；无预设退出 F1 到 N1 |
| `hard_interrupt` | 立即退出 F1，进入 N1 / B1 / P0 |

事件模板必须提供：

```yaml
event_time_mode: info | local_time_stop | light_encounter | formal_encounter_b1 | breakthrough_b1 | global_pause_p0
safe_default_option_ref: string | null
p0_required_if_timeout: bool
visibility_policy: private_player | known_to_party | sect_visible | rumor_visible | public_world | hidden_world | debug_only
result_package_template: object
```

普通个人事件保留玩家处理权；重大事件不得被普通队列、自动兜底或低价值托管策略吞掉。

## 5. 规则与状态

### 5.1 事件触发上下文

`EventContext` 推荐字段：

```yaml
EventContext:
  context_id: string
  trigger_world_day: int
  trigger_world_hour: int
  trigger_type: travel_leave | travel_enter | route_hour_tick | action_hour_tick | action_complete | node_update | sect_update | window_update | contingency_trigger | death_or_reincarnation | rumor_update | manual_debug
  event_time_mode: info | local_time_stop | light_encounter | formal_encounter_b1 | breakthrough_b1 | global_pause_p0
  actor_refs: list[string]
  faction_refs: list[string]
  node_id: string | null
  route_id: string | null
  route_segment_ref: string | null
  current_command_ref: string | null
  action_context: object
  visibility_context: object
  risk_level: low | medium | high | unknown | null
  resource_slot_refs: list[string]
  facility_refs: list[string]
  hidden_layer_refs: list[string]
  contingency_refs: list[string]
  remnant_site_refs: list[string]
  opportunity_window_refs: list[string]
  rumor_refs: list[string]
  current_macro_period_id: string | null
  rng_namespace: string
```

迁移口径：

| 旧字段 / 旧说法 | 当前口径 |
| --- | --- |
| `quarter` | 不作为事件主时间字段；宏观批次使用 `current_macro_period_id` |
| `tick` | 具体结算使用 `hour_tick`、`trigger_world_day`、`trigger_world_hour` |
| `danger_level` | 地图风险统一为 `risk_level`；事件自身可另有风险描述标签 |
| `route_segment` | 迁移为 `route_segment_ref` |
| 行动格消耗 | 迁移为 `consumed_hours`、行动进度变化、B1 世界推进或交锋自身结算耗时 |
| 世界刷新只在季度开始发生 | 迁移为世界小时演化 + 宏观周期批次；窗口、资源和传闻仍可按宏观周期批量显现 |

候选生成必须使用稳定随机种子或稳定排序，不能靠刷新 UI 改变结果。

### 5.2 事件链结构

MVP 事件链不需要复杂脚本语言，优先使用模板、条件、阶段、选项、检定、结果包和子事件请求。

```yaml
EventChain:
  chain_id: string
  event_type: string
  gameplay_type: choice | check | investment | clash | discovery | window | aftermath | arbitration
  parent_context: EventContext
  stages: list[object]
  choices: list[EventOption]
  checks: list[object]
  result_packages: list[ResultPackage]
  visibility_rules: list[object]
  log_rules: list[object]
  child_event_requests: list[object]
  status: pending | active | resolved | failed | escalated
```

事件链状态至少区分 `pending / active / resolved / failed / escalated`。进入 `escalated` 时，父系统必须明确承接到 B1、P0、死亡 / 转世、突破、宗门清点、遗留设施争夺或其他专用链。

### 5.3 玩法层事件类型

#### 5.3.1 选择事件

选择事件是常规事件核心。它用于移动、节点、关系、资源、传闻、宗门和突破外扰等普通问题。

```yaml
ChoiceEvent:
  event_id: string
  template_id: string
  problem_statement_key: string
  event_context: EventContext
  candidate_option_dimensions: list[ChoiceDimension]
  generated_candidate_options: list[EventOption]
  primary_options: list[EventOption]
  overflow_options: list[EventOption]
  option_view_state: primary | overflow
  selected_option_ref: string | null
  checks: list[object]
  outcome_package_refs: list[string]
  child_event_requests: list[object]
  log_rules: list[object]
```

#### 5.3.2 检定事件

检定事件用于低交互或不适合打断玩家的判定，例如行踪暴露、线索发现、节点灵气波动、护法阵自动抵消外扰、被动法宝受损、NPC 察觉欺诈痕迹。

检定事件不承担重大路线决策。高风险、高损失、高稀缺机会事件应转成选择事件、正式交锋或窗口事件。

#### 5.3.3 投入事件

投入事件让玩家在离散档位中承诺资源，以降低风险、提高收益或推进事件。

MVP 只允许离散档位：

```text
不投入；
标准投入；
高额投入。
```

不使用滑杆式连续追加投入。每个投入档位必须显示明确方向性后果，并通过库存、资源预留、行动资源输入或事件选项资源输入校验来源。

#### 5.3.4 交锋事件

交锋事件用于高风险、多阶段对抗。战斗 / 斗法和突破挑战是专用交锋事件。

普通选择事件可以触发交锋，但不在自身文本中假结算战斗。例如：

```text
选择事件：如何处理威胁？
→ 选择正面应对
→ 触发战斗 / 斗法事件链
→ 战斗返回结果包
→ 父事件生成余波事件或直接回写后果
```

#### 5.3.5 探索揭示事件

探索揭示事件的主要收益是信息、线索、隐藏层、入口或后续行动链，而不是立即发放资源。

常见结果：

```text
解锁节点；
解锁特殊持续行动；
增加线索进度；
改变可见传闻；
生成后续窗口事件；
提高某类选择事件中出奇制胜或解构问题选项的可用性。
```

#### 5.3.6 窗口事件

窗口事件是带时间边界的机会或危机状态，不是单独文本事件。

MVP 窗口事件范围：

```text
秘境窗口；
节点危机；
突破资源 / 名额窗口。
```

进入窗口后，具体交互复用选择事件、投入事件、交锋事件或检定事件。

#### 5.3.7 余波事件

余波事件用于主要事件后处理，例如战斗结束、突破失败、欺诈暴露、宗门行动失败、节点灾变、NPC 死亡和遗产 / 清点前后处理。

余波事件不应无成本逆转核心失败，只能改变损失分布、信息公开程度、关系后果和后续修复路径。

#### 5.3.8 协同 / 仲裁事件

协同 / 仲裁事件用于多个主体对同一事件拥有不同立场、权限或行动意图的场景。

MVP 只保留接口和少量场景：

```text
宗门行动中的建议 / 决策采纳；
NPC 护法或宗门支持的抽象修正；
多宗门争夺窗口时的可见状态与结果包接口。
```

复杂多人 PvP 仲裁后置。直接玩家冲突若发生，进入正式交锋。

### 5.4 选择事件五类内部维度

五类维度是设计者组织选项的内部结构，不是玩家 UI 必须显示的固定分类名。

| 维度 | 内部枚举 | 定义 | 典型代价 / 风险 |
| --- | --- | --- | --- |
| 正面应对 | `direct` | 正面回答事件问题，并按当前语境的朴素规则处理 | 直接资源消耗、正面战斗、承受失败 |
| 出奇制胜 | `unconventional` | 使用特殊资源、技能、身份、关系、地点布置或信息真正解决问题 | 消耗稀缺资源、暴露能力、占用后手 |
| 逃避推诿 | `avoid` | 离开、拖延、绕行、转交、降低接触强度，避免承担主要风险 | 奖励损失、声望下降、窗口错过、长期后果 |
| 解构问题 | `deconstruct` | 改变问题成立的前提、身份关系、规则解释或目标定义 | 关系代价、越权风险、失败后更严重追责 |
| 欺诈蒙骗 | `deceive` | 未真正解决问题，而是通过伪装、隐瞒、误导或伪造获得解决后的回报 | 暴露风险、隐藏后患、传闻、追查标签 |

规则：

1. 每个维度在同一事件中最多生成 1 个候选选项。
2. 一般事件应尽量提供正面应对；若条件不足，可退化为直面失败、如实回答或承受后果。
3. 出奇制胜通常依赖稀缺客观条件，例如高阶符箓、特殊法宝、宗门权限、前世线索、隐藏身份或地点布置。
4. 逃避推诿不是失败按钮；对低价值、高风险、非必要问题，它可以是理性选择。
5. 解构问题常依赖身份、关系、证据、权限、前世记忆或规则理解，成功时常降低事件严重度或改变事件类型。
6. 欺诈蒙骗必须留下暴露风险、后续追责、因果负担、关系破裂或隐藏失败标签，不得只给短期收益。

### 5.5 选项生成与展示规则

候选选项生成流程：

```text
读取事件模板
→ 读取 EventContext
→ 逐个维度检查候选条件
→ 每个维度保留最匹配的 0–1 个选项
→ 使用稳定排序或事件实例稳定随机种子分配主选项和溢出选项
```

候选条件可以包括：

```text
修为阶段；
生机 / 元气 / 神念状态；
当前行动状态；
当前节点、路线、风险等级；
已学功法、术法、神通；
随身法宝、符箓、丹药、特殊物品；
宗门职位、权限、贡献、门内声望；
NPC 关系、道侣、弟子、师承；
前世后手、真灵感应、轮回账本信息；
当前事件已揭示的信息；
世界日志隐藏标签；
宗门清点、遗留设施或隐藏层状态。
```

主选项区规则：

```text
候选可见选项 = 0：改用检定事件 / 余波事件，或生成兜底正面应对。
候选可见选项 = 1：主选项区显示 1 个选项。
候选可见选项 = 2–3：主选项区全部显示。
候选可见选项 > 3：主选项区显示 3 个选项，并在第三个选项后显示“...”按钮。
```

超过 3 个开放选项时：

```text
主选项区优先保留：正面应对 / 逃避推诿 / 欺诈蒙骗
溢出选项区优先放入：出奇制胜 / 解构问题
点击“...”切换到溢出选项区
切换后“...”变为“返回”
点击“返回”回到主选项区
```

UI 约束：

1. 不使用“上一页 / 下一页”式翻页按钮。
2. 不显示页码。
3. 溢出区不是与主选项完全等价的第二页，而是更深一层、条件更强、解释成本更高的处理方式。
4. “返回”只代表回到主选项区，不代表取消事件。
5. MVP 中溢出选项区通常最多显示 2 个开放选项。

不可用选项显示规则：

1. 常规事件默认隐藏不可用选项。
2. 教学事件可灰显少量不可用选项，说明缺少什么。
3. 突破准备面板可显示不可用准备方向，因为它服务长期规划。
4. 关键节点事件可显示少量不可用高价值解法，作为未来目标提示。
5. 常规事件不应频繁灰显不可用选项，避免玩家把事件理解成资格列表。

### 5.6 事件结果规则

每个选项必须至少影响一类内容：

```text
角色状态；
物品或库存；
行动进度或连续状态；
节点状态；
路线状态；
宗门关系、贡献、职位评价或库存；
NPC 关系；
战斗、突破、死亡、后手、遗留设施等子事件入口；
传闻与世界日志；
轮回账本或隐藏失败标签。
```

结果分三层：

| 层级 | 含义 |
| --- | --- |
| 即时结果 | 当场获得、损失、位置变化、状态变化、进入子事件 |
| 延迟结果 | 后续世界小时、宏观周期、节点、关系或传闻中触发 |
| 隐藏结果 | 玩家暂时不可见，但进入隐藏世界日志、因果标签或后续事件池 |

失败也必须有方向，不能只输出“未成功”。失败标签示例：

```text
资源不足；
判断失误；
修为压制；
关系不足；
伪装暴露；
护法不足；
地点不稳；
心境动摇；
行踪暴露；
前世后手失配；
宗门权限不足；
遗留设施开启条件不满足。
```

失败标签可以进入事件日志、轮回账本、NPC 记忆、宗门评价、传闻候选或后续事件池。

### 5.7 局部时停、默认选项与 C1

普通个人选择事件和轻遭遇使用本人局部时停：

```text
事件玩家本人局部时停；
事件玩家当前行动、资源变化、风险变化冻结在触发时刻；
其他玩家、宗门和世界继续 N1；
gap 最多 1 游戏日；
事件结束后 C1 追赶补结算；
其他玩家不看到事件归因。
```

事件选项可以有游戏内时间成本。该成本从事件触发 `world_hour` 开始回填，而不是从玩家现实提交选择后开始计算。

gap 阶段：

| gap | 系统行为 |
| --- | --- |
| 0～12 游戏小时 | 正常局部时停 |
| 12～18 游戏小时 | 仅事件玩家本人轻提示 |
| 18～24 游戏小时 | 事件玩家本人强提示 |
| 24 游戏小时 | 自动安全默认或 P0 同步保护 |

到达 1 日：

```text
有安全默认选项 → 自动执行默认选项；
无安全默认选项 → P0 同步保护。
```

安全默认例子：

```text
同门邀约：默认婉拒；
坊市机会：默认错过；
普通资源反馈：默认接受保守方案；
轻度机缘：默认不冒险；
突破前道具确认：默认取消突破，进入休整。
```

P0 同步保护例子：

```text
死亡边缘；
不可逆功法路线选择；
重大夺舍 / 心魔交易；
无法默认处理的多人冲突；
严重资源损毁选择。
```

C1 只结算确定性内容：

```text
行动进度；
修炼收益；
资源消耗；
药性衰减；
伤势恢复；
队列切换；
已知状态变化；
事件选择带来的明确后果。
```

C1 不触发：

```text
随机个人事件；
普通机缘；
普通战斗；
软机会事件；
普通心魔；
普通资源反馈。
```

`CatchupSettlementState` 必须满足：

```yaml
deterministic_only: true
random_events_blocked: true
```

### 5.8 队列、托管与事件处理权

未知事件的选项选择不进入普通行动队列。普通队列只保存当前已经合法的普通指令，不能保存通用事件预案、条件脚本或未来资源规划。

不进入普通队列的事件选择包括：

```text
未知事件的选项选择；
需要新情报判断的宗门站队；
多人直接冲突选择；
正式交锋中的轮内策略选择；
突破挑战中的轮内选择；
临时触发的机缘事件；
临时触发的心魔或风险抉择。
```

自动兜底只用于防止角色行动空档，不承担事件处理预案，不参与 F1。

显式托管可以保守处理低价值事件：

```text
普通邀约：婉拒；
普通传闻：记录；
低价值机会：忽略；
轻微状态波动：保守处理；
普通资源波动：不冒险。
```

重大事件仍进入通知、局部时停、B1 或 P0：

```text
死亡风险；
正式交锋；
重大心魔；
重大机缘；
不可逆选择；
大境界突破挑战；
多人直接冲突；
宗门重大事件。
```

F1 中同样适用该边界。以下内容不允许普通预设自动处理：

```text
高风险突破；
主动转世；
叛宗；
强 PvP；
消耗稀有不可逆资源；
重大路线选择；
暴露核心后手；
开启高危藏宝；
决定他人利益的公共选择。
```

丹药、灵材、符箓和临时 boost 作为行动或事件选项资源输入。事件选项生效时才消耗对应资源，并必须可追溯到合法资产容器、宗门预留、事件锁定奖励包或其他合法来源。

### 5.9 优先级与去重

同一 `hour_tick` 和同一上下文中可能有多个候选事件。MVP 规则：

1. 强制事件优先于普通事件。
2. 专用事件链优先于普通传闻。
3. 已经进入 B1 或 P0 的事件优先锁定对应速度状态。
4. 同一语义事件在同一 `hour_tick` 和同一上下文中只触发一次。
5. 事件链进行中时，普通角色时间线按 `event_time_mode` 决定冻结、继续或进入交锋。
6. 事件返回后，由权威结算决定是否继续原计划、进入 C1、跳过指令、自动兜底或开启子事件。
7. 候选池最大触发数量、权重和概率表尚未定，不在本文补写数值。

`cooldown_tags` 可用于防止同类事件短期重复爆发。节点、路线、窗口、NPC 或宗门的状态变化应优先改变候选池，而不是靠无来源随机刷新制造重复事件。

## 6. 资源、角色、地图、事件或 NPC 接口

### 6.1 移动、节点与窗口接口

移动事件读取：

```text
当前位置；
目标节点；
路线是否可见；
passability；
requirements；
current_cost_hours；
risk_tags；
角色状态；
宗门、NPC 或事件授予的通行许可；
是否存在 route_blocker 或 public_node_event。
```

移动中可触发：

```text
轻遭遇；
正式追击；
路线阻断；
绕行或延误；
行踪暴露；
线索发现；
节点窗口提示；
资源或状态消耗。
```

节点事件挂载点：

```text
NodeState.active_events；
NodeState.active_windows；
NodeResourceSlot.depletion_event_refs；
facility_refs；
hidden_layer_refs；
contingency_refs；
sect_clearance_refs；
remnant_site_refs；
route_edge_refs；
cooldown_tags。
```

机会窗口最少字段：

```yaml
OpportunityWindow:
  window_id: string
  node_id: string
  starts_world_day: int
  starts_world_hour: int
  ends_world_day: int
  ends_world_hour: int
  visibility_policy: private_player | known_to_party | sect_visible | rumor_visible | public_world | hidden_world | debug_only
  entry_requirements: list[object]
  event_template_refs: list[string]
  contest_policy: string
```

窗口开启、关闭、进入、错过、被争夺或被后手影响，都必须写入结果包和回放。玩家进入窗口必须通过个人行动、事件选择或正式交锋入口完成，地图不能直接改角色状态。

### 6.2 宗门、NPC、后手与遗留设施接口

宗门事件可以读取身份、职位、贡献、门内声望、资源申请、宗门库存、资源预留、宗门持续行动、宗门 NPC 支持、节点压力和事件状态。

宗门资源申请可以作为普通行动，也可以作为事件选项。资源批准、预留、消耗、释放、过期和拒绝必须写入宗门审计日志与结果包。

NPC 交易、战斗奖励或死亡资产只能来自：

```text
NPC 已持久化的随身 / 可调用资产；
NPC 合法个人储藏或洞府库存中当前可调用的资产；
事件链在结算前明确锁定的交易包、赔偿、赎买、赠予或奖励包；
有预算来源并写入日志的轻量交易包。
```

禁止在事件开始时临时生成完整 NPC 库存，也禁止把商店、宗门或节点库存写成入口 NPC 的个人背包。

遗产、后手和无主遗留设施必须区分：

| 类型 | 事件边界 |
| --- | --- |
| 宗门相关遗产 / 清点 | NPC 随身物品、NPC 个人洞府库存、玩家转世前留在宗门管辖个人洞府中的普通库存、宗门托管 / 职务资产，可触发宗门锁定、清点、回收和审计事件 |
| 宗门外个人洞府 / 普通藏宝 / 旧洞府线索 | 无主遗留设施，不进入遗产分配、继承或宗门回收；通过钥匙、功法、线索、位置、事件条件、破阵或争夺事件开启 |
| 真灵藏宝 | MVP 正式后手藏物形态；绑定同一真灵，跨世感应和开启；受设置数量与单个容量限制；MVP 不生成被他人搬空、损坏或移动的事件 |

宗门外遗留设施记录应能表达：

```yaml
RemnantSiteRecord:
  remnant_site_id: string
  location_node_id: string
  attachment_mode: natural_resource_slot | hidden_layer | facility
  location_resource_slot_id: string | null
  location_hidden_layer_id: string | null
  remnant_type: outside_cave | treasure_cache | sealed_room | clue_site | lost_storage
  origin_hint_ref: string | null
  storage_container_id: string | null
  access_condition: object
  visibility_policy: private_player | known_to_party | sect_visible | rumor_visible | public_world | hidden_world | debug_only
  discovered_by: list[string]
  blocks_resource_slot_facility_construction: bool
  status: hidden | known | opened | depleted | lost | contested
```

高风险后手回收、破阵、争夺或核心藏宝开启必须由玩家明确行动或事件选择推动。自动兜底和显式托管不得主动回收、暴露、移动或销毁核心后手。

### 6.3 可见性、日志与传闻接口

可见性层级：

```text
private_player：单个玩家、真灵或当前角色可见；
known_to_party：当前事件、队伍、临时协作对象或授权对象可见；
sect_visible：宗门权限范围内可见；
rumor_visible：作为传闻、模糊信息、延迟信息或不完整情报可见；
public_world：公共世界信息，可进入公开地图或世界摘要；
hidden_world：世界真实状态记录，玩家不可直接看到；
debug_only：调试、审计和开发工具可见。
```

需要区分：

| 记录 | 用途 |
| --- | --- |
| 世界日志 | 系统完整记录，用于测试、调试、回放，默认玩家不可见 |
| 角色日志 | 角色自身经历、听闻和确认的信息 |
| 宗门摘要 | 宗门成员或权限层可见的组织信息 |
| 地图公开变化 | 节点、路线、窗口、风险、控制权的可见结果 |
| 传闻 | 世界日志或事件结果的可见子集，可模糊、延迟、不完整 |
| 轮回账本 | 与真灵、转世、失败原因、后手和跨世线索相关的长期记录 |

`RumorEntry` 推荐结构：

```yaml
RumorEntry:
  rumor_id: string
  source_ref: string
  created_world_day: int
  created_world_hour: int
  visibility_policy: private_player | known_to_party | sect_visible | rumor_visible | public_world | hidden_world | debug_only
  node_id: string | null
  sect_id: string | null
  confidence: low | medium | high
  delay_hours: int
  summary_text_key: string
  hidden_truth_ref: string | null
```

传闻生成受以下因素影响：

```text
事件公开性；
地点人流；
宗门关系；
玩家声望；
行踪暴露标签；
事件严重度；
情报能力；
节点控制权；
宗门清查；
后手风险标签。
```

传闻文本只描述可见后果，不泄露 `hidden_truth_ref`、私人事件归因、隐秘局部时停来源、未公开突破选择、隐藏后手真实归属或 Debug 信息。

公开地图变化示例：

```text
黑石岭驻守加强。
云麓山道近日妖兽踪迹增多。
青木谷灵气波动，疑有秘境窗口。
坊市筑基资源短缺。
```

### 6.4 权威结算接口

事件结果交给权威结算合并。事件系统输出的结果包可包含：

```yaml
ResultPackage:
  package_id: string
  source_system: event
  world_day: int
  world_hour: int
  time_mode: string
  speed_before: F1 | N1 | B1 | P0
  speed_after: F1 | N1 | B1 | P0
  character_delta: object
  ongoing_state_delta: object
  inventory_delta: object
  resource_effect_delta: object
  node_delta: object
  route_delta: object
  resource_slot_delta: object
  event_window_delta: object
  sect_delta: object
  npc_delta: object
  relationship_delta: object
  contingency_delta: object
  legacy_delta: object
  visibility_delta: object
  rumor_entries: list[RumorEntry]
  ledger_entries: list[object]
  event_outcomes: list[EventOutcome]
  f1_batch_ref: string | null
  auto_resolved_event_refs: list[string]
  interrupted_event_ref: string | null
  triggered_child_events: list[object]
  visible_log_entries: list[object]
  hidden_world_log_entries: list[object]
  debug_log_entries: list[object]
```

结果包要求：

1. 所有状态变化必须带 `world_day / world_hour`。
2. 所有库存、物品、资源、奖励、预留和转移必须可追溯来源。
3. 高价值变化必须进入日志、账本或回放。
4. Debug 信息不能进入普通玩家 UI。
5. 事件结果不得绕过权威结算直接改写角色、节点、宗门或库存。
6. 事件结果若向角色施加伤势、药性、祝福、诅咒、封禁、标记或其他持续影响，应写入 `ongoing_state_delta`，并由《角色持续状态系统》（`02_角色与真灵设计/07_角色持续状态系统.md`）统一管理生命周期、叠加互斥和属性修正导出。

## 7. 数据字段建议

| 字段 | 含义 |
| --- | --- |
| `EventContext.context_id` | 事件上下文唯一标识，用于连接触发源、候选池、事件实例和回放 |
| `EventContext.trigger_world_day / trigger_world_hour` | 事件触发的共享世界时间 |
| `EventContext.trigger_type` | 触发来源，例如移动、行动完成、节点更新、宗门更新、窗口更新、后手触发、死亡 / 转世或传闻更新 |
| `EventContext.event_time_mode` | 事件时间处理模式，决定信息记录、局部时停、B1 或 P0 |
| `EventContext.actor_refs / faction_refs` | 事件相关角色、玩家、NPC、宗门或势力引用 |
| `EventContext.node_id / route_id / route_segment_ref` | 事件发生位置、路线和路段语义 |
| `EventContext.current_command_ref` | 触发时角色正在执行或刚完成的行动指令 |

## 8. UI 展示边界

常规选择事件卡片建议展示：

```text
事件标题；
事件问题 / 局面描述；
关键上下文标签；
主选项 1～3；
仅在存在溢出选项时显示“...”；
可能后果方向提示；
确认按钮。
```

点击“...”后切换为：

```text
事件标题；
事件问题 / 局面描述；
关键上下文标签；
溢出选项 1～2；
返回按钮；
可能后果方向提示；
确认按钮。
```

后果提示显示方向，不显示隐藏标签和精确追查条件：

```text
可能进入战斗；
消耗元气；
延误行程；
暴露身份；
提高关系；
写入传闻；
可能产生隐藏后患。
```

事件文本可以有风味，但必须服务于选择。

不推荐：

```text
长篇描述三屏文字，最后只有“继续”。
```

推荐：

```text
短文本建立问题
→ 用选项表达解法
→ 结果文本解释后果
→ 写入日志、传闻或子事件
```

只有 1 个选项不等于设计失败。合理场景包括：

```text
玩家客观条件极差，只能承受后果；
玩家已经提前准备，唯一选项是执行预案；
事件是强制后果展示；
事件处于专用事件链中的过渡阶段。
```

但如果事件只是展示结果，应改为检定事件或余波事件，不应伪装成选择事件。

普通 UI 不展示其他玩家私人事件归因、隐秘局部时停原因、隐藏后手真实归属、`hidden_truth_ref`、精确候选权重、Debug 字段、内部倍率或 C1 内部逐 tick 明细。

## 9. MVP 范围

MVP 应实现：

1. 信息事件进入角色日志、宗门摘要、地图变化或传闻，且不打断玩家。
2. 移动中至少触发一种路线事件，并按 `event_time_mode` 处理。
3. 节点上至少触发一种资源、风险、窗口或控制权相关事件。
4. 常规选择事件使用 1～3 个主选项和“...”溢出结构。
5. 常规事件默认隐藏不可用选项，教学、突破准备和关键节点事件可灰显少量例外。
6. 普通个人事件冻结本人 `frozen_world_day / frozen_world_hour`，其他玩家、宗门和世界继续 N1。
7. gap 在 12 / 18 / 24 游戏小时正确提示、默认处理或进入 P0 同步保护。
8. C1 追赶只补确定性内容，不触发新的随机个人事件。
9. 轻遭遇按个人局部时停处理。
10. 正式交锋和突破挑战进入 B1，不由普通队列替代。
11. 显式托管只保守处理低价值事件，重大事件仍通知、局部时停、B1 或 P0。
12. 事件结果进入结果包、日志、传闻和回放，不直接绕过权威结算。
13. 传闻不泄露私人事件归因、隐藏真相引用或 Debug 信息。
14. 宗门外个人洞府、普通藏宝、真灵藏宝与宗门相关遗产在事件链中有清晰边界。
15. F1 中的摘要事件、自动处理事件、软中断事件和硬中断事件能写入批量摘要或中断原因。

MVP 不实现：

1. 完整事件文本库。
2. 事件概率、权重、候选池最大触发数量和窗口出现频率的最终数值表。
3. 战斗伤害、突破成功率、NPC AI 权重和宗门 AI 具体策略。
4. 复杂多人 PvP 仲裁。
5. 滑杆式连续追加投入。
6. 用普通事件绕过库存来源、资源预留、行动校验或后手封存规则。
7. 数据库 schema、网络协议和存档格式定稿。

## 10. 验收约束

1. 事件候选必须由稳定上下文、稳定排序或稳定随机种子生成，刷新 UI 不得改变候选。
2. 重大事件、正式交锋、突破挑战、不可逆选择和死亡风险不得被普通行动队列、自动兜底或低价值托管吞掉。
3. 事件选项生效时才消耗丹药、灵材、符箓和临时 boost，并必须可追溯到合法资产容器、宗门预留、事件锁定奖励包或其他合法来源。
4. 所有状态变化、库存变化、资源转移、宗门资源、NPC 奖励、后手开启和遗留设施处理必须通过结果包或权威结算接口落账。
5. 事件结果若施加伤势、药性、祝福、诅咒、封禁、标记或其他持续影响，应写入 `ongoing_state_delta`，并交由角色持续状态系统管理生命周期和属性修正导出。
6. 普通个人事件局部时停期间，其他玩家不得看到事件归因；外部 UI 只能显示中性的速度状态、公开结果或传闻。
7. C1 追赶只能补确定性内容，不得触发新的随机个人事件、普通机缘、普通战斗、软机会事件、普通心魔或普通资源反馈。
8. 宗门外个人洞府、普通藏宝和旧洞府线索作为无主遗留设施处理，不进入遗产分配、继承或宗门回收；真灵藏宝作为正式后手，由同一真灵跨世感应和开启。
9. 传闻文本只描述可见后果，不泄露 `hidden_truth_ref`、私人事件归因、隐秘局部时停来源、未公开突破选择、隐藏后手真实归属或 Debug 信息。
10. Debug 信息、精确候选权重、内部倍率和开发审计字段不得进入普通玩家 UI。
11. 闭关承诺不得吞掉心魔、资源耗尽、洞天异动、宗门突发、突破契机或其它应触发事件。
