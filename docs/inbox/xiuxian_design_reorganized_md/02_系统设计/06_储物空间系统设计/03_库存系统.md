# 储物空间系统设计｜库存系统

## 1. 当前定位

库存是非随身资产容器，不是行囊。

行囊绑定角色随身资产，随角色移动；库存绑定在设施、店铺、宗门、节点、洞府、藏宝点、真灵藏宝、市场、事件或其他非角色实例上。库存系统负责统一这些非随身资产的位置、权限、锁定、转移、审计和存档口径。

本页承接所有库存底层规则。商店买卖、宗门资源申请、个人洞府存取、藏宝封存、事件奖励领取和市场挂牌都应先落到库存系统的容器与资产流水，再由各自系统处理业务规则。

## 2. 与行囊的边界

| 概念 | 绑定点 | 是否随角色移动 | 主要用途 |
| --- | --- | --- | --- |
| 行囊 | 当前角色实例 | 是 | 随身物品、可调用道具、当前携带资产 |
| 库存 | 设施、组织、节点、市场、事件、洞府、藏宝或后手封存点 | 否 | 非随身储藏、交易库存、组织库存、节点储藏、事件锁定资产 |

旧文档中出现的“NPC 库存”应拆分处理：

1. N3 / N4 等重要 NPC 的随身或可调用资产，属于角色随身资产容器，不是本页定义的库存。
2. NPC 的洞府、库房、职务托管资产、市场挂牌或事件锁定资产，按对应库存类型处理。
3. N2 功能服务 NPC 通常只是服务入口，商店库存、宗门库存或节点库存不绑定在该 NPC 个人身上。

## 3. 资产容器模型

库存底层使用 `AssetContainer` 表达。

```yaml
AssetContainer:
  container_id: string
  container_type: carried_inventory | personal_storage | sect_storage | shop_stock | node_storage | market_listing | event_locked | treasure_cache | true_spirit_cache | trade_escrow | system_pool
  owner_type: character | true_spirit | sect | node | shop | market | event | system
  owner_ref: string
  bind_ref: string
  location_node_id: string | null
  item_instance_refs: list
  currency_balances: object
  access_policy: object
  visibility_policy: object
  reservation_refs: list
  audit_log_refs: list
  status: active | locked | hidden | contested | depleted | destroyed | archived
```

字段口径：

| 字段 | 含义 |
| --- | --- |
| `container_type` | 容器类型，决定是否随身、是否可交易、是否可反复存取 |
| `owner_type / owner_ref` | 资产法理或系统归属，不等于入口 NPC |
| `bind_ref` | 绑定设施、店铺、宗门部门、节点、事件、藏宝或后手记录 |
| `location_node_id` | 容器所在世界位置；纯系统池可为空 |
| `access_policy` | 查看、存入、取出、消耗、转移和审计权限 |
| `visibility_policy` | 普通 UI、传闻、宗门日志、隐藏世界日志和 Debug 的可见范围 |
| `reservation_refs` | 资源预留、交易锁定、事件锁定或后手封存引用 |
| `audit_log_refs` | 生成、存入、取出、消耗、出售、上交、封存、清点、回收和异常转移记录 |

## 4. 库存类型

| 库存类型 | `container_type` | 绑定点 | 主要规则 |
| --- | --- | --- | --- |
| 商店库存 | `shop_stock` | 店铺、摊位、坊市设施、宗门商店或市场服务容器 | 入口 NPC 只是服务入口；买卖规则见《商店与交易系统设计》 |
| 宗门库存 | `sect_storage` | 宗门库房、部门、设施或资源平台 | 资源申请、预留、审计与可见性见《宗门系统设计》 |
| 节点库存 | `node_storage` | 地图节点、建筑、资源点、秘境、仓库或事件节点 | 可由采集、宗门控制、事件、世界演化和清查改变 |
| 个人洞府库存 | `personal_storage` | 个人洞府设施 | 可反复存取；重大异常后的归属见《个人洞府库存、藏宝与后手系统设计》 |
| 藏宝库存 | `treasure_cache` | 藏宝点或特化洞府设施 | 设置时存入，正式取出一次性 |
| 真灵藏宝库存 | `true_spirit_cache` | 正式后手藏物点 | MVP 阶段主人可发现，不损坏、不移动，取出一次性 |
| 市场挂牌 | `market_listing` | 市场、寄售、订单或待成交容器 | 资产离开随身容器，成交或撤单必须写流水 |
| 事件锁定库存 | `event_locked` | 奖励、战利品、赌注、押运、任务或事件选择结果 | 未解锁前不能当作随身物品调用 |
| 交易暂存 | `trade_escrow` | 交易、赠予、寄售、多人交换或事件交换流程 | 双方确认或事件条件满足后结算，失败则回滚或释放 |

`system_pool` 只表达系统预算、生成池或未实例化资源，不是玩家可直接查看或调用的库存。资源槽、资源池、阶段预算和世界生成预算在转化为具体物品、灵石、奖励包或容器资产前，不应显示成可取库存。

## 5. 资产位置枚举

面向规则与 UI 的资产位置至少包括：

```yaml
AssetLocation:
  carried_by_character
  personal_cave_storage
  sect_storage
  shop_stock
  node_storage
  treasure_cache
  true_spirit_cache
  market_listing
  event_locked
  trade_escrow
```

说明：

1. `carried_by_character` 是随身位置，属于行囊或 NPC 随身资产，不是非随身库存。
2. `personal_cave_storage`、`treasure_cache`、`true_spirit_cache` 是个人储物空间的三种不同业务形态。
3. `shop_stock`、`sect_storage`、`node_storage` 都是机构或地点库存，不能写成入口 NPC 个人背包。
4. `market_listing` 与 `trade_escrow` 表示资产已被交易流程锁定，不应同时作为行囊物品调用。
5. `event_locked` 表示事件链尚未释放的资产，只有事件条件满足后才可转入行囊或其他库存。

## 6. 权限策略

库存权限至少要能表达：

```yaml
AccessPolicy:
  can_view: object
  can_deposit: object
  can_withdraw: object
  can_consume: object
  can_transfer: object
  require_same_location: bool
  require_identity_or_role: list
  require_contribution_or_reputation: object
  require_relationship_or_event_flag: object
  require_unlock_condition: object
  audit_level: none | personal | organization | public | hidden_world | debug
```

通用规则：

1. 查看权限不等于取出权限。
2. 存入权限不等于反复存取权限；藏宝和真灵藏宝只允许设置时存入。
3. 取出权限必须检查容器状态、角色位置、角色状态、物品状态、绑定状态、事件锁定、市场挂牌、资源预留和后手封存。
4. 宗门、商店和节点库存可按身份、职位、贡献、声望、关系、事件状态和可见性展示不同摘要。
5. 权限不足时，普通 UI 不应泄露调试级完整库存。

## 7. 流转请求

所有行囊与库存、库存与库存之间的资产移动，都使用资产转移请求表达。

```yaml
AssetTransferRequest:
  actor_ref: string
  source_container_ref: string
  target_container_ref: string
  asset_refs_or_query: object
  amount: number
  transfer_reason: string
  permission_context: object
  allow_partial: bool
```

流程：

```text
提交转移意图
→ 校验来源容器、目标容器、角色位置、权限、状态和物品限制
→ 校验预留、挂牌、事件锁定、绑定和后手封存
→ 执行扣减、增加、拆栈或实例迁移
→ 写资产流水和必要日志
→ 更新 UI 可见摘要、事件结果包和存档状态
```

失败规则：

1. 校验失败时，资产保持原位置。
2. 部分成功必须由 `allow_partial` 明确允许，并记录剩余失败原因。
3. 高价值物品、法宝、功法载体、突破资源、后手物、绑定物和独立实例物品的转移必须可复盘。
4. 程序层数量上限只作为性能、存档和异常防护，不表达为玩法层背包容量。

## 8. 可堆叠与实例追踪

可堆叠物品和独立实例物品必须分开处理，不做“半可堆叠”。

推荐堆叠键：

```yaml
StackKey:
  item_template_id: string
  tier: string
  quality: string
  key_state_tags: list
  condition_bucket: string | null
  recognition_state: string | null
  seal_state: string | null
  bind_state: string | null
  owner_restriction: string | null
  special_tags: list
```

进入堆叠键的标准：字段会影响战斗、突破、交易、后手、消耗、绑定、可见性或事件结果。仅作为风味来源、普通产地描述或无规则影响的历史，不应拆分堆叠。

以下资产默认应作为独立实例或保留独立流水：

1. 法宝、功法载体、命名宝物、宗门令牌、任务钥匙。
2. 正式后手物、真灵藏宝物、普通遗产核心物。
3. 高价值突破资源、唯一材料、绑定物、不可回收物。
4. 具有损伤、灵性、污染、封印、阵法、残余效果或识别状态的物品。

## 9. 预留、锁定与释放

预留和锁定用于避免同一资产被重复使用。

```yaml
ResourceReservation:
  reservation_id: string
  source_container_id: string
  reserved_asset_refs: list
  reserved_for_character_id: string | null
  reserved_for_system: string
  bound_request_id: string | null
  bound_command_id: string | null
  created_world_day: int
  created_world_hour: int
  expires_world_day: int | null
  expires_world_hour: int | null
  status: active | consumed | released | expired | failed
  log_refs: list
```

使用场景：

1. 宗门资源申请、突破支持、护法支持和设施时段。
2. 市场挂牌、玩家交易、NPC 交易和交易暂存。
3. 事件赌注、押运、任务奖励、战利品待分配和事件锁定奖励。
4. 藏宝设置、后手封存、遗产处理和洞府清点。
5. 商店出售物保留期、回收队列和不可回收资产特殊处理。

预留资源不可在其他行动中重复消耗。释放、过期、失败和消耗都必须写入资产流水。

## 10. 业务接口

### 10.1 商店与交易

商店库存使用 `shop_stock`，市场挂牌使用 `market_listing`，交易暂存使用 `trade_escrow`。宗门内商店、宗门外商店、玩家与非商店 NPC 交易、玩家之间交易的业务规则统一放在《商店与交易系统设计》中。

### 10.2 宗门资源申请

宗门库存使用 `sect_storage`。申请、审批、预留、消耗、释放、过期、审计、宗门页面可见性和多人间接竞争影响统一放在《宗门系统设计》中。

### 10.3 洞府、藏宝与后手

个人洞府库存、藏宝库存和真灵藏宝库存使用本页容器模型。洞府类型、宗门接管、自辟洞府遗留、藏宝一次性取出和 MVP 真灵藏宝边界统一放在《个人洞府库存、藏宝与后手系统设计》中。

### 10.4 节点资源与事件奖励

节点资源槽、资源池和世界预算不是库存。采集、加工、宗门行动、事件结算或世界演化把它们转化为 `node_storage`、`sect_storage`、`event_locked`、`shop_stock` 或行囊资产后，才进入库存流转。

## 11. 存档与回放

库存状态必须持久化，不得由 UI 临时推导。

存档至少需要保留：

1. `asset_containers`：所有活跃库存、随身资产容器、交易暂存和事件锁定容器。
2. `item_instances`：可堆叠物品栈和独立实例物品。
3. `reservation_records`：资源预留、市场挂牌、交易锁定和事件锁定。
4. `asset_transfer_logs`：生成、转移、出售、上交、消耗、封存、回收、清点和异常处理。
5. `contingency_records` 或等价后手记录：正式后手和真灵藏宝的状态引用。

回放不需要展示所有隐藏库存，但必须能在 Debug 或审计路径中解释资产为什么出现、移动、消耗、封存、损坏、失效或被回收。

## 12. 矛盾校验

已统一口径：

1. 掌柜、摊主、接引 NPC 和商店入口 NPC 不是商店库存绑定点。
2. 宗主、长老或管事不是宗门库存的个人持有人。
3. N2 功能服务 NPC 不应在交易或战斗开始时临时生成完整库存。
4. 资源槽、资源池和世界预算不是可取库存，必须先实例化或进入资产容器。
5. 正式后手在正式版可有暴露、损坏、争夺或污染原因链；MVP 阶段的真灵藏宝按主人可发现、不损坏、不移动处理。
6. 旧文档中的季度 / 回合保留期可作为宏观交易周期说明；底层时间字段应使用 `world_day / world_hour` 或等价世界日历字段记录创建与过期。
7. 市场挂牌、事件锁定、资源预留和后手封存中的资产不能同时作为行囊可调用物品。

## 13. 待决策项目

1. 各类库存的默认可见性模板和 UI 文案。
2. 商店出售物保留期是否固定为一个宏观交易周期，还是按店铺类型、物品类型或节点状态配置。
3. `trade_escrow` 是否进入 MVP，尤其是玩家之间直接交易是否开放。
4. 节点库存、洞府库存、藏宝库存和事件锁定库存的 Debug 查看层级。
5. 不可回收物、绑定物、任务物进入商店或交易暂存后的异常处理模板。
