## 1. 继承约束

### 1.1 事件系统边界

事件系统负责把玩家、NPC、宗门、节点和世界状态在特定上下文中转化为事件链、选择、判定和结果包。

既有 S10 已经确定：

```
事件触发
→ 进入事件链或专用事件链
→ 玩家选择 / 系统判定 / 子事件处理
→ 生成 EventOutcome
→ 交给 S1 统一回写角色、物品、节点、宗门、日志、传闻
```

因此，本页只定义事件的“玩法类型”和选择框架，不直接绕过结算总线。

### 1.2 与 S3 的关系

事件可以中断 S3 时间轴。

S3 提供：

- 当前季度、tick、行动格上下文。
- 角色位置、路线段、节点进入 / 离开 / 途经上下文。
- 当前持续行动状态。
- 剩余行动格。
- 托管状态。
- 行踪暴露与风险上下文。

事件返回：

- 是否继续原计划。
- 是否消耗剩余行动格。
- 是否强制中断本季度计划。
- 是否改变位置、状态、连续行动。
- 是否进入战斗、突破、死亡 / 转世等专用事件链。

### 1.3 与战斗 / 突破的关系

战斗和突破已经是较详细的专用事件链。

本页不重写它们，而是提供更上层的事件类型框架：

- 常规移动、节点、关系、资源、传闻事件优先使用“选择事件”。
- 战斗事件可以被选择事件触发，也可以作为专用“交锋事件”。
- 突破事件链内部可以嵌入选择事件、投入事件、外扰事件、特殊交锋事件和余波事件。
- 事件类型是玩法结构，不是触发来源分类。移动事件、节点事件、宗门事件、突破外扰都可以使用同一种玩法类型。

## 2. 核心判断

### 2.1 最核心的常规事件类型是选择事件

选择事件的本质是：

> 系统抛出一个问题，玩家用一个选项回答这个问题，系统根据回答生成后果。
> 

问题不是纯文本氛围，而是一次可结算的局面压力。

例如：

- 路上遇到山贼，问题是“你如何处理当前威胁？”
- 道侣索要珍贵法宝，问题是“你如何回应亲密关系中的资源请求？”
- 宝库需要真灵波动解锁，问题是“你如何满足或绕过进入条件？”
- 突破中出现外扰，问题是“你如何稳定突破局面？”

选择事件的价值不在于提供很多按钮，而在于让玩家以较低交互成本表达一次策略态度，并承担相应后果。

### 2.2 事件选项是“解题姿态”，不是同义选项集合

同一事件中，每个选项应代表不同解题姿态。

不推荐：

```
给 / 不给 / 犹豫一下 / 再问一句
```

推荐：

```
正面应对 / 出奇制胜 / 逃避推诿 / 解构问题 / 欺诈蒙骗
```

这五类不是玩家可见的固定按钮名，而是设计者组织选项时的内部维度。

### 2.3 每个维度最多提供一个选项

同一个维度不应同时出现多个选项。

原因：

1. 多个同维选项通常只是数值、文本或道德方向的细碎差异，选择体验不够有趣。
2. 事件选项太多会增加阅读成本，削弱文字策略游戏的节奏。
3. 同维多选会制造 UI 和配置复杂度，且收益有限。

因此，常规选择事件的主选项区合理选项数量是 1–3 个；在客观条件不足时，只有 1 个选项也是正常的。超过 3 个开放选项时，通过省略按钮进入溢出选项区。

## 3. 五类选择维度

### 3.1 正面应对

定义：

> 正面回答事件抛出的核心问题，并按照该问题在当前语境下的朴素规则处理。
> 

正面应对不是永远“接受要求”或“给予资源”，而是直面问题本身。

判断原则：

- 对合理请求，正面应对通常是满足、协助、如实说明能力不足。
- 对不合理侵犯，正面应对通常是拒绝、反击、保护自身权益。
- 对客观危险，正面应对通常是处理危险本体。
- 对无法处理的问题，正面应对可以是承受代价或明确失败。

示例：

```
狼要吃你：正面应对 = 反过来干掉狼，或硬抗求生。
道侣索要珍贵法宝：正面应对 = 有则给；没有则如实回答没有。
混混索要珍贵道具：正面应对 = 不给，而不是同时提供“给”和“不给”。
突破外扰来袭：正面应对 = 稳住突破并处理外扰。
```

设计规则：

- 一般事件应至少尝试生成正面应对选项。
- 如果正面应对需要道具、修为、关系或身份支持，而玩家不满足条件，则正面应对可以退化为“直面失败 / 如实回答 / 承受后果”。
- 正面应对承担“事件基本解法”的教学职责，是玩家理解事件问题的锚点。
- 当候选选项超过 3 个时，正面应对默认优先留在主选项区。

### 3.2 出奇制胜

定义：

> 使用超出事件默认预设的合法手段解决问题，并且确实解决了问题本体。
> 

出奇制胜的核心是“非常规但有效”。它不是骗过系统，也不是回避问题，而是使用特殊资源、技能、关系、地点、道具或信息，给出更高效或更高质量的解法。

示例：

```
任务 NPC 请求你亲自击败敌人：你给他一张高阶符箓，让他自己完成反杀。
山贼拦路：你亮出真实宗门长老令，使其主动退走。
妖兽袭扰药田：你用阵盘临时封锁入口，而不是直接战斗。
突破外扰：你提前布置的护法阵自动分担外部压力。
```

设计规则：

- 出奇制胜通常依赖稀缺客观条件，例如高阶符箓、特殊法宝、宗门权限、前世线索、隐藏身份、地点布置。
- 出奇制胜应获得较好收益或较低损耗，但需要消耗对应资源或暴露某些能力。
- 不是所有事件都必须有出奇制胜空间。
- 当候选选项超过 3 个时，出奇制胜优先进入溢出选项区。

### 3.3 逃避推诿

定义：

> 不直接解决问题本体，而是通过离开、拖延、绕行、转移责任、降低接触强度等方式避免承担主要风险。
> 

逃避推诿不是失败按钮。对低价值、高风险、非主线、非必要问题而言，它往往是最高效选项。

示例：

```
赶路途中遇到山贼：运转轻身功法逃遁。
陌生 NPC 请求高风险帮忙：婉拒并继续原计划。
节点危机尚未扩大：暂不上报，转交当地执事处理。
突破准备不足：放弃本次窗口，继续巩固。
```

设计规则：

- 逃避推诿通常降低即时风险，但可能损失奖励、声望、线索、关系或后续窗口。
- 逃避推诿不应被设计成永远正确。重要事件、强制危机或高因果事件可以让逃避带来长期后果。
- 对移动事件而言，逃避推诿是非常重要的低成本策略入口。

### 3.4 解构问题

定义：

> 改变问题成立的前提、身份关系、规则解释或目标定义，让原问题不再以原强度存在。
> 

解构问题不是“更聪明的正面应对”，也不是欺骗。它是对事件语境的重构。

示例：

```
你蒙面偷盗师尊藏宝库，师尊来势汹汹要打杀你。
你揭下面罩说：师尊，我是在和你闹着玩。
原问题从“高修为敌人来袭”降级为“师徒惩戒 / 关系清算”。
```

更多示例：

```
争夺资源点：你证明该资源点本来属于宗门共同辖区，而非私人争夺。
宝库门禁：你不破解门禁，而是证明自己有继承授权。
道侣索要法宝：你指出该法宝已被设为共同后手，问题从“给不给”变为“如何共同维护后手”。
宗门处罚：你把个人失误解释为节点规则缺陷，推动问题进入制度修订。
```

设计规则：

- 解构问题通常需要身份、关系、信息、证据、权限、前世记忆、规则理解等条件。
- 成功时常常改变事件类型或降低事件严重度，而不是直接给最高奖励。
- 失败时可能造成更高关系代价，因为玩家显得狡辩、越权或不敬。
- 当可用选项超过 3 个时，解构问题优先进入溢出选项区，而不是直接出现在主选项区。

### 3.5 欺诈蒙骗

定义：

> 没有真正解决问题本体，而是通过伪装、模拟、隐瞒、误导或伪造，让系统或对象误以为问题已经解决，从而获得解决问题的回报。
> 

欺诈蒙骗与出奇制胜的区别：

```
出奇制胜：用非常规方式真正解决问题。
欺诈蒙骗：没有解决问题，但获得了解决问题后的通行、收益或信任。
```

示例：

```
宝库需要提供真灵波动才能解锁。
你使用宝库主人前世的一件法宝模拟真灵波动，骗过宝库门禁。
宝库并未真正确认你是主人，但你获得了进入权限。
```

更多示例：

```
伪造宗门令牌通过关卡。
把低阶灵材包装成高阶灵材完成交易。
在突破资源审查中隐瞒资源污染。
对 NPC 假称已经完成任务，提前领取报酬。
```

设计规则：

- 欺诈蒙骗应能带来短期收益或低成本通行。
- 欺诈蒙骗必须有暴露风险、后续追责、因果负担、关系破裂或隐藏失败标签。
- 欺诈蒙骗的结果不应只在当场结算；它适合写入隐藏世界日志或后续事件钩子。
- 欺诈蒙骗不等于邪恶路线，它是修仙沙盒中高风险、高机巧的事件解法。
- UI 中应提示“可能留下后患 / 暴露风险”等方向性风险，但不显示具体隐藏标签、追查对象或后续触发条件。

## 4. 选择事件生成规则

### 4.1 标准结构

```
ChoiceEvent {
  event_id
  template_id
  problem_statement
  event_context
  candidate_option_dimensions
  visible_options
  primary_options
  overflow_options
  option_view_state             // primary / overflow
  selected_option
  checks
  outcome_package
  child_event_requests
  log_rules
}
```

事件模板先定义“这个问题是什么”，再定义五类维度中哪些可能存在。

### 4.2 候选选项生成

每个维度最多生成 1 个候选选项。

```
读取事件模板
→ 读取 EventContext
→ 逐个维度检查候选条件
→ 每个维度保留最匹配的 0–1 个选项
→ 得到候选选项池
```

候选条件可以包括：

- 修为阶段。
- 生机 / 元气 / 神念状态。
- 当前行动状态。
- 当前节点、路线、地点危险等级。
- 已学功法、术法、神通。
- 随身法宝、符箓、丹药、特殊物品。
- 宗门职位、权限、声望。
- NPC 关系、道侣、弟子、师承。
- 前世后手、真灵感应、轮回账本信息。
- 当前事件已揭示的信息。
- 世界日志隐藏标签。

### 4.3 可见选项数量

常规选择事件的主选项区显示 1–3 个选项。

当满足开放条件的候选选项超过 3 个时，不直接丢弃多余选项，而是使用“主选项区 + 省略按钮切换溢出选项”的结构。

推荐规则：

```
候选可见选项 = 0：改用检定事件 / 余波事件，或生成兜底正面应对。
候选可见选项 = 1：主选项区显示 1 个选项。
候选可见选项 = 2–3：主选项区全部显示。
候选可见选项 > 3：主选项区显示 3 个选项，并在第三个选项后显示“...”按钮。
点击“...”按钮后，切换到溢出选项区；此时“...”按钮变为“返回”按钮。
```

### 4.4 超过 3 个选项时的裁剪与溢出规则

已定规则：当超过 3 个选项都满足开放条件时，优先将“出奇制胜”和“解构问题”放入溢出选项区。

基础排序原则：

```
候选选项超过 3 个
→ 主选项区优先保留：正面应对 / 逃避推诿 / 欺诈蒙骗
→ 溢出选项区优先放入：出奇制胜 / 解构问题
→ 主选项区第 3 个选项后显示“...”按钮
→ 点击“...”按钮后切换到溢出选项区
→ 切换后“...”按钮变为“返回”按钮
→ 点击“返回”后回到主选项区
```

设计理由：

- 出奇制胜和解构问题的设计难度最高，也最依赖事件语境自圆其说。
- 将这两类选项藏深一点，可以提高玩家对其稀有性、条件性和文本解释难度的容忍度。
- 玩家仍然能访问这些选项，因此不是直接隐藏或没收解法。
- 主选项区仍保持 1–3 个低成本决策入口，避免普通事件阅读负担过高。

交互要求：

- 不使用“上一页 / 下一页”式翻页按钮。
- 不显示页码。
- 不把溢出选项表现为与主选项完全等价的第二页。
- “...”按钮语义是“还有更深一层的处理方式”，而不是“当前选项列表分页”。
- “返回”按钮只用于回到主选项区，不代表取消事件。
- 溢出选项区最多显示本事件中剩余的开放选项；MVP 中正常情况下最多 2 个。

实现要求：

- 候选选项池仍需完整生成，并记录主选项区 / 溢出选项区分配结果。
- 分配结果必须使用事件实例的稳定随机种子或稳定排序，避免玩家反复刷新改变入口分布。
- 调试模式可以显示候选池、分区原因、条件命中情况和选项排序依据。
- 教学事件、关键主线事件、突破关键节点可以通过模板配置强制某些维度留在主选项区，但不应成为常规默认。

### 4.5 不可用选项的显示原则

已定规则：常规事件默认隐藏不可用选项。

例外情况：

1. 教学事件：可以显示灰色不可用选项，帮助玩家理解“缺少什么”。
2. 突破准备面板：可以显示不可用准备方向，因为它服务于长期规划。
3. 关键节点事件：可以显示少量不可用高价值解法，作为未来目标提示。

常规事件中，不建议频繁显示灰色选项，否则玩家会把事件理解成“系统列出了我没资格玩的按钮”。

## 5. 选择事件结果规则

### 5.1 每个选项必须有后果方向

选项不是纯文字分支。每个选项至少影响以下一类内容：

- 角色状态。
- 物品或库存。
- 行动格或连续状态。
- 节点状态。
- 宗门关系或职位评价。
- NPC 关系。
- 战斗 / 突破 / 死亡 / 后手等子事件入口。
- 传闻与世界日志。
- 轮回账本或隐藏失败标签。

### 5.2 结果可分为三层

```
即时结果：当场获得、损失、进入子事件。
延迟结果：后续季度、节点、关系、传闻中触发。
隐藏结果：玩家暂时不可见，但进入世界日志或因果标签。
```

示例：

```
欺诈蒙骗通过宝库门禁：
即时结果 = 获得进入宝库权限。
延迟结果 = 门禁主人后续可能追查异常。
隐藏结果 = 写入“真灵波动伪造”世界日志标签。
```

### 5.3 失败也必须有方向

失败不能只输出“未成功”。

失败结果应尽量写成可解释标签：

- 资源不足。
- 判断失误。
- 修为压制。
- 关系不足。
- 伪装暴露。
- 护法不足。
- 地点不稳。
- 心境动摇。
- 行踪暴露。
- 前世后手失配。

这些标签可以进入事件日志、轮回账本、NPC 记忆、宗门评价或后续事件池。

## 6. 选择事件示例模板

### 6.1 路途山贼事件

问题：

```
你在赶路途中被山贼截住。对方要求你交出财物，否则动手。
```

候选维度：

| 维度 | 选项设计 | 条件 | 结果方向 |
| --- | --- | --- | --- |
| 正面应对 | 拒绝并正面击退 | 基础可用 | 可能进入战斗，胜利后获得安全通过或少量战利品 |
| 出奇制胜 | 使用宗门信物震慑 | 有真实宗门身份 / 信物 | 消耗或暴露身份，避免战斗 |
| 逃避推诿 | 运转轻身功法绕路逃遁 | 有轻身功法或移动优势 | 消耗元气 / 行动格，降低受伤风险，可能延误 |
| 解构问题 | 指出此地已归某宗门管辖，抢劫会招来追责 | 有节点控制权信息 / 宗门声望 | 降低冲突强度，可能转化为交涉 |
| 欺诈蒙骗 | 伪装成高阶修士吓退对方 | 有伪装手段 / 神念压迫 / 法宝特效 | 当场通过，后续可能暴露并生成传闻 |

### 6.2 道侣索要法宝事件

问题：

```
道侣向你索要一件珍贵法宝，希望借此处理自身瓶颈或危机。
```

候选维度：

| 维度 | 选项设计 | 条件 | 结果方向 |
| --- | --- | --- | --- |
| 正面应对 | 有则赠予；无则如实说明 | 基础可用 | 改变关系、库存、信任；无物时可能产生遗憾但不构成欺骗 |
| 出奇制胜 | 提供替代方案，例如共同炼制、借用宗门资源 | 有炼器 / 宗门权限 / 替代资源 | 保留原法宝，同时解决部分需求 |
| 逃避推诿 | 暂缓答复，承诺日后寻找 | 基础可用 | 延迟关系压力，可能积累不满 |
| 解构问题 | 说明该法宝已作为共同后手，问题改为共同维护 | 有后手记录 / 共同目标 | 需求转化为协作事件 |
| 欺诈蒙骗 | 交付仿品或隐瞒法宝真实状态 | 有仿制物 / 信息优势 | 短期维持关系，后续暴露风险高 |

### 6.3 真灵宝库门禁事件

问题：

```
宝库需要匹配真灵波动才能开启。
```

候选维度：

| 维度 | 选项设计 | 条件 | 结果方向 |
| --- | --- | --- | --- |
| 正面应对 | 提供自身真灵波动；不匹配则放弃 | 基础可用 | 成功开启或明确失败 |
| 出奇制胜 | 破解门禁阵纹 | 有阵法能力 / 时间 / 工具 | 真正绕过门禁，但消耗时间与资源 |
| 逃避推诿 | 标记位置，暂时离开 | 基础可用 | 保留线索，后续可再来 |
| 解构问题 | 证明自己拥有继承授权 | 有遗嘱、信物、宗门文书或前世记录 | 门禁逻辑从“身份匹配”改为“授权验证” |
| 欺诈蒙骗 | 用前世法宝模拟宝库主人真灵波动 | 有对应法宝或真灵残留 | 当场开启，写入隐藏追查风险 |

## 7. 其他玩法层面事件类型

以下类型不是按触发来源分类，而是按玩家在事件中的交互方式分类。

### 7.1 检定事件

定义：

> 系统根据上下文做一次判定，玩家没有有意义选择，结果直接生成。
> 

适用场景：

- 行踪是否暴露。
- 路途中是否发现线索。
- 节点灵气是否波动。
- 护法阵是否自动抵消外扰。
- 被动法宝是否受损。
- NPC 是否察觉欺诈痕迹。

设计价值：

- 处理不适合打断玩家的低交互事件。
- 让世界自然演化，不把所有变化都变成选择题。
- 降低事件系统的交互疲劳。

边界：

- 检定事件不应承担重大玩家路线决策。
- 高风险、高损失、高稀缺机会事件应尽量转化为选择事件、交锋事件或窗口事件。

MVP 建议：需要实现。

### 7.2 投入事件

定义：

> 玩家选择投入哪些资源、投入多少、是否消耗稀缺物，以换取风险降低、收益提高或事件推进。
> 

投入事件的核心不是选择态度，而是资源承诺。

适用场景：

- 突破前投入辅助资源。
- 修复法宝。
- 临时加固阵法。
- 救援 NPC。
- 消耗灵石加速建筑维护。
- 使用聚灵石强化修炼或节点设施。

示例结构：

```
不投入：保留资源，但风险不变。
标准投入：消耗常规资源，获得基础修正。
高额投入：消耗稀缺资源，获得更强修正或额外结果。
```

已定规则：

- 投入事件不应变成复杂数值滑杆。
- MVP 不允许滑杆式连续追加投入。
- MVP 只允许 0 / 标准 / 高额等离散档位。
- 每个投入档位必须显示明确方向性后果。

MVP 需要实现最小版。

### 7.3 交锋事件

定义：

> 双方或玩家与事件模板之间进行多格或多阶段对抗，玩家通过预判、克制、资源消耗和顺序安排影响结果。
> 

战斗 / 斗法事件链是交锋事件的专用版本。

突破特殊挑战也可以视为交锋事件：

```
突破模板生成挑战序列
→ 玩家填入应对指令
→ 按格结算稳定度、损耗、失败标签、奖励修正
```

适用场景：

- 战斗 / 斗法。
- 突破内景挑战。
- 阵法攻防。
- 神念对抗。
- 秘境机关破解。
- 宗门小规模冲突的个人介入。

设计价值：

- 提供比单选更强的策略感。
- 复用战斗系统的 5 格交锋结构。
- 适合高风险、高仪式感事件。

边界：

- 不应滥用于普通事件，否则交互成本过高。
- 一般移动、社交、低价值资源事件不需要交锋结构。

MVP 建议：战斗与突破已需要实现；其他交锋事件后置。

### 7.4 探索揭示事件

定义：

> 事件的主要收益是揭示信息、生成线索、开启隐藏层、发现新行动入口，而不是立即给资源或胜负。
> 

适用场景：

- 探索节点隐藏层。
- 发现前世后手线索。
- 听闻世界传闻。
- 调查资源异变。
- 秘境入口波动。
- 发现 NPC 真实目的。

设计价值：

- 支撑沙盒演化与长期目标感。
- 让探索、卜算、情报、宗门职位等非战斗路线有价值。
- 将一次事件转化为后续行动链。

常见结果：

- 解锁节点。
- 解锁特殊持续行动。
- 增加线索进度。
- 改变玩家可见传闻。
- 生成后续窗口事件。
- 提高某类选择事件中解构问题 / 出奇制胜选项的可用性。

MVP 建议：需要最小版，尤其用于移动线索、节点资源异变、前世后手入口。

### 7.5 窗口事件

定义：

> 某个机会或危机在有限时间内存在，玩家可以选择介入、忽略、延后、交给宗门或等待条件变化。
> 

适用场景：

- 秘境开启。
- 节点危机扩大前窗口。
- 宗门任务限期。
- 突破资源名额。
- 敌对宗门行动征兆。
- 市场或资源节点短期波动。

设计价值：

- 强化季度行动格压力。
- 让玩家面对“现在做还是之后做”的规划选择。
- 连接 S3 行动经济、宗门行动、世界刷新事件。

边界：

- 窗口事件不是单独文本事件，而是一种持续存在的事件状态。
- 进入窗口后的具体交互仍可使用选择事件、投入事件、交锋事件或检定事件。

MVP 最小范围已定：

- 秘境窗口。
- 节点危机。
- 突破资源 / 名额窗口。

其他世界事件先使用普通选择事件或检定事件表达。

### 7.6 余波事件

定义：

> 主要事件结果已经发生，玩家在后处理阶段选择如何收尾、补救、隐瞒、追责、救援或利用后果。
> 

适用场景：

- 战斗结束后的处置。
- 突破失败后的疗伤、保密、求援、转世前安排。
- 欺诈暴露后的危机公关。
- 宗门行动失败后的追责。
- 节点灾变后的救援或撤离。
- NPC 死亡后的遗产分配前后处理。

设计价值：

- 降低失败的无力感。
- 让玩家在损失发生后仍有策略空间。
- 为日志、传闻、关系、遗产、后手污染提供自然接口。

边界：

- 余波事件不应无成本逆转核心失败。
- 它只能改变失败后的损失分布、信息公开程度、关系后果和后续修复路径。

MVP 建议：突破失败、战斗失败、死亡 / 遗产分配相关需要最小版。

### 7.7 协同 / 仲裁事件

定义：

> 多个主体对同一事件拥有不同立场、权限或行动意图，需要通过规则决定谁的选择生效、如何合流或如何冲突。
> 

适用场景：

- 多名玩家影响同一宗门行动。
- 玩家与 NPC 共同护法。
- 宗门高层对节点危机作出决策。
- 多个宗门争夺同一资源窗口。
- 道侣、弟子、师尊等关系主体参与同一事件。

设计价值：

- 支撑 3 人共玩和宗门经营。
- 让世界不是只围绕单一玩家响应。
- 可以表达“全员锁定或超时后自动结算”的多人节奏。

边界：

- MVP 不应做复杂多人 PvP 仲裁。
- 第一版可只支持宗门行动中的建议 / 决策采纳，以及 NPC 护法 / 宗门支持的抽象修正。

MVP 建议：只做接口和少量宗门行动场景，复杂协同后置。

## 8. 推荐的事件类型优先级

### 8.1 MVP 必需

1. 选择事件：常规事件核心。
2. 检定事件：处理被动、低交互、世界演化判定。
3. 投入事件：连接物品、资源、突破、维护与救援。
4. 交锋事件：战斗与突破已依赖。
5. 探索揭示事件：支撑节点探索、前世线索、传闻。
6. 余波事件：支撑失败后处理，尤其突破、战斗、死亡。

### 8.2 MVP 简化实现

1. 窗口事件：先做为带期限的事件状态，具体交互复用其他类型。
2. 协同 / 仲裁事件：先做宗门行动与护法修正接口，不展开复杂多人冲突。

### 8.3 暂不建议独立成型

以下更适合作为选择事件或专用事件链的子结构，不建议在 MVP 中独立成事件类型：

- 纯对话事件：应归入选择事件或关系事件模板。
- 纯奖励事件：应归入检定结果或余波事件。
- 纯剧情事件：应归入选择事件、探索揭示事件或窗口事件。
- 纯商店事件：属于经济 / 交易界面，不应混入事件类型，除非出现特殊问题。

## 10. UI 与交互原则

### 10.1 事件卡片结构

常规选择事件建议展示：

```
事件标题
事件问题 / 局面描述
关键上下文标签
主选项 1
主选项 2
主选项 3
... 按钮（仅当存在溢出选项时显示）
可能后果方向提示
确认按钮
```

点击“...”后切换为：

```
事件标题
事件问题 / 局面描述
关键上下文标签
溢出选项 1
溢出选项 2
返回按钮
可能后果方向提示
确认按钮
```

这里不采用翻页按钮。溢出区不是“第二页等价选项”，而是更深一层、设计条件更强、解释成本更高的解法入口。

后果提示不需要显示精确数值，但应显示方向：

- 可能进入战斗。
- 消耗元气。
- 延误行程。
- 暴露身份。
- 提高关系。
- 写入传闻。
- 可能产生隐藏后患。

### 10.2 避免“读小说式事件”

事件文本可以有风味，但必须服务于选择。

不推荐：

```
长篇描述三屏文字，最后只有“继续”。
```

推荐：

```
短文本建立问题
→ 用选项表达解法
→ 结果文本解释后果
→ 写入日志 / 子事件
```

如果事件没有选择空间，应归入检定事件或余波事件，而不是伪装成选择事件。

### 10.3 只有 1 个选项时的处理

只有 1 个选项不等于设计失败。

合理场景：

- 玩家客观条件极差，只能承受后果。
- 玩家已经提前准备，唯一选项是执行预案。
- 事件是强制后果展示。
- 事件处于专用事件链中的过渡阶段。

但需要区分：

```
只有一个可执行策略：仍可作为选择事件。
只是展示结果：应改为检定事件或余波事件。
```

## 11. 与突破事件链的结合

突破事件链可以由多个玩法事件组合：

```
瓶颈提示：检定事件 / 信息事件
突破准备面板：投入事件 + 风险预览
突破行动确认：选择事件
开链校验：检定事件
外部干扰：选择事件 / 交锋事件
内景挑战：交锋事件
资源追加：投入事件
失败后处理：余波事件
结果传播：检定事件 / 传闻生成
```

这能保留 S4 的仪式感，同时避免把所有东西塞进一个巨大选择事件。

---

## 12. 与战斗事件链的结合

战斗通常不应作为普通选择事件内部的纯文本结果。

更合理结构：

```
选择事件：你如何处理威胁？
→ 选择正面应对
→ 触发战斗 / 斗法事件链
→ 战斗返回结果包
→ 父事件生成余波事件或直接回写
```

也可以出现：

```
选择事件：你如何处理威胁？
→ 选择逃避推诿
→ 触发移动 / 逃遁检定
→ 成功则继续 S3 原计划，失败则进入战斗
```

这样可以保持选择事件轻量，又能让战斗承担真正的对抗结算。

## 13. 实现建议

### 13.1 MVP 不需要脚本语言

MVP 可以使用：

```
模板 + 条件 + 结果包 + 子事件请求
```

暂不需要完整剧情脚本语言。

Godot 实现上可优先使用 Resource / JSON 配置：

- EventTemplate。
- EventOption。
- EventCondition。
- EventOutcomeRef。
- EventLogRule。

### 13.2 稳定随机与调试

所有事件实例必须有稳定随机种子。

用途：

- 选项分区。
- 检定结果。
- 候选事件抽取。
- 子事件变体。

同一个事件实例不能通过关闭重开、刷新 UI、重复读取来改变候选选项。

调试模式需要显示：

- 命中的事件模板。
- 候选选项池。
- 条件通过 / 失败原因。
- 主选项区 / 溢出选项区分配原因。
- 结果包内容。
- 日志与传闻写入。

### 13.3 事件结果统一回写

事件内部不直接改状态。

标准流程：

```
事件结算
→ 生成 EventOutcome
→ 交给 S1 / 结算总线
→ 回写角色、物品、节点、宗门、日志、传闻
```

这样可以避免战斗、突破、移动、宗门事件各自绕过账本。

## 14. 已收敛决策

### 14.1 不可用选项显示规则｜已定

常规事件默认隐藏不可用选项。

允许灰显的例外场景：

1. 教学事件：用于提示玩家缺少什么条件。
2. 突破准备面板：用于服务长期规划。
3. 关键节点事件：用于少量提示未来高价值解法。

设计理由：减少常规事件中的挫败感与 UI 噪音，避免玩家把事件理解成“系统列出一堆我不能玩的按钮”。

### 14.2 正面应对保留规则｜已定

一般事件应至少尝试生成正面应对选项。

当候选选项超过 3 个时，正面应对默认优先留在主选项区，不再与出奇制胜随机二选一。

教学事件、关键主线事件、突破关键节点可以通过模板配置强制正面应对留在主选项区。

设计理由：正面应对承担事件基本解法和问题理解锚点，不应在普通裁剪中被藏入溢出区。

### 14.3 多阶段选择事件的阶段数上限｜已定

常规选择事件最多 2 阶段。

重要事件最多 3 阶段。

超过 3 阶段后，应转为专用事件链，而不是继续膨胀为普通选择事件。

设计理由：避免普通事件膨胀成剧情脚本，保持事件系统的可配置性与可验证闭环。

### 14.4 欺诈蒙骗的后患提示｜已定

欺诈蒙骗选项在 UI 中应显示“可能留下后患 / 暴露风险”等方向性提示，但不显示具体隐藏标签、追查对象或后续触发条件。

设计理由：让玩家理解风险，不破坏欺诈路线的不确定性与后续追查空间。

### 14.5 出奇制胜与解构问题的溢出规则｜已定

当超过 3 个选项都满足开放条件时，优先将出奇制胜和解构问题放入溢出选项区。

裁剪不再等同于直接隐藏。主选项区第 3 个选项后显示“...”按钮，点击后切换到溢出选项区；此时“...”按钮变为“返回”按钮。

不使用翻页按钮，也不显示页码。

设计理由：出奇制胜和解构问题的设计难度、自圆其说难度和语境依赖度最高。把这两类选项藏深一点，可以提高玩家对其条件性、稀有性和解释成本的容忍度，同时保留玩家主动发现高级解法的体验。

### 14.6 投入事件投入方式｜已定

MVP 不允许滑杆式连续追加投入。

MVP 只允许离散档位，例如：

```
不投入
标准投入
高额投入
```

每个投入档位必须显示明确方向性后果。

设计理由：降低 UI 与数值复杂度，并避免玩家在事件中进入细碎资源调参。

### 14.7 窗口事件最小实现范围｜已定

MVP 只为以下内容实现窗口事件：

- 秘境窗口。
- 节点危机。
- 突破资源 / 名额窗口。

其他世界事件先使用普通选择事件或检定事件表达。

设计理由：窗口事件主要服务季度行动压力与关键机会管理，不应在 MVP 阶段泛化到所有世界波动。

---

## 15. 暂定结论

事件系统的核心不是“发生很多故事”，而是让玩家在世界压力下持续回答问题。

常规事件的主干应是选择事件：

```
系统抛出问题
→ 玩家先从 1–3 个主选项中选择，必要时通过“...”查看更深层的溢出选项
→ 事件生成可解释后果
→ 后果写入角色、节点、宗门、日志、传闻或专用事件链
```

五类选项维度暂定为：

```
正面应对
出奇制胜
逃避推诿
解构问题
欺诈蒙骗
```

它们是事件设计者的内部框架，不一定直接暴露给玩家。

除选择事件外，MVP 还需要最小支持：

```
检定事件
投入事件
交锋事件
探索揭示事件
窗口事件
余波事件
协同 / 仲裁事件接口
```

其中选择事件负责常规交互，检定事件负责低交互世界演化，投入事件连接经济和资源，交锋事件承载战斗与突破，探索揭示事件支撑沙盒信息层，窗口事件制造季度行动压力，余波事件降低失败无力感，协同 / 仲裁事件为宗门经营和 3 人共玩预留接口。
