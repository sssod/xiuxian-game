# 房间、季度推进与权威结算

## 0. 文档定位

本文整理房间运行、季度阶段机、玩家锁定 / 超时、权威服务器、插入事件链、结果回写、日志与存档交接规则。

开发实现时，S1 应作为全项目结算总线。任何玩法系统都不应绕过 S1 直接写最终状态。

## 1. MVP 目标

房间与结算系统必须支持：

1. 本地单人测试房间。
2. 私人服务器部署房间。
3. 至少 3 名玩家共玩。
4. 保存、暂停、恢复、续开。
5. 无人在线时世界不自动推进。
6. 全员锁定或超时后自动结算。
7. 结算过程可回放、可调试、可写入日志。

## 2. 房间状态

建议最小结构：

```
RoomState {
  room_id: String,
  world_seed: int,
  current_year: int,
  current_quarter: int,
  current_phase: String,
  player_slots: Array,
  active_players: Array,
  ai_controlled_factions: Array,
  world_state_version: int,
  pending_decisions: Dictionary,
  settlement_status: String,
  save_version: String
}
```

房间不是实时持续世界。季度推进只发生在明确的回合提交和服务器结算过程中。

## 3. 标准季度阶段机

```
加载 / 创建房间
→ 季度开始
→ 世界刷新
→ 宗门行动决策阶段
→ 宗门行动即时反馈
→ 角色行动决策阶段
→ 玩家锁定 / 超时等待
→ 服务器统一结算
→ 插入事件链处理
→ 结果回写与日志生成
→ 存档写入
→ 下一季度
```

### 3.1 世界刷新

刷新内容包括：

- 节点事件候选。
- 秘境窗口。
- 宗门动态。
- 资源波动。
- 传闻候选。
- 隐藏层可发现性变化。
- 市场或商店常规运营事件。

世界刷新只生成候选和状态变化，不直接替玩家做选择。

### 3.2 宗门行动决策阶段

玩家根据宗门身份、权限、职位、门内声望、贡献记录提交：

- 宗门建议。
- 宗门提议。
- 宗门决策意图。

服务器立即反馈采纳倾向、预计资源、人力、风险、路线和可能结果，但此时仍只是预估。

### 3.3 角色行动决策阶段

玩家规划本角色 6 个朔望行动格，包括：

- 当前节点操作。
- 移动方式。
- 目标节点。
- 停靠点。
- 持续行动。
- 宗门行动亲自介入。
- 休整 / 警戒 / 停留。

客户端预览不是最终结果，最终以服务器结算为准。

## 4. 权威服务器原则

规则：

1. 客户端只提交意图，不直接改写世界状态。
2. 服务端校验所有宗门行动、角色行动、资源消耗、位置、权限与事件触发。
3. 客户端显示的预估收益、预估消耗、预计结束位置都不是最终结果。
4. 本地单人测试也走同一套权威结算流程，只是服务端可以在本地进程中运行。
5. 服务端必须记录足够的输入、随机命名空间、校验结果和结果包，用于调试与回放。

## 5. 玩家锁定、超时与托管

### 5.1 结算触发方式

已定口径：

```
全员锁定
或
部分玩家超时后由托管生成行动
→ 自动进入服务器统一结算
```

房主手动确认可以作为后续房间设置预留，但不是 MVP 默认规则。

### 5.2 锁定

玩家锁定后：

- 不再修改本季度行动。
- 可以查看已锁定预案。
- 可以等待其他玩家。
- 若事件链在结算中要求响应，再进入对应事件响应界面。

### 5.3 超时

玩家超时后：

- S12 生成稳健托管计划。
- 托管计划必须走 S3 行动合法性校验。
- 托管不得主动执行重大不可逆选择。

### 5.4 托管优先级

```
保命 / 避险
> 不暴露核心后手
> 延续安全连续状态
> 巩固修炼或基础修炼
> 维持低风险宗门职责
> 休整 / 警戒 / 停留
```

## 6. 结算主循环

服务器结算采用固定顺序，避免跨系统互相抢改状态。

```
读取本季度锁定决策
→ 校验宗门行动意图
→ 校验角色行动计划
→ 生成 S3 tick 时间轴
→ 按 tick 推进行动、移动、持续行动与事件判定
→ 遇到插入事件链则暂停普通时间轴
→ 接收事件链结果包
→ 回写角色、宗门、节点、资源、日志
→ 处理季度结束状态
→ 写入存档
```

## 7. 插入事件链

插入事件链包括：

- 突破。
- 战斗 / 斗法。
- 死亡 / 转世。
- 前世后手回收。
- 秘境关键节点。
- 节点危机。
- 重大宗门事件。

S3 提供触发上下文：

```
TimelineInterruptContext {
  quarter: int,
  tick: int,
  character_id: String,
  node_id: String,
  route_segment_id: String,
  current_action_state: Dictionary,
  remaining_action_slots: int,
  autopilot_state: String,
  exposure_context: Dictionary
}
```

事件链返回：

```
ResultPackage {
  package_id: String,
  source_system: String,
  character_delta: Dictionary,
  inventory_delta: Dictionary,
  node_delta: Dictionary,
  sect_delta: Dictionary,
  route_delta: Dictionary,
  consumed_ticks: int,
  interrupt_s3_plan: bool,
  triggered_child_events: Array,
  ledger_entries: Array,
  visible_log_entries: Array,
  hidden_world_log_entries: Array
}
```

## 8. 结果回写规则

所有结果包交给 S1 统一回写。

禁止：

- 事件链直接修改角色最终状态。
- 战斗链直接修改节点控制权。
- 宗门行动直接绕过库存预留。
- 物品系统直接绕过日志和资产容器。
- 后手系统无日志改变封存资产状态。

推荐回写顺序：

1. 校验结果包合法性。
2. 合并同类 delta。
3. 检查资源预留、库存、资产容器。
4. 应用角色状态变化。
5. 应用库存和资产变化。
6. 应用节点、宗门、地图变化。
7. 应用账本、日志、传闻。
8. 写入世界状态版本。
9. 写入存档。

## 9. 随机与可回放

每个季度结算应使用可追踪随机命名空间。

建议：

```
RngContext {
  world_seed: int,
  quarter: int,
  namespace: String,  # movement_event / breakthrough / combat / sect_action 等
  actor_ref: String,
  sequence_index: int
}
```

Debug 模式至少能回放：

- 玩家提交意图。
- 托管生成原因。
- 服务器校验过程。
- RNG 输入和关键 roll。
- 事件触发上下文。
- 结果包。
- 最终状态差异。

## 10. 日志分类

### 10.1 玩家可见日志

- 角色日志。
- 宗门摘要。
- 传闻。
- 轮回账本。

### 10.2 世界日志

系统完整事件记录，默认玩家不可见。用于传闻生成、后手追踪、调试和世界状态解释。

### 10.3 Debug 日志

包括结算输入、校验、随机、结果包、错误、状态差异。

## 11. MVP 验收清单

- 可以创建本地单人房间。
- 可以创建 3 人房间。
- 玩家可进入宗门行动阶段和角色行动阶段。
- 玩家可锁定行动。
- 未锁定玩家超时后可托管。
- 全员锁定或超时后自动结算。
- 结算可触发至少一种移动事件和一种插入事件。
- 结果包通过 S1 回写。
- 结算后角色、位置、库存、节点、日志可保存。
- 退出后可恢复房间并继续下一季度。
