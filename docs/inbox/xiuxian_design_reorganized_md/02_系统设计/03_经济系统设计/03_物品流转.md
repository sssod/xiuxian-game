# 系统设计｜物品流转

## 1. 设计定位

物品流转负责回答资源、物品、灵石、情报、控制权和高价值资产在世界中如何从来源进入合法容器，并在转移、消耗、封存、回收、交易、上交或清点时保持可追踪、可审计和不重复结算。

经济系统的核心不是完整市场模拟，而是资源流转与资产可信系统。本文只维护经济视角下的资产位置、转移权限、预算不返还、堆叠 / 实例边界、价值口径和流水要求；不重定义库存底层、交易成交规则、灵石对象、宗门资源申请、个人洞府后手或完整数值公式。

灵石、低阶货币与聚灵石的定义、余额 / 物品边界、加工、消耗和价值口径统一见《灵石及聚灵石》（`../05_物品设计/05_灵石及聚灵石.md`）。本文只记录它们进入资产容器、转移请求、交易、上交、封存、消耗或回收时的流转约束。

## 2. 当前结论

1. 物品流转必须回答资产从哪里来、当前在哪里、为什么能被移动或处理，以及之后谁能看见、使用、追踪或审计。
2. 资产容器、库存类型、事件锁定、市场暂存、预留、锁定、释放和资产流水的底层规则，以《库存系统》（`../06_储物空间系统设计/03_库存系统.md`）为准。
3. 所有资产移动都应通过资产转移请求表达，并检查来源容器、目标容器、角色位置、权限、可见性、绑定、预留、事件锁定、市场挂牌和后手封存。
4. 物品只分为可堆叠物品或独立实例物品，不设计“半可堆叠”状态；影响战斗、突破、交易、后手或消耗结果的字段必须进入堆叠键或实例追踪。
5. 出售、拆解、销毁、上交、回收、消耗或封存不返还世界生成预算；正式后手只处理已封存进真灵藏宝的已有资产，不等于前世资产全量承接。

## 4. 核心循环或触发入口

经济系统的基础流转循环：

```text
行动 / 风险 / 权限 / 宗门持续行动
→ 获得资源、物品、灵石、情报或控制权
→ 投入修炼、突破、战斗、建设、探索、交易、后手
→ 提高个人与宗门资源获取效率
→ 接触更高阶资源窗口
→ 死亡、转世、遗产分配、无主遗留设施、后手与世界演化继续改变资源分布
```

单次资产流转的常规步骤：

```text
触发资产移动或处理
→ 生成 AssetTransferRequest
→ 校验来源、目标、权限、位置、锁定、绑定、可见性和处理规则
→ 转移、消耗、封存、回收或失败
→ 写入资产流水、库存日志和必要的业务结果
```

主要触发入口：

1. 地图采集、宗门常态产出、宗门持续行动、事件奖励、战利品、宝藏、秘境或 NPC 掉落形成资产。
2. 玩家存取、交易、出售、上交、拆解、修复、加工、销毁、封存、领取、分配或回收资产。
3. 宗门清点、遗产分配、职务资产回收、无主遗留设施开启、真灵藏宝开启或后手取出。
4. 市场挂牌、寄售、交易暂存、商店库存回收或玩家之间交易改变资产位置。

## 5. 规则与状态

### 5.1 资产容器归口

本页只保留经济系统视角的流转约束：

| 经济场景 | 容器归口 |
| --- | --- |
| 角色随身资产 | 行囊 / `carried_by_character` |
| 灵石余额与聚灵石物品 | `../05_物品设计/05_灵石及聚灵石.md` + `currency_balances` / `ItemStack` / `ItemInstance` |
| 商店买卖、出售物保留、商店回收 | `04_交易系统.md` + `shop_stock` |
| 市场挂牌、寄售、玩家交易暂存 | `04_交易系统.md` + `market_listing` / `trade_escrow` |
| 宗门资源申请、上交、预留、消耗 | `../17_宗门系统设计.md` + `sect_storage` |
| 洞府存取、藏宝、真灵藏宝 | `../18_个人洞府库存_藏宝与后手系统设计.md` |
| 节点采集、事件奖励、战利品待分配 | `node_storage` / `event_locked` |

错误口径：

```text
掌柜 = 商店库存持有人；
宗主 = 全宗库房持有人；
资源槽可被玩家直接取用，或可无限叠加任意设施；
将正式后手误解为“前世资产全量承接”。
```

正确口径：

```text
掌柜是 ShopStock 服务入口；
宗主是 SectStorage 权限影响者；
村长、管事或节点 NPC 是 NodeStorage / PopulationPool 的代表；
资源槽是节点上的广义资源承载位，只有经过采集、加工、宗门行动、事件结算或附属设施产出后，才转化为库存资产；
生产、修炼、加工、防护等设施是资源槽附属建设，同一资源槽只能建造一类设施，规模和等级可变且受规模上限约束；
正式后手只处理已封存进真灵藏宝的资产，且受数量和单个容量限制；
宗门外个人洞府和普通藏宝是无主遗留设施，不进入遗产分配、继承或回收，必须满足开启条件或破阵后才能取出。
```

### 5.2 遗产、无主遗留设施与后手

1. 遗产是仍有原持有人、需要分配、继承、清点或回收的资产；典型对象是 NPC 死亡后的随身物品、NPC 洞府库存、玩家角色转世前留在宗门管辖个人洞府中的普通库存，以及宗门托管 / 职务资产。
2. 玩家角色转世前留下的宗门个人洞府库存，按宗门相关遗产规则清点并回收宗门。
3. 宗门外个人洞府和普通藏宝是无主遗留设施，不进入遗产分配、继承或回收；它们可通过钥匙、功法、线索、位置、事件条件或强行破阵开启，因此可能被其他角色提前打开。
4. 真灵藏宝作为正式后手，由同一真灵跨世感应和开启，不等于前世资产全量承接。

### 5.3 可堆叠与实例物品

不设计“半可堆叠”物品。规则层明确为：

```text
可堆叠物品
或
独立实例物品
```

堆叠键、独立实例判断和高价值资产追踪，以《库存系统》（`../06_储物空间系统设计/03_库存系统.md`）为准。

经济系统补充要求：

1. 如果字段影响战斗、突破、交易、后手或消耗结果，则进入堆叠键。
2. 如果字段只是风味来源、普通产地描述或无规则影响的历史，不拆分堆叠。
3. 法宝、功法载体、宗门令牌、任务钥匙、正式后手物、命名宝物和高价值突破资源应保留独立流水。

### 5.4 流转请求

所有资产移动都应使用资产转移请求表达：

```yaml
AssetTransferRequest:
  actor_ref: string
  source_container_ref: string
  target_container_ref: string
  asset_refs_or_query: object
  amount: number
  transfer_reason: string
  permission_context: object
  allow_partial: bool
```

流转规则：

1. 资产转移前必须检查来源容器、目标容器、角色位置、权限、可见性、绑定、预留、事件锁定、市场挂牌和后手封存。
2. 生成、转移、消耗、出售、上交、拆解、修复、加工、销毁、封存、回收和清点都要写日志。
3. 出售、拆解、销毁、上交或回收不返还世界生成预算。
4. 失败时保持原资产位置；部分成功必须有明确配置和剩余失败原因。

### 5.5 价值口径

经济系统至少区分四类价值：

| 价值 | 用途 |
| --- | --- |
| `TradeValue` | 买卖、估价、商店价格、市场挂牌 |
| `BudgetValue` | 事件、秘境、掉落、宝藏等生成预算扣除 |
| `SalvageValue` | 拆解、修复折价、残片产出和商店回收 |
| `ContributionValue` | 上交宗门后的贡献、声望、职位评价或权限修正 |

规则：

1. `BudgetValue` 不必等于 `TradeValue`。
2. `SalvageValue` 通常低于交易价值，受物品状态、设施、角色技艺、污染和物品类型影响。
3. `ContributionValue` 可读取 `TradeValue` 并乘以宗门需求程度，但贡献不是货币。
4. 宗门实际发放资源仍必须检查 `sect_storage`，不能用贡献绕过库存。

## 7. 数据字段建议

| 字段 | 含义 |
| --- | --- |
| `asset_transfer_id` | 单次资产转移、消耗、封存、回收或清点请求身份 |
| `actor_ref` | 发起流转的角色、宗门、NPC、事件或系统服务 |
| `source_container_ref` | 来源容器，必须可追踪到合法库存或事件锁定资产 |
| `target_container_ref` | 目标容器；消耗、销毁或回收也应记录业务目标 |
| `asset_refs_or_query` | 资产引用或筛选条件，用于指定堆叠、实例或资源包 |
| `amount` | 转移数量；实例物品通常为 1 或实例列表 |
| `transfer_reason` | 流转原因，例如采集、领取、交易、上交、拆解、封存、遗产清点 |
| `permission_context` | 权限、位置、可见性、绑定、职务、开启条件和事件状态 |
| `allow_partial` | 是否允许部分成功；为 true 时必须记录剩余失败原因 |
| `stack_key` | 可堆叠物品的堆叠键，来源以库存系统和物品基准建模为准 |
| `item_instance_id` | 独立实例物品身份，用于法宝、功法载体、任务钥匙、后手物等 |
| `lock_state` | 市场挂牌、事件锁定、预留、封存、绑定或不可达状态 |
| `value_refs` | `TradeValue`、`BudgetValue`、`SalvageValue`、`ContributionValue` 的引用或快照 |
| `ledger_entry` | 本次流转对应资产流水、库存日志、预算扣除或审计记录 |
| `failure_reason` | 权限不足、位置不符、目标不可用、锁定、绑定、预算或部分成功失败原因 |

字段建议是实现提示，不等同于最终数据库或代码结构。

## 8. UI 展示边界

普通 UI 应展示：

1. 资产当前位于行囊、宗门库存、节点库存、事件锁定、市场挂牌、交易暂存、洞府、藏宝或其他合法容器。
2. 玩家可理解的不可转移、不可领取、不可交易、不可上交或不可封存原因。
3. 物品是可堆叠物品还是独立实例物品，以及影响使用、交易、突破、后手或任务提交的关键状态。
4. 买卖、拆解、上交或贡献折算时使用的可见价值摘要。
5. 真灵藏宝、普通藏宝、遗产、无主遗留设施和宗门回收之间的业务差异。

普通 UI 不展示：

1. 内部容器 ID、资产查询表达式、预算池 ID、随机种子和完整 Debug 审计链。
2. 未揭示藏宝、NPC 隐性资产、事件后续奖励、隐藏开启条件或未公开市场信息。
3. 原始价值公式、完整概率表、调参倍率和内部流水批次。

## 9. MVP 范围

MVP 应实现：

1. 资产转移请求作为统一入口，覆盖获得、转移、消耗、上交、出售、回收、封存和清点。
2. 来源容器、目标容器、权限、位置、锁定、绑定、事件锁定、市场挂牌和后手封存校验。
3. 可堆叠物品与独立实例物品二分，并对高价值资产保留独立流水。
4. 出售、拆解、销毁、上交、回收、消耗或封存不返还生成预算。
5. 遗产、普通藏宝、真灵藏宝和宗门外无主遗留设施按已有资产流转处理。
6. 流转成功、失败和部分成功都写入资产流水或库存日志。

MVP 不实现：

1. 完整市场撮合、寄售税费、跨区域物流和复杂价格波动。
2. 拆解、修复、加工、销毁、封存的完整配置表。
3. 高级 Debug 审计视图、预算回溯图谱和长期世界资产再平衡。
4. 全量遗产继承系统或前世资产自动承接。

## 10. 验收约束

1. 任何资产移动、消耗、封存、回收或清点都必须能追溯到来源容器、目标容器、发起者、原因和流水。
2. 资产流转失败时必须保持原资产位置；允许部分成功时必须记录剩余失败原因。
3. 预算扣除不得因为资产后续出售、拆解、损坏、销毁、上交、封存或回收而返还。
4. 宗门资源发放必须检查 `sect_storage`，不得用贡献、声望或职位直接凭空兑换库存不存在的资产。
5. 资源槽产出必须先经过采集、加工、宗门行动、事件结算或附属设施产出，才能转化为库存资产。
6. 真灵藏宝只承接已封存的已有资产，不得被实现为前世资产全量继承。
7. 普通 UI 不得暴露未揭示资产、隐藏宝藏、NPC 隐性库存或完整内部审计链。
