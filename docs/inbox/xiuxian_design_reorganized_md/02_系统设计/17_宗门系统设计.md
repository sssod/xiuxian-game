# 宗门系统设计

## 1. 当前定位

宗门是玩家长期成长的平台与沙盒世界演化主体，但不是玩家本体。玩家死亡或转世后，宗门仍由 AI 托管并继续演化。

宗门负责身份、职位、贡献、门内声望、资源申请、库存预留、常规运营指令、宗门持续行动、宗门日志、宗门 NPC 支持和宗门对节点与世界演化的影响。

当前核心口径：

1. 宗门仍是组织资源平台与世界演化实体，不是玩家本体，也不变成玩家直接排程的城市建设面板。
2. 每个宗门同一时间最多只有一个 active `SectContinuousActionState`，代表宗门当前需要组织取舍的重点持续行动。
3. 宗门常规运营指令重新作为玩家可参与的高层 / 职位玩法入口，用于调整日常运营策略、预算倾向、权限归属和常态资源使用边界。
4. 常规运营指令不占用个人行动队列，也不占用宗门唯一持续行动槽；需要玩家亲自到场执行的事务仍必须使用个人行动、事件选择或正式交锋。
5. 为避免即时切换权限、抢占库存、绕过 NPC 协作和多人冲突，常规运营指令的运营效果必须延迟生效。

宗门库存的底层容器规则见《06_储物空间系统设计/03_库存系统》。宗门内商店的买卖规则见《03_经济系统设计/04_交易系统》。本页负责宗门资源申请、预留、常规运营指令、支出、审计和权限。

组织形态边界：

1. 宗门与家族属于同级组织概念。家族不是宗门的下级组织，也不是宗门之后的备用归属。
2. 角色和 NPC 同时只能有一个明确所属组织；MVP 阶段该所属组织为宗门或空。
3. MVP 不开发家族、帮派、商会、王朝官署等非宗门组织。文档中保留的 `faction_ref`、`owner_faction_id`、`controlling_faction_ref` 等泛组织字段仅为未来扩展占位；MVP 运行规则不得据此生成第二所属组织或非宗门组织系统。

## 2. 身份与权限

MVP 身份序列：

```text
外门弟子 → 内门弟子 → 真传弟子 → 执事 → 长老
```

MVP 不开放宗主。M3 或第三大境界起点后进入长老序列或等价高层决策体验。

权限标签示例：

```text
request_resources
use_training_site
request_breakthrough_support
lead_task
access_inner_archive
manage_node_affairs
assign_guard_or_support
view_sect_inventory_summary
view_resource_reservations
submit_operation_suggestion
issue_operation_command
manage_operation_authority
view_operation_audit
```

贡献是历史凭证，不是货币。门内声望是宗门内部对可靠性、潜力与影响力的综合评价。资源申请可读取贡献与声望，但最终仍必须校验真实库存、权限、地点和宗门当前状态。

身份层级含义：

1. 外门弟子：入门身份，主要获得基础功法、基础任务、最低宗门保护和个人资源申请入口。
2. 内门弟子：稳定修行身份，解锁更好的修炼设施、任务层级和宗门关系入口。
3. 真传弟子：重点培养身份，可接触高价值资源、护法、突破名额、核心任务和部分建议权。
4. 执事：组织执行层，可管理局部资源、节点事务、任务分派或低到中级运营指令。
5. 长老：宗门高层，可管理更完整的库存、预留、培养方向、节点控制、护法支持和重大运营指令。

权限来源：

1. 宗门身份层级。
2. 具体职位。
3. 门内声望。
4. 贡献记录。
5. 关键 NPC 支持。
6. 特殊事件授权。
7. 高层权限委托或收回。

MVP 不开放玩家宗主职位。宗主、掌门、太上长老等多权限主体可作为 NPC 高层或后续阶段扩展职位存在；若未来玩家获得多权限高层身份，使用同一套权限委托规则。

权限委托规则：

1. 多权限主体可以将某一类运营权限设为由具体职位负责人自行决断，例如让执事堂负责人自行调整低阶任务派发，让药园执事自行调整药田维护优先级。
2. 权限委托的对象是职位或职责范围，不是玩家账号本身；同一规则可由玩家角色、NPC 或多人房中的其他玩家角色持有。
3. 设置、转移或收回权限即时生效：新的负责人立即获得提交或审批资格，被收回者立即失去提交新指令、审批新指令和查看超出权限细节的资格。
4. 权限变化不即时改写已经生效的运营结果；运营指令的实际更新仍按延迟生效规则进入下一次运营生效窗口。
5. 未到生效窗口的待生效运营指令必须在生效前重新校验权限。提交者或职位在生效前失去对应权限时，该指令转为 `rejected`、`expired` 或待新负责人复核。

## 3. 宗门资源与库存

宗门追踪五类抽象资源：

1. 灵石。
2. 修炼资源。
3. 材料 / 矿材。
4. 人力 / 弟子规模。
5. 声望 / 影响力。

宗门发放给玩家或 NPC 的资源必须来自真实库存。贡献、职位、声望、关系和身份只能影响权限、优先级和审批概率，不能绕过库存检查。

`SectInventory` 是宗门侧库存摘要，底层物品持久化仍由资产容器与物品系统承载。

```yaml
SectInventory:
  sect_id: string
  container_id: string
  spirit_stones: number
  cultivation_resources: number
  material_stock: number
  manpower: number
  sect_reputation: number
  material_items: list
  method_carriers: list
  pills: list
  talismans: list
  reserved_resources: list
  public_access_policy: object
  audit_log_refs: list
```

宗门库存可包含：

```text
灵石；
丹药；
灵材；
符箓；
法器；
完整功法载体；
残页 / 章节；
任务物；
节点产出资源；
宗门遗产清点接管物；
宗门个人洞府清点物；
突破支持资源；
设施时段与导师支持名额。
```

注意：

1. `sect_reputation` 是宗门整体资源口径，不等同于节点影响力。
2. `manpower` 是组织人力规模，不是可放入行囊的物品。
3. 抽象资源在需要成为具体道具、奖励、突破资源或后手封存物时，再由物品系统实例化。
4. 世界产出预算只提高宗门资源可得性，不自动批准玩家申请。
5. 高于当前预算境界的宗门资源默认不稳定生成，除非来自先锋泄漏、宗门重大事件、宗门自身专属资源池或已完成清点的合法遗产接管。遗产接管只适用于有原持有人且需要分配、继承、清点或回收的资产，例如 NPC 死亡后的随身物品、NPC 洞府库存、宗门管辖个人洞府库存、宗门托管 / 职务资产。

## 4. 宗门资源来源

MVP 来源：

1. 控制节点的基础产出。
2. 宗门持续行动结果。
3. 玩家上交资源。
4. 节点事件奖励。
5. 宗门声望带来的外部供给。
6. 特殊秘境、机会窗口或隐藏层。
7. 宗门个人洞府清点、NPC 死亡后的宗门相关遗产接管、宗门托管 / 职务资产回收。
8. 宗门商店、资源槽附属设施、部门或生产链产出。

所有来源都应进入 `sect_storage`、宗门库存摘要、审计日志或结果包，不应直接表现为玩家无来源获得物品。

宗门建设和生产必须读取地图资源槽。MVP 阶段同一资源槽只能建设一类设施；宗门可以升级设施规模、等级和维护状态，但不能在同一资源槽上叠加多类产出设施。设施规模上限由资源类型、资源品级、节点等级、地形、控制权和特殊事件决定。

宗门不能把宗门外个人洞府、普通藏宝或真灵藏宝直接写成宗门资源来源。宗门外个人洞府和普通藏宝是无主遗留设施，必须满足钥匙、功法、线索、位置、事件条件或破阵结果后才能进入 / 取出；真灵藏宝作为正式后手由同一真灵跨世感应和开启，受设置数量和单个容量限制，不进入遗产分配、继承或回收。

## 5. 宗门资源支出

MVP 支出：

1. 发放弟子培养资源。
2. 支持玩家或 NPC 突破。
3. 宗门持续行动消耗。
4. 节点建设与修复。
5. 驻守、远征、探索的人力占用。
6. 应对节点危机。
7. 维护宗门核心建筑、节点公共设施或资源槽附属设施。
8. 发放俸禄。
9. 宗门内商店、任务奖励和设施支持。

宗门俸禄口径：

```text
境界基数 + 职位绝对值
→ 宗门财政状态修正
→ 最终发放额
```

所有宗门采用同一套基础标准，宗门财政状态只作为发放修正。俸禄进入角色随身资产或合法个人容器时，必须写入资产流水。

## 6. 资源申请

资源申请可以作为 `Command.command_type=apply_resource`，也可以作为事件选项进入系统。

```yaml
SectResourceRequest:
  request_id: string
  character_id: string
  sect_id: string
  requested_resource_refs: list
  purpose_command_ref: string | null
  submitted_world_day: int
  submitted_world_hour: int
  status: pending | approved | rejected | partial | expired
  result_package_refs: list
```

申请流程：

```text
贡献 / 门内声望 / 身份 / 权限 / 请求用途
→ 是否允许申请
→ 检查宗门库存与既有预留
→ 检查宗门当前行动、节点压力、事件状态和 NPC 支持
→ 生成资源预留、部分批准、拒绝或过期
→ 写入宗门审计日志与结果包
```

审批依据：

1. 身份与职位。
2. 贡献。
3. 门内声望。
4. 库存与预留状态。
5. 宗门当前持续行动。
6. 关键 NPC 支持。
7. 节点压力。
8. 事件状态。
9. 请求用途。
10. 公开影响。
11. 宗门 AI 策略。

资源申请通过后：

1. 高价值资源应生成资源预留。
2. 丹药、灵材、符箓等在进入个人行动或事件选项时，必须作为行动资源输入消耗。
3. 设施时段、导师指点、护法支持进入行动、事件或突破模板修正，并记录来源。
4. 行动开始或事件选项生效前仍需执行前校验。
5. 消耗、释放、过期和拒绝都必须写入宗门审计日志与结果包。

## 7. 资源预留

资源预留用于避免宗门库存被多系统重复使用。

```yaml
SectResourceReservation:
  reservation_id: string
  sect_id: string
  source_container_id: string
  reserved_resource_refs: list
  reserved_for_character_id: string | null
  reserved_for_system: string
  bound_request_id: string | null
  bound_command_id: string | null
  created_world_day: int
  created_world_hour: int
  expires_world_day: int | null
  expires_world_hour: int | null
  status: active | consumed | released | expired | failed
  log_refs: list
```

示例：玩家申请突破支持后，宗门同意预留一批修炼资源。突破开始则消耗；事件取消则释放、过期或部分损耗。

预留规则：

1. 被预留资源不能被宗门持续行动、商店售卖、其他玩家申请或事件奖励重复消耗。
2. 预留可以绑定角色、命令、事件或系统用途。
3. 预留到期、行动失败、请求撤销、宗门状态变化或事件中断时，应释放、过期或失败。
4. 资源预留结果默认只对本人、相关宗门权限层和 Debug 可见。
5. 多人房中，宗门库存被申请会影响其他玩家机会，但不直接公开私人申请详情。

## 8. 宗门内商店与资源申请边界

宗门内商店和资源申请是两条路径。

| 路径 | 支付 / 判断 | 来源 | 结果 |
| --- | --- | --- | --- |
| 宗门内商店购买 | 灵石、价格、身份折扣、货架权限 | 宗门商店 `shop_stock` | 物品进入行囊或合法库存 |
| 宗门资源申请 | 身份、贡献、声望、用途、审批、真实库存 | 宗门库存 `sect_storage` | 预留、行动资源绑定、事件支持或拒绝 |
| 上交宗门 | 宗门需求程度、物品价值、事件状态 | 玩家行囊或合法来源库存 | 资产进入 `sect_storage`，角色获得贡献、声望或权限修正 |

宗门内商店的买卖、出售物保留和店铺库存规则见《03_经济系统设计/04_交易系统》。资源申请、预留、消耗和审计以本页为准。

## 9. 宗门持续行动

每个宗门同一时间最多拥有一个 active `SectContinuousActionState`。持续行动类型：

```text
开采 / 资源介入；
驻守 / 控制强化；
探索；
远征；
建设；
培养。
```

宗门持续行动可以改变宗门库存、节点资源、资源槽附属设施状态、节点公共设施状态、宗门影响力、控制权事件、玩家贡献与声望、秘境窗口、宗门遗产清点结果或宗门外洞府 / 普通藏宝等无主遗留设施的线索窗口。

宗门持续行动消耗必须来自宗门库存、资源预留、节点资源、抽象人力或事件明确提供的输入，不得绕过库存与预留。

常态运营不占用唯一持续行动槽：

```text
已控制矿场 / 药田的基础产出；
已建成基础设施的稳定效果；
已建立驻守状态的持续安全修正；
宗门俸禄或基础供给；
宗门库存维护；
已完成培养体系的基础弟子成长；
宗门商店基础补货倾向；
常规任务派发与低阶人力轮换。
```

这些内容仍按 `world_hour` 或宗门运营结算窗口常态结算，但不得被计为第二个 `SectContinuousActionState`。

## 10. 宗门常规运营指令

常规运营指令是职位权限对宗门日常运转参数的调整，不是宗门主行动输入，也不是个人行动队列。它允许玩家在安排自己角色的普通行动队列之外，参与宗门更细节的运营。

可覆盖的运营范围：

1. 资源预算倾向：培养、维护、驻守、商店、突破支持、任务奖励之间的低到中级预算比例。
2. 库存与预留政策：低阶资源保底线、高价值资源申请门槛、过期预留释放策略、商店补货优先级。
3. 节点与设施维护：已控制资源槽、公共设施、宗门核心建筑的维护优先级和风险阈值。
4. 人力与职务安排：驻守轮换、低阶任务分派、护法名额、导师时段、执事职责范围。
5. 培养与招收倾向：弟子培养方向、低阶功法开放范围、重点培养名额倾向。
6. 情报与档案访问：不同身份能看到的库存摘要、节点摘要、宗门日志和档案层级。
7. 常规危机响应：节点压力、库存短缺、外部威胁或设施损坏时的默认处理优先级。

不得通过常规运营指令直接完成的事项：

1. 发起第二个宗门持续行动。
2. 绕过宗门库存、预留、位置、权限、节点状态或事件状态校验。
3. 即时转移高价值资源给玩家、NPC 或私人容器。
4. 直接迫害同宗玩家、锁死其他玩家长期体验或泄露私人事件归因。
5. 替玩家角色移动、战斗、修炼、突破或处理需要亲自到场的事件。
6. 把未知事件选项、正式交锋轮内策略或突破挑战轮内选择预先写成自动脚本。

`SectOperationCommand` 最小结构：

```yaml
SectOperationCommand:
  operation_command_id: string
  sect_id: string
  operation_type: resource_policy | inventory_policy | node_maintenance_policy | manpower_assignment | training_policy | shop_policy | archive_policy | crisis_response_policy
  target_ref: string | null
  issuer_character_id: string
  submitted_by_player_id: string | null
  issuer_position_ref: string
  authority_scope: string
  authority_source_ref: string
  payload: object
  submitted_world_day: int
  submitted_world_hour: int
  earliest_effective_world_day: int
  earliest_effective_world_hour: int
  status: pending_effective | active | superseded | rejected | expired | revoked
  validation_refs: list
  supersedes_command_id: string | null
  log_refs: list
```

延迟生效规则：

1. 常规运营指令提交后先进入 `pending_effective`，只记录意图、权限来源、目标范围和预计影响。
2. 指令在下一个宗门运营生效窗口统一校验并生效。MVP 默认生效窗口为下一个宗门日结窗口；若需要更细粒度，可配置为固定 `sect_operation_command_delay_hours`，但不得同小时即时生效。
3. 生效前必须重新校验职位、权限、宗门库存、已有预留、节点状态、事件状态、其他待生效指令和宗门 AI 安全边界。
4. 校验失败时，指令不得部分偷跑；只能生成拒绝、过期、等待复核或被上级新指令覆盖的结果。
5. 高权限主体可以提交覆盖指令，但覆盖指令本身仍延迟生效。权限收回可以即时阻断资格，但不能即时制造一个新的运营结果。
6. 同一职责范围在同一生效窗口存在多条互斥指令时，按有效权限、职位负责人、上级覆盖、提交时间、门内声望、贡献记录和宗门 AI 安全边界裁定。
7. 指令生效后只改变后续常态运营参数，不回滚已经完成的库存消耗、事件结果或玩家个人行动结果。

`SectOperationAuthorityPolicy` 最小结构：

```yaml
SectOperationAuthorityPolicy:
  policy_id: string
  sect_id: string
  authority_scope: string
  owner_position_ref: string
  owner_character_id: string | null
  decision_mode: ai_default | owner_self_decide | upper_review_required
  granted_by_character_id: string | null
  granted_world_day: int
  granted_world_hour: int
  revoked_world_day: int | null
  revoked_world_hour: int | null
  status: active | revoked
  audit_log_refs: list
```

协作规则：

1. 玩家与 NPC 使用同一套职位、权限、待生效指令和审计日志。
2. NPC 负责人可以按宗门 AI 策略提交运营指令；玩家负责人可以提交显式指令；双方冲突时按权限委托、职位范围和宗门 AI 安全边界处理。
3. 多人房中，同宗玩家不走强制投票。玩家之间的运营协作通过职位负责人、上级覆盖、权限委托、资源申请、个人行动、事件结果和可见日志表达。
4. 同一职位若允许多名角色共同持有，必须有一个当前负责人或明确的复核规则；否则只能作为建议来源，不能自行决断运营指令。
5. 运营指令只公开到对应权限层。无权限成员可看到公开结果或传闻，但不能看到完整库存、私人申请、隐秘后手或其他玩家的私人归因。

## 11. 日志、可见性与宗门页面

宗门输出日志分层：

```text
本人可见；
宗门成员可见；
权限层可见；
公开传闻；
隐藏世界日志；
Debug 日志。
```

宗门页面稳定表达：

1. 宗门概览、常规运营指令、当前持续行动、库存权限和反馈。
2. 宗门库存首页显示五类抽象资源。
3. 详情区显示具体资产、资源申请、预留状态、过期时间、用途、是否已消耗、释放、失败或拒绝。
4. 不同身份、职位和权限看到不同摘要，不展示调试级完整库存。
5. 宗门库存变更、资源申请结果、功法载体发放、NPC 支持、交易、护法、导师指点和设施支持来源都应可回放。
6. 常规运营指令应显示待生效、已生效、被覆盖、被拒绝、过期和撤销状态，并显示生效窗口、提交者职位、权限来源、影响范围和权限层可见的校验摘要。
7. 权限委托与收回应在权限页即时反馈；对应运营指令仍显示其自身的待生效或失效结果。

## 12. MVP 不做

1. 宗门内部派系 / 山头变量。
2. 玩家直接夺宗主位。
3. 复杂同宗议会。
4. 通过宗门持续行动直接迫害同宗玩家长期体验。
5. 贡献作为可自由消费货币。
6. 资源申请绕过真实库存。
7. 宗门库存直接挂在宗主、长老或管事个人身上。
8. 玩家直接排多个宗门持续行动。
9. 常规运营指令即时生效。
10. 用常规运营指令替代个人行动、事件选择、正式交锋或突破挑战。

## 13. 待决策项目

1. 宗门资源申请的数值阈值、贡献消耗或声望影响公式。
2. 资源申请是否允许同一玩家多项并行，以及并行上限。
3. 预留过期时间是按世界日历、宏观周期还是事件阶段配置。
4. 宗门库存首页五类抽象资源与具体资产列表的 UI 层级。
5. 宗门内商店是否共享宗门库存短缺惩罚，还是拥有独立货架缓冲。
6. 常规运营指令是否保留“下一个宗门日结窗口”作为统一默认延迟，还是按固定 24 小时或指令类型分别配置。
7. 同一职位是否允许多名玩家 / NPC 共同持有；如允许，负责人、复核人和覆盖规则是否需要进一步细分。
8. 宗主或等价多权限玩家是否进入 MVP；当前文档仍按 MVP 不开放玩家宗主处理。
9. 运营权限的最小 UI 粒度：按大类显示，还是展开到每个节点、设施、商店、培养名额和资源类型。
