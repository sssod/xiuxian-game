# 系统设计｜库存系统

## 1. 设计定位

库存系统负责统一非随身资产容器的底层规则，回答“资产存放在哪里、谁能看见、谁能取用、何时锁定、如何转移、如何审计和如何存档”的问题。

行囊绑定当前角色随身资产，随角色移动；库存绑定设施、店铺、宗门、节点、洞府、藏宝点、真灵藏宝、市场、事件或交易暂存容器，不随角色自然移动。本文维护库存容器、资产位置、权限、锁定、预留、流转、堆叠、实例追踪和回放审计的通用口径。

本文不负责商店价格、宗门审批、洞府开启、藏宝感应、事件奖励生成或页面布局细节。这些业务规则由对应系统文档承接，本文只提供它们必须复用的资产容器和流水边界。

## 2. 当前结论

1. 库存是非随身资产容器，不等同行囊；重要 NPC 的随身可调用资产也不应误写成本文定义的库存。
2. 商店库存、宗门库存、节点库存、个人洞府库存、藏宝库存、真灵藏宝库存、市场挂牌、事件锁定库存和交易暂存都应复用 `AssetContainer` 口径。
3. 所有行囊与库存、库存与库存之间的资产移动，都应通过 `AssetTransferRequest` 校验权限、位置、状态、预留、挂牌、事件锁定、绑定和后手封存。
4. 可堆叠资产与独立实例资产必须分开处理；高价值、绑定、任务、后手、遗产待分配和状态复杂资产必须保留可复盘流水。
5. 查看权限不等于取出权限，普通 UI 不应泄露隐藏库存、完整权限策略、Debug 字段或玩家尚未知晓的资产。
6. `system_pool` 只表达预算、生成池或未实例化资源，不是玩家可直接查看、取出或调用的库存。

## 4. 核心循环或触发入口

库存系统没有单一玩家循环，而是被资产生成、转移、锁定、释放、业务结算和存档回放共同触发。

常见触发入口：

1. 系统把资源、奖励、战利品、交易物或藏宝内容实例化为资产，并写入目标容器。
2. 玩家、NPC、事件或系统提交资产转移意图。
3. 宗门申请、突破支持、交易、事件赌注、市场挂牌、后手封存或藏宝设置创建预留和锁定。
4. 业务系统查询容器摘要、可见资产、可取资产或失败原因。
5. 存档、回放、Debug 或审计路径解释资产来源、移动、消耗、封存、损坏、失效或回收。

通用流转步骤：

```text
提交资产意图
→ 定位来源容器与目标容器
→ 校验角色位置、身份、权限、可见性、容器状态和物品状态
→ 校验预留、挂牌、事件锁定、绑定保护、后手封存和藏宝 / 洞府开启条件
→ 执行扣减、增加、拆栈、合栈或实例迁移
→ 写资产流水、审计日志、事件结果包和存档状态
→ 向业务系统与 UI 返回可见摘要或失败原因
```

## 5. 规则与状态

### 5.1 行囊与库存边界

| 概念 | 绑定点 | 是否随角色移动 | 主要用途 |
| --- | --- | --- | --- |
| 行囊 | 当前角色实例 | 是 | 随身物品、可调用道具、当前携带资产 |
| 库存 | 设施、组织、节点、市场、事件、洞府、藏宝或后手封存点 | 否 | 非随身储藏、交易库存、组织库存、节点储藏、事件锁定资产 |

旧文档中出现的“NPC 库存”应拆分处理：

1. N3 / N4 等重要 NPC 的随身或可调用资产，属于角色随身资产容器，不是本文定义的库存。
2. NPC 的洞府、库房、职务托管资产、市场挂牌或事件锁定资产，按对应库存类型处理。
3. N2 功能服务 NPC 通常只是服务入口，商店库存、宗门库存或节点库存不绑定在该 NPC 个人身上。

### 5.2 资产容器模型

库存底层使用 `AssetContainer` 表达。

```yaml
AssetContainer:
  container_id: string
  container_type: carried_inventory | personal_storage | sect_storage | shop_stock | node_storage | market_listing | event_locked | treasure_cache | true_spirit_cache | trade_escrow | system_pool
  owner_type: character | true_spirit | sect | node | shop | market | event | system
  owner_ref: string
  bind_ref: string
  location_node_id: string | null
  item_instance_refs: list
  currency_balances: object
  access_policy: object
  visibility_policy: object
  reservation_refs: list
  audit_log_refs: list
  status: active | locked | hidden | contested | depleted | destroyed | archived
```

字段口径：

| 字段 | 含义 |
| --- | --- |
| `container_type` | 容器类型，决定是否随身、是否可交易、是否可反复存取 |
| `owner_type / owner_ref` | 资产法理或系统归属，不等于入口 NPC |
| `bind_ref` | 绑定设施、店铺、宗门部门、节点、事件、藏宝或后手记录 |
| `location_node_id` | 容器所在世界位置；纯系统池可为空 |
| `access_policy` | 查看、存入、取出、消耗、转移和审计权限 |
| `visibility_policy` | 普通 UI、传闻、宗门日志、隐藏世界日志和 Debug 的可见范围 |
| `reservation_refs` | 资源预留、交易锁定、事件锁定或后手封存引用 |
| `audit_log_refs` | 生成、存入、取出、消耗、出售、上交、封存、清点、回收和异常转移记录 |

### 5.3 库存类型

| 库存类型 | `container_type` | 绑定点 | 主要规则 |
| --- | --- | --- | --- |
| 商店库存 | `shop_stock` | 店铺、摊位、坊市设施、宗门商店或市场服务容器 | 入口 NPC 只是服务入口；买卖规则见《交易系统》（`../03_经济系统设计/04_交易系统.md`） |
| 宗门库存 | `sect_storage` | 宗门库房、部门、设施或资源平台 | 资源申请、预留、审计与可见性见《宗门系统设计》（`../17_宗门系统设计.md`） |
| 节点库存 | `node_storage` | 地图节点、资源槽附属设施、资源点、秘境、仓库或事件节点 | 可由采集、宗门控制、事件、世界演化和清查改变 |
| 个人洞府库存 | `personal_storage` | 个人洞府设施 | 可反复存取；宗门管辖内洞府可按遗产清点回收宗门，宗门外洞府作为无主遗留设施处理 |
| 藏宝库存 | `treasure_cache` | 藏宝点或特化洞府设施 | 设置时存入，正式取出一次性；作为无主遗留设施按开启条件或破阵结果取出 |
| 真灵藏宝库存 | `true_spirit_cache` | 正式后手藏物点 | 同一真灵可跨世感应和开启；MVP 阶段不损坏、不移动，取出一次性，受数量和单个容量限制 |
| 市场挂牌 | `market_listing` | 市场、寄售、订单或待成交容器 | 资产离开随身容器，成交或撤单必须写流水 |
| 事件锁定库存 | `event_locked` | 奖励、战利品、赌注、押运、任务或事件选择结果 | 未解锁前不能当作随身物品调用 |
| 交易暂存 | `trade_escrow` | 交易、赠予、寄售、多人交换或事件交换流程 | 双方确认或事件条件满足后结算，失败则回滚或释放 |

`system_pool` 只表达系统预算、生成池或未实例化资源，不是玩家可直接查看或调用的库存。资源槽、资源池、阶段预算和世界生成预算在转化为具体物品、灵石、奖励包或容器资产前，不应显示成可取库存。

### 5.4 资产位置枚举

面向规则与 UI 的资产位置至少包括：

```yaml
AssetLocation:
  carried_by_character
  personal_cave_storage
  sect_storage
  shop_stock
  node_storage
  treasure_cache
  true_spirit_cache
  market_listing
  event_locked
  trade_escrow
```

说明：

1. `carried_by_character` 是随身位置，属于行囊或 NPC 随身资产，不是非随身库存。
2. `personal_cave_storage`、`treasure_cache`、`true_spirit_cache` 是个人储物空间的三种不同业务形态。
3. `shop_stock`、`sect_storage`、`node_storage` 都是机构或地点库存，不能写成入口 NPC 个人背包。
4. `market_listing` 与 `trade_escrow` 表示资产已被交易流程锁定，不应同时作为行囊物品调用。
5. `event_locked` 表示事件链尚未释放的资产，只有事件条件满足后才可转入行囊或其他库存。

### 5.5 权限策略

库存权限至少要能表达：

```yaml
AccessPolicy:
  can_view: object
  can_deposit: object
  can_withdraw: object
  can_consume: object
  can_transfer: object
  require_same_location: bool
  require_identity_or_role: list
  require_contribution_or_reputation: object
  require_relationship_or_event_flag: object
  require_unlock_condition: object
  audit_level: none | personal | organization | public | hidden_world | debug
```

通用规则：

1. 查看权限不等于取出权限。
2. 存入权限不等于反复存取权限；藏宝和真灵藏宝只允许设置时存入。
3. 取出权限必须检查容器状态、角色位置、角色状态、物品状态、绑定状态、事件锁定、市场挂牌、资源预留、后手封存和藏宝 / 洞府开启条件。
4. 宗门、商店和节点库存可按身份、职位、贡献、声望、关系、事件状态和可见性展示不同摘要。
5. 权限不足时，普通 UI 不应泄露调试级完整库存。
6. 宗门外个人洞府和普通藏宝允许通过钥匙、功法、线索、位置、事件条件或强行破阵获得取出权限，因此可能被其他角色提前打开。
7. 真灵藏宝的取出权限以同一真灵为核心，但仍必须检查设置数量、单个容量、封存状态和一次性取出状态。

### 5.6 流转请求

所有行囊与库存、库存与库存之间的资产移动，都使用资产转移请求表达。

```yaml
AssetTransferRequest:
  actor_ref: string
  source_container_ref: string
  target_container_ref: string
  asset_refs_or_query: object
  amount: number
  transfer_reason: string
  permission_context: object
  allow_partial: bool
```

失败规则：

1. 校验失败时，资产保持原位置。
2. 部分成功必须由 `allow_partial` 明确允许，并记录剩余失败原因。
3. 高价值物品、法宝、功法载体、突破资源、后手物、绑定物和独立实例物品的转移必须可复盘。
4. 程序层数量上限只作为性能、存档和异常防护，不表达为玩法层背包容量。

### 5.7 可堆叠与实例追踪

可堆叠物品和独立实例物品必须分开处理，不做“半可堆叠”。

推荐堆叠键：

```yaml
StackKey:
  item_template_id: string
  tier: string
  quality: string
  key_state_tags: list
  condition_bucket: string | null
  recognition_state: string | null
  seal_state: string | null
  bind_state: string | null
  owner_restriction: string | null
  special_tags: list
```

进入堆叠键的标准：字段会影响战斗、突破、交易、后手、消耗、绑定、可见性或事件结果。仅作为风味来源、普通产地描述或无规则影响的历史，不应拆分堆叠。

以下资产默认应作为独立实例或保留独立流水：

1. 法宝、功法载体、命名宝物、宗门令牌、任务钥匙。
2. 正式后手物、真灵藏宝物、遗产待分配核心物。
3. 高价值突破资源、唯一材料、绑定物、不可回收物。
4. 具有损伤、灵性、污染、封印、阵法、残余效果或识别状态的物品。

### 5.8 预留、锁定与释放

预留和锁定用于避免同一资产被重复使用。

```yaml
ResourceReservation:
  reservation_id: string
  source_container_id: string
  reserved_asset_refs: list
  reserved_for_character_id: string | null
  reserved_for_system: string
  bound_request_id: string | null
  bound_command_id: string | null
  created_world_day: int
  created_world_hour: int
  expires_world_day: int | null
  expires_world_hour: int | null
  status: active | consumed | released | expired | failed
  log_refs: list
```

使用场景：

1. 宗门资源申请、突破支持、护法支持和设施时段。
2. 市场挂牌、玩家交易、NPC 交易和交易暂存。
3. 事件赌注、押运、任务奖励、战利品待分配和事件锁定奖励。
4. 藏宝设置、后手封存、遗产处理、无主遗留设施开启和洞府清点。
5. 商店出售物保留期、回收队列和不可回收资产特殊处理。

遗产处理只适用于仍有原持有人并明确进入分配、继承、清点或回收流程的资产，典型对象是 NPC 死亡后的随身物品、NPC 洞府库存、玩家角色转世前留在宗门管辖个人洞府中的普通库存，以及宗门托管 / 职务资产。宗门外个人洞府、普通藏宝和真灵藏宝不进入遗产分配、继承或回收；宗门外个人洞府和普通藏宝属于无主遗留设施，只通过开启条件、破阵或争夺处理，真灵藏宝按同一真灵感应处理。

预留资源不可在其他行动中重复消耗。释放、过期、失败和消耗都必须写入资产流水。

### 5.9 存档与回放

库存状态必须持久化，不得由 UI 临时推导。

存档至少需要保留：

1. `asset_containers`：所有活跃库存、随身资产容器、交易暂存和事件锁定容器。
2. `item_instances`：可堆叠物品栈和独立实例物品。
3. `reservation_records`：资源预留、市场挂牌、交易锁定和事件锁定。
4. `asset_transfer_logs`：生成、转移、出售、上交、消耗、封存、回收、清点和异常处理。
5. `contingency_records` 或等价后手记录：正式后手、真灵藏宝、开启条件、数量容量限制和一次性取出状态引用。

回放不需要展示所有隐藏库存，但必须能在 Debug 或审计路径中解释资产为什么出现、移动、消耗、封存、损坏、失效或被回收。

## 6. 资源、角色、地图、事件或 NPC 接口

| 接口对象 | 本文读取 | 本文写入或要求 |
| --- | --- | --- |
| 角色与行囊 | 当前角色、随身资产、位置、状态、绑定关系和可调用上下文 | 不把随身资产误归为非随身库存；行囊与库存转移必须走 `AssetTransferRequest` |
| 商店与交易 | 店铺、摊位、市场、寄售、订单、交易双方和成交条件 | 使用 `shop_stock`、`market_listing`、`trade_escrow` 和资产流水；入口 NPC 不是库存绑定点 |
| 宗门系统 | 宗门库房、部门、设施、职位、贡献、审批和审计上下文 | 使用 `sect_storage`、权限策略、资源预留和消耗 / 释放日志 |
| 洞府、藏宝与后手 | 个人洞府、普通藏宝、真灵藏宝、开启条件、后手记录和遗产处理口径 | 使用 `personal_storage`、`treasure_cache`、`true_spirit_cache`；区分遗产、无主遗留设施和真灵藏宝 |
| 地图节点与资源 | 节点、资源槽、附属设施、资源点、秘境、世界预算和采集结果 | 未实例化资源不是库存；实例化后写入 `node_storage`、`sect_storage`、`event_locked`、`shop_stock` 或行囊 |
| 事件与战斗 | 奖励、战利品、赌注、押运、任务、事件条件和战斗结算 | 使用 `event_locked`、预留和转移流水；未释放资产不能作为随身物品调用 |
| NPC 与服务入口 | NPC 身份、服务关系、职务托管资产和随身资产 | N2 功能 NPC 通常只提供服务入口；重要 NPC 随身资产按角色随身容器处理 |

## 7. 数据字段建议

| 字段 | 含义 |
| --- | --- |
| `container_id` | 资产容器唯一标识 |
| `container_type` | 容器类型，决定库存业务形态、随身性、可交易性和可反复存取性 |
| `owner_type / owner_ref` | 资产法理或系统归属；不得用入口 NPC 替代真实归属 |
| `bind_ref` | 容器绑定的设施、店铺、宗门部门、节点、事件、藏宝或后手记录 |
| `location_node_id` | 容器所在世界节点；纯系统池或未实例化池可为空 |
| `item_instance_refs` | 容器内物品实例或物品栈引用 |
| `currency_balances` | 容器内灵石、低阶货币或其他货币余额 |
| `access_policy` | 查看、存入、取出、消耗、转移和审计权限 |
| `visibility_policy` | 普通 UI、传闻、日志、隐藏世界信息和 Debug 的可见范围 |
| `reservation_refs` | 资源预留、交易锁定、事件锁定、后手封存或其他锁定引用 |
| `audit_log_refs` | 资产生成、移动、消耗、出售、上交、封存、回收、清点和异常处理记录 |
| `AssetTransferRequest.actor_ref` | 提交资产转移意图的角色、NPC、事件或系统引用 |
| `AssetTransferRequest.permission_context` | 校验位置、身份、角色状态、事件条件、绑定保护和业务权限所需上下文 |
| `ResourceReservation.status` | 预留状态：`active`、`consumed`、`released`、`expired` 或 `failed` |
| `StackKey` | 可堆叠物品的规则有效差异键；影响战斗、突破、交易、后手、消耗、绑定、可见性或事件结果的字段必须进入键 |

字段建议是实现提示，不等同于最终数据库或代码结构。若未来实现采用不同表名，也必须保留本文定义的资产位置、权限、锁定和流水语义。

## 8. UI 展示边界

普通 UI 应展示：

1. 玩家当前有权限查看的容器摘要、资产列表、可执行操作和不可用原因。
2. 市场挂牌、交易暂存、事件锁定、资源预留、藏宝封存、真灵藏宝一次性取出等会影响玩家决策的状态。
3. 与当前操作直接相关的权限不足、位置不符、容器锁定、物品绑定、事件未释放、后手封存或藏宝未开启提示。

普通 UI 不展示：

1. 完整内部 ID、隐藏容器、Debug 库存、完整权限策略、隐藏世界日志和未暴露的资产来源。
2. 玩家尚未获知的藏宝内容、真灵藏宝位置、事件奖励池、宗门隐藏库存或 NPC 私密资产。
3. `system_pool`、世界预算、未实例化资源槽产能或阶段预算。
4. 程序层数量上限、性能保护字段或存档防护字段的玩法化表达。

## 9. MVP 范围

MVP 应实现：

1. 行囊与库存的概念分离，以及非随身资产容器的统一 `AssetContainer` 口径。
2. 商店库存、宗门库存、节点库存、个人洞府库存、藏宝库存、真灵藏宝库存、市场挂牌和事件锁定库存的基础位置与权限语义。
3. 行囊与库存之间、库存与库存之间的资产转移请求、失败原因、资产流水和必要审计日志。
4. 可堆叠资产与独立实例资产的区分，高价值、绑定、任务、后手和状态复杂资产的实例追踪。
5. 预留、锁定、释放、过期和消耗的基础状态，避免同一资产被重复使用。
6. 存档与回放所需的容器、物品实例、预留记录、转移日志和后手记录引用。

MVP 不实现：

1. 玩法层通用容量、重量、体积、格子、负重或背包扩容玩法。
2. 所有库存类型的完整高级 UI、完整 Debug 管理界面或隐藏资产浏览器。
3. 未经交易系统裁决的玩家之间直接交易全流程。
4. 宗门外洞府、普通藏宝和真灵藏宝的完整破阵、争夺、提前打开和扩展容量规则。
5. 储物空间法宝内部资产容器的独立玩法。

## 10. 验收约束

1. 掌柜、摊主、接引 NPC 和商店入口 NPC 不能作为商店库存绑定点。
2. 宗主、长老或管事不能作为宗门库存的个人持有人。
3. N2 功能服务 NPC 不应在交易或战斗开始时临时生成完整库存。
4. 资源槽、资源池和世界预算不是可取库存，必须先实例化或进入资产容器。
5. 市场挂牌、事件锁定、资源预留和后手封存中的资产不能同时作为行囊可调用物品。
6. 正式后手在 MVP 阶段按真灵藏宝处理：同一真灵可跨世感应和开启，不进入遗产分配、继承或回收，不损坏、不移动，并受设置数量和单个容量限制。
7. 宗门外个人洞府和普通藏宝是无主遗留设施，不进入遗产分配、继承或回收；它们可以因开启条件满足、线索泄露、阵法被解除或防御被攻破而被其他角色提前打开。
8. 旧文档中的固定保留期可作为宏观交易周期说明；底层时间字段应使用 `world_day / world_hour` 或等价世界日历字段记录创建与过期。
9. 任何资产生成、转移、出售、上交、消耗、封存、清点、回收和异常处理都必须能通过日志或回放路径解释。
