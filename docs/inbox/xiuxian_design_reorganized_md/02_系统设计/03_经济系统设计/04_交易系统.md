# 系统设计｜交易系统

## 1. 设计定位

交易系统负责把灵石、物品、市场供给、NPC 互动、玩家交换和组织资源出口接入统一资产流转。它回答“谁能以什么条件把什么资产转给谁、价格如何校验、资产当前在哪里、失败后如何回滚、结果如何追踪”。

本文只维护买卖、出售、寄售、市场挂牌、玩家与 NPC 交易、玩家之间交易、商店库存和交易暂存的系统层规则。灵石、低阶货币与聚灵石的对象定义、币制边界、加工和资源输入接口统一见《灵石及聚灵石》（`../05_物品设计/05_灵石及聚灵石.md`）。库存、资产位置、预留、锁定和交易暂存底层规则见《库存系统》（`../06_储物空间系统设计/03_库存系统.md`）。

交易不是凭空改数值。每次买入、卖出、上交、领取、赠予、交换、寄售、撤单、回收或抢劫结算，都必须能追踪来源容器、目标容器、价格、权限、原因和日志。

## 2. 当前结论

1. 交易统一表现为资产容器之间的转移，必须校验价格、权限、位置、可见性、绑定、预留、锁定和事件条件。
2. 灵石是主交易通货；低阶货币只在受限场景兑换或折算；聚灵石按高密度灵气物品处理，不写入货币余额。
3. 商店是库存容器和交易服务，不是入口 NPC 的个人背包；掌柜、摊主、接引 NPC、宗门管事和店铺入口 NPC 只是服务入口。
4. 宗门内商店依赖真实宗门供给、身份权限和宗门状态；宗门资源申请、上交和审批属于宗门系统，不按普通商店买卖处理。
5. 玩家与非商店 NPC 交易必须使用持久化资产、事件锁定资产或有预算来源的轻量交易包，不能在交易开始时临时生成完整个人库存。
6. 玩家之间直接交易不作为 MVP 核心闭环；若开放，必须双确认、资产锁定、服务端复验和双方资产流水。

## 4. 核心循环或触发入口

交易系统的通用流程：

```text
行囊 / 随身资产 / 库存 / 市场挂牌 / 交易暂存
→ 校验价格、权限、位置、可见性、绑定、预留、锁定和事件条件
→ 转移物品、灵石或货币余额
→ 写资产流水、交易日志和必要的可见日志
```

主要触发入口：

1. 宗门外商店交易：城镇店铺、坊市摊位、游商、非宗门据点商店和事件商店。
2. 宗门内商店交易：宗门商店、部门供给、权限货架和门内折扣。
3. 玩家与非商店 NPC 交易：买卖、赠予、交换、赔偿、赎买、情报交换或事件交易。
4. 玩家之间交易：双方行囊、合法库存或 `trade_escrow` 之间的可追踪交换。
5. 市场挂牌与寄售：资产进入 `market_listing`，等待成交、撤单、过期或事件处理。
6. 抢劫、查抄与洗劫：不属于交易，只保留对正式事件链和资产转移的边界接口。

## 5. 规则与状态

### 5.1 通用交易约束

| 约束 | 当前口径 |
| --- | --- |
| 主通货 | 灵石是主交易通货 |
| 低阶货币 | 只在受限场景兑换或折算，不能成为修行资源主入口 |
| 聚灵石 | 作为高密度灵气物品交易，不写入货币余额 |
| 库存归属 | `shop_stock`、`market_listing`、`trade_escrow`、行囊、宗门库存等容器必须真实存在 |
| 服务入口 | 掌柜、摊主、接引 NPC、宗门管事和店铺入口 NPC 只是服务入口，不绑定商店库存 |
| 贡献 | 贡献不是货币，只影响权限、价格修正、申请资格或可见范围 |
| 禁止转移 | 绑定、事件锁定、资源预留、市场挂牌、后手封存和不可交易标签阻止普通交易转移 |

### 5.2 交易类型

| 类型 | 来源容器 | 目标容器 | 当前口径 |
| --- | --- | --- | --- |
| 一口价购买 | `shop_stock` / `market_listing` | 行囊或合法目标库存 | MVP 可支持 |
| 一口价出售 | 行囊或合法来源容器 | `shop_stock` / 商店回收容器 | MVP 可支持 |
| 宗门内商店购买 | 宗门商店 `shop_stock` | 行囊或合法目标库存 | 受身份、权限、贡献、宗门库存和供给状态影响 |
| 玩家与非商店 NPC 交易 | 双方随身资产或合法库存 | 双方随身资产或合法库存 | 需要持久化 NPC 资产、关系或事件许可 |
| 玩家之间交易 | 双方行囊 / 合法库存 / `trade_escrow` | 双方行囊 / 合法库存 | 不作为 MVP 核心闭环；若开放，必须双确认和可追溯 |
| 市场挂牌 / 寄售 | 行囊或合法来源容器 | `market_listing` | 规则保留，价格、税费、撤单和成交机制待定 |
| 上交宗门 | 行囊或合法来源容器 | `sect_storage` | 属于宗门资源与贡献规则，不按普通商店买卖处理 |
| 宗门资源申请 | `sect_storage` | 行囊、行动资源绑定或事件结果 | 归《宗门系统设计》（`../17_宗门系统设计.md`），不归商店交易规则 |
| 事件交换 | 事件锁定容器或参与方容器 | 事件锁定容器或参与方容器 | 由事件链决定，仍写资产流水 |

### 5.3 商店库存模型

商店是库存容器，不是 NPC 背包。

```yaml
ShopStock:
  shop_id: string
  shop_type: external_shop | sect_internal_shop | market_stall | event_shop
  node_id: string
  owner_faction_ref: string | null
  facility_ref: string | null
  entrance_actor_refs: list
  stock_container_id: string
  source_container_refs: list
  restock_rule: object
  price_rule: object
  visibility_rules: object
  transaction_log_refs: list
  status: open | restricted | out_of_stock | disrupted | closed | destroyed
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `shop_type` | 区分宗门外商店、宗门内商店、摊位和事件商店 |
| `entrance_actor_refs` | 可打开交易界面的 NPC 或交互点；死亡、替换或离开不自动搬空库存 |
| `stock_container_id` | 实际库存容器 |
| `source_container_refs` | 宗门库存、节点库存、市场挂牌、生产设施或运营事件来源 |
| `restock_rule` | 补货周期、来源、事件压力和世界预算接口 |
| `price_rule` | 基准价、折扣、身份修正、节点修正和供给修正 |
| `visibility_rules` | 哪些角色能看到哪些货架、限制、缺货和传闻 |

### 5.4 宗门外商店

宗门外商店包括城镇店铺、坊市摊位、游商、非宗门据点商店和事件商店。

规则：

1. 不要求维护完整上游生产链。
2. 库存由商店常规运营事件、节点繁荣度、商路状态、世界生成预算、传闻、事件压力和刷新规则共同决定。
3. 可被断供、灾害、战争、封锁、抢劫、节点控制变化和市场事件影响。
4. 价格可以先采用基准价加节点、供给、声望、关系、风险和事件修正。
5. 商店库存变化必须写日志，不应表现为无来源 UI 数值跳变。
6. 宗门外商店主要承担世界交易入口和物品投放功能，不应在 MVP 阶段扩展成完整社会经济模拟。

### 5.5 宗门内商店

宗门内商店是宗门资源平台的一部分，但不等同于宗门资源申请。

宗门内商店供应依赖：

1. 宗门建筑、设施和部门产出。
2. 宗门控制节点、资源点、药田、矿脉、炼丹房、炼器房、符箓部门等供给状态。
3. 宗门库存、宗门任务产出、采购渠道和宗门 AI 行动结果。
4. 宗门当前危机、建设重点、培养方向和突破支持压力。

规则：

1. 宗门商店库存不足时，应反映宗门生产、库存、供应链或权限压力。
2. 宗门内商店可根据身份、职位、贡献、门内声望、关系和事件状态展示不同货架。
3. 购买仍按商店交易处理，消耗玩家灵石或等价支付。
4. 资源申请是另一条路径：从 `sect_storage` 生成申请、审批、预留、消耗或拒绝，规则归《宗门系统设计》（`../17_宗门系统设计.md`）。
5. 上交宗门不是普通出售给商店；上交进入 `sect_storage`，换取贡献、声望、职位评价或权限修正。

### 5.6 买入、出售与回收

买入流程：

```text
打开商店入口
→ 读取可见 ShopStock / MarketListing
→ 选择物品和数量
→ 校验价格、库存、购买权限、当前位置、角色状态和目标容器
→ 支付灵石或交易对价
→ 物品转入行囊或合法目标库存
→ 写资产流水和交易日志
```

出售流程：

```text
选择来源容器中的可出售物品
→ 校验绑定、锁定、预留、后手封存、任务限制和不可交易标签
→ 按商店回收价支付灵石
→ 物品进入 ShopStock、商店交易缓存或回收队列
→ 写资产流水和交易日志
```

出售规则：

1. 出售属于即时交易，不应占用长期行动执行时间；新手阶段“准备干粮”可用即时交易承载教学。
2. 出售给商店的物品真实进入 `ShopStock` 或商店回收容器。
3. 出售不支持原价回购；玩家若再次购买，按商店售价规则购买。
4. 出售、拆解、销毁、上交或回收不返还世界生成预算。
5. MVP 不做操控市场和倒卖赚差价玩法。

玩家出售给商店的物品默认进入保留期：

1. 默认可按一个宏观交易周期配置，具体长度由店铺类型、节点状态、物品类型或服务器配置决定。
2. 底层记录应使用 `created_world_day / created_world_hour` 与过期字段，避免只绑定早期宏观规划字段。
3. 保留期内，物品仍可出现在货架、交易缓存或可见回购列表中，但回购价格按商店售价规则计算。
4. 保留期结束后，可堆叠物品通常按回收价折算为灵石进入商店库存或系统回收，不可堆叠物品继续保留在 `ShopStock`。
5. 商店可设置库存上限和警戒缓冲区；进入警戒区后，不可堆叠物品按回收价从低到高进入回收系统。
6. 被回收物品从 `ShopStock` 移除，并向商店库存返还等价回收价灵石或等价经营状态。
7. 带 `non_recyclable` 或不可回收标签的物品不进入自动回收队列，应由事件、任务、权限或特殊库存规则处理。

### 5.7 玩家与非商店 NPC 交易

非商店 NPC 交易指玩家与不代表商店库存的 NPC 进行买卖、赠予、交换、赔偿、赎买、情报交换或事件交易。

规则：

1. 只有持久化资产的 NPC、事件明确锁定资产的 NPC、或具备轻量交易包的事件 NPC 可以交易。
2. 交易资产必须来自 NPC 已持久化的随身 / 可调用资产、合法个人库存、事件锁定奖励包或有预算来源的交易包。
3. 不能在交易开始时为 NPC 临时生成完整个人库存。
4. N2 功能服务 NPC 若代表店铺、宗门、节点或市场，则走对应商店 / 机构库存，不走个人 NPC 交易。
5. 关系、恩怨、身份、宗门立场、声望、事件状态和可见性可影响交易是否出现、价格、可交易清单和风险。
6. 赠予、贿赂、交换、借用和赎买都必须写资产流水；高价值资产还应进入 NPC 关系、事件或日志。
7. 死亡、失败或战斗后可获得资产，不等于交易。战利品和遗产按事件链、战斗、死亡和库存规则处理。

宗门个人洞府库存可按有主遗产清点回收；宗门外个人洞府和普通藏宝是无主遗留设施，不能通过普通交易直接转移其中资产。

### 5.8 玩家之间交易

玩家之间直接交易不作为 MVP 核心验证项。若作为低成本附加能力开放，必须遵守以下流程：

```text
发起交易
→ 双方选择物品、灵石或可交易资产
→ 进入 trade_escrow 或双向锁定
→ 双方确认
→ 服务端再次校验位置、权限、资产状态、锁定状态和可见性
→ 同步结算
→ 写双方资产流水、交易日志和必要可见日志
```

约束：

1. 必须双方确认；不确认、不在线或托管状态下，不能自动成立普通交易。
2. 普通交易不能转移绑定物、事件锁定物、资源预留物、后手封存物、市场挂牌物、不可交易任务物或真灵藏宝物。
3. 交易失败时，锁定资产应回到原容器或保持原位置。
4. 离线袭击、强抢、欺诈、偷窃和洗劫不属于交易，应进入事件、战斗、抢劫或正式交锋规则。
5. 多人交易的可见性应默认只对交易双方、相关事件、隐藏世界日志和 Debug 可见；公开传闻需由事件结果生成。
6. 税费、手续费、同宗限制、跨节点交易距离、托管代收、拍卖和寄售不在 MVP 核心内。
7. 洞府钥匙、藏宝线索或开启条件相关物可以按自身物品规则交易，但交易它们不等于转移洞府或藏宝中的资产；后续仍需满足开启、破阵和取出规则。

### 5.9 市场挂牌与寄售

市场挂牌是资产进入 `market_listing`，等待成交、撤单、过期或事件处理。

当前保留规则：

1. 挂牌资产必须从行囊或合法来源库存转出，并写入来源日志。
2. 挂牌期间不能同时作为行囊物品、突破资源、后手封存物或事件消耗物调用。
3. 成交时从 `market_listing` 转入买方容器，灵石或对价转入卖方容器。
4. 撤单、过期、冻结、查封或事件干预必须释放或转移资产，并写日志。
5. 市场挂牌规则、税费、成交匹配、拍卖、匿名性、跨区域市场和玩家寄售优先级仍待决策。

### 5.10 抢劫、查抄与洗劫边界

MVP 可保留店铺、仓库、车队、节点库房作为正式版抢劫、查抄或洗劫对象的规则接口，但不实现完整抢劫玩法。

边界：

1. 抢劫目标是 `shop_stock`、`node_storage`、`event_locked`、押运容器或仓库容器，不是掌柜个人背包。
2. 击败、死亡、失踪或替换入口 NPC，不应自动搬空商店库存。
3. 抢劫必须进入节点事件链、守卫反应、风险、名声、通缉、宗门关系、市场秩序和资产转移。
4. 抢劫不是交易，不走买卖价格规则。
5. 如果抢劫造成商店缺货、关闭、断供或传闻，应更新商店状态和世界日志。
6. 宗门外个人洞府和普通藏宝的强行开启或破阵不属于交易，也不属于遗产分配、继承或回收；它应进入藏宝 / 洞府开启、争夺、破阵或正式交锋事件链。
7. 真灵藏宝作为正式后手，不作为抢劫、查抄或洗劫目标；MVP 阶段由同一真灵跨世感应和开启，并受设置数量与单个容量限制。

### 5.11 价格与价值口径

交易系统至少区分四类价值：

| 价值 | 用途 |
| --- | --- |
| `TradeValue` | 买卖、估价、商店价格、市场挂牌 |
| `BudgetValue` | 事件、秘境、掉落、宝藏等生成预算扣除 |
| `SalvageValue` | 拆解、修复折价、残片产出和商店回收 |
| `ContributionValue` | 上交宗门后的贡献、声望、职位评价或权限修正 |

规则：

1. `BudgetValue` 不必等于 `TradeValue`。
2. 出售、拆解、销毁、上交、回收不返还生成预算。
3. `SalvageValue` 通常低于交易价值，受状态、设施、技艺、污染和物品类型影响。
4. `ContributionValue` 可基于交易价值和宗门需求程度折算，但贡献不是货币。
5. 价格公式可先采用基准价加节点、供给、宗门关系、权限、声望、事件压力和市场状态修正。

### 5.12 已统一口径

1. 商店入口 NPC 不是商店库存绑定点。
2. 宗门内商店依赖真实宗门供给，宗门外商店不要求完整上游生产链。
3. 玩家出售物进入 `ShopStock` 或回收容器，不支持原价买回。
4. 玩家与非商店 NPC 交易必须使用持久化资产或事件锁定资产，不能临时生成完整库存。
5. 玩家之间交易不作为 MVP 核心；若开放，必须双确认、锁定资产、服务端校验和写日志。
6. 宗门资源申请不放在商店交易规则内，已纳入《宗门系统设计》（`../17_宗门系统设计.md`）。
7. 普通交易不能绕过宗门遗产清点、无主遗留设施开启条件或真灵藏宝数量容量限制。

## 8. UI 展示边界

1. 商店入口应打开统一储物空间页面的 `shop_trade` 模式，同时展示行囊和商店库存。
2. 玩家出售、购买、挂牌、撤单、确认交易和取消交易都必须展示来源容器、目标容器、数量、价格和限制原因。
3. 交易界面不应展示入口 NPC 的个人背包，除非当前业务明确是玩家与该 NPC 的个人交易。
4. 宗门内商店应能展示身份、权限、贡献、职位或宗门供给导致的可见性与价格差异，但不展示 Debug 库存 ID。
5. 交易失败必须保留原资产位置，并展示失败原因。
6. 高价值物品、后手物、功法载体、法宝和突破资源的交易应有额外确认和可追溯提示。
7. 普通 UI 不展示 `transaction_id`、`stock_container_id`、`trade_escrow_id`、随机命名空间、日志内部键和完整复验上下文；这些只进入 Debug / QA。

## 9. MVP 范围

MVP 应实现：

1. 宗门外商店的一口价购买与出售。
2. 宗门内商店的权限货架、购买校验和库存不足反馈。
3. 灵石支付、商店回收价、出售物进入 `ShopStock` 或回收容器。
4. 绑定、锁定、预留、后手封存、任务限制和不可交易标签校验。
5. 买卖成功、失败和回滚的资产流水与交易日志。
6. 储物空间页面中的 `shop_trade` 模式和高价值物品确认。

MVP 不实现：

1. 完整社会经济模拟和商路生产链。
2. 操控市场、倒卖赚差价和完整动态竞价。
3. 玩家之间直接交易作为核心闭环。
4. 完整市场挂牌、寄售、税费、手续费、拍卖和跨区域市场。
5. 完整抢劫、偷窃、查抄、洗劫事件链。
6. 复杂 NPC 议价、债务、赎买、贿赂和关系变化公式。

## 10. 验收约束

1. 任意交易都必须能解释来源容器、目标容器、资产、数量、价格、权限、结果和日志。
2. 商店库存不得绑定到入口 NPC 个人背包；入口 NPC 死亡、离开或替换不应自动搬空商店库存。
3. 聚灵石不得被写入货币余额；贡献不得作为货币直接兑换并绕过库存。
4. 玩家出售物必须进入 `ShopStock`、商店交易缓存或回收队列，不得凭空消失为预算返还。
5. 交易失败时资产保持原位置，或按已声明的部分成功规则处理剩余失败原因。
6. 普通交易不得转移绑定物、事件锁定物、资源预留物、后手封存物、市场挂牌物、不可交易任务物或真灵藏宝物。
7. 宗门资源申请、上交、审批和宗门清点不得放入普通商店买卖规则。
8. 玩家与非商店 NPC 交易不得临时生成完整 NPC 个人库存。
9. 玩家之间交易若开放，必须双确认、锁定资产、服务端复验和双方日志。
10. 抢劫、查抄和洗劫不得走交易价格规则，应进入事件、战斗或正式交锋规则。
