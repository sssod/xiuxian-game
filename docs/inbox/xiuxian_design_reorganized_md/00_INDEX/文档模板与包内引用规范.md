# 文档模板与包内引用规范

适用范围：`docs/inbox/xiuxian_design_reorganized_md`。

本文用于后续新建文档、重排文档和做结构性修订时统一格式。现有文档不要求一次性机械迁移；在人工修订到对应主题时逐步收敛即可。

## 1. 使用原则

1. 先确认主题归属，再选择模板：通用、系统设计、数值设计或交互设计。
2. 每篇文档只回答一个清晰主题，避免把系统规则、数值公式和页面布局混在同一正文中维护。
3. 文档应优先沉淀已稳定结论；未决内容进入“待裁决与待补”，不要伪装成定稿。
4. 包外材料只能作为参考。若采用包外信息，必须改写进包内正文，使本文档包可独立解释。
5. 实现影响写成字段建议、验收约束、风险、技术决策门或待补项；除非用户明确要求，不把文档修订扩展为源码改动。

## 2. 包内引用统一格式

### 2.1 正文引用

正文首次提到其他包内文档时，使用“文档标题 + 相对路径”的形式：

```text
《修炼公式与数值设计》（`../03_数值设计/02_修炼公式与数值设计.md`）负责维护修炼公式。
```

引用路径从当前文件所在目录计算。优先使用相对路径，不使用仓库根绝对路径或 `docs/inbox/xiuxian_design_reorganized_md/...` 长路径，除非是在 `README.md`、`AGENTS.md` 或总索引中说明包位置。

路径写法按实际文件位置计算：同目录使用 `目标文档.md`，相邻一级目录使用 `../03_数值设计/目标文档.md`，位于二级子目录时通常需要 `../../03_数值设计/目标文档.md`。

### 2.2 关联表

每篇较完整的主题文档末尾应保留“包内关联文档”或“包内关联”段落。推荐表格：

```markdown
## N. 包内关联文档

| 文档 | 关系 |
| --- | --- |
| `../03_数值设计/02_修炼公式与数值设计.md` | 提供修炼公式、tick 输出和调参边界 |
| `../04_交互设计/04_修为页面设计.md` | 承接修为进度、瓶颈和突破准备的页面表达 |
```

“关系”列应说明引用目的，而不是只写“参考”。推荐用词：

| 用词 | 含义 |
| --- | --- |
| 唯一信源 | 该规则、表格或定义只在目标文档维护，本文不重复维护 |
| 承接 | 本文读取目标文档结论并在本主题中展开 |
| 被承接 | 目标文档读取本文结论用于其他层面表达 |
| 展示 | 交互文档负责把本文规则转成页面信息和操作反馈 |
| 验算 | 数值验算文档用于验证本文模型、表格或边界 |
| 待整合 | 仅表示后续需要人工判断是否纳入，不代表已经采纳 |

### 2.3 章节级引用

除非章节标题已经稳定，不建议使用 Markdown 锚点引用中文标题。需要指出章节时，在“关系”列或正文中写明章节名即可：

```text
详见 `01_修为境界与期望游玩时间建模.md` 的“境界段根表”。
```

不要引用行号。行号会随修订变化，不适合作为设计文档约束。

### 2.4 包外与 Figma 引用

包外文件、历史文档和 Figma 只能作为参考来源或 UI 位置依据：

1. 包外信息被采纳后，应改写进本包内部，不让读者必须跳出本包才能理解规则。
2. Figma 只用于节点级 UI 布局和组件位置；稳定 UI 决策应沉淀到 `04_交互设计`。
3. 维护记录可以说明“从包外资料整理而来”，但正文应以包内结论为准。

## 3. 通用文档模板

适用于 `README.md`、总索引、规范说明、跨主题约束、术语边界和轻量级说明文档。

```markdown
# {文档标题}

适用范围：{本文件约束的目录、主题或工作阶段}。

## 1. 当前定位

说明本文为什么存在、解决什么问题、不解决什么问题。

## 2. 使用方式

1. {入口或阅读顺序}
2. {修订或执行步骤}
3. {遇到冲突时的处理方式}

## 3. 规则或清单

按主题列出稳定规则、目录清单、术语口径或流程约束。

## 4. 包内关联文档

| 文档 | 关系 |
| --- | --- |
| `{相对路径}` | {唯一信源 / 承接 / 被承接 / 待整合} |

## 5. 维护记录

YYYY-MM-DD：{本次新增、修订或收束的内容}。
```

通用文档可以不编号到很深，但应清楚说明适用范围、使用方式和维护状态。

## 4. 系统设计模板

适用于玩法、系统、对象规则、流程、资源流转、角色状态和世界规则。

```markdown
# 系统设计｜{主题名}

## 1. 设计定位

说明本系统负责回答的问题、玩家或世界层面的作用，以及不负责的内容。

## 2. 当前结论

1. {已稳定结论}
2. {已稳定结论}
3. {仍有边界但可作为当前口径的结论}

## 3. 文档边界

| 文档 | 负责内容 |
| --- | --- |
| `{到目标数值文档的相对路径}` | 公式、表格、倍率、验算或调参边界 |
| 本文 | 系统规则、流程、状态、约束和玩家可决策内容 |
| `{到目标交互文档的相对路径}` | 页面表达、操作入口、反馈和异常状态 |

## 4. 核心循环或触发入口

描述玩家入口、系统触发条件、循环步骤和中断点。

## 5. 规则与状态

按子主题维护可执行规则、状态枚举、生命周期、权限、锁定、失败条件和边界。

## 6. 资源、角色、地图、事件或 NPC 接口

列出本系统读取和写入的其他系统口径。只维护职责边界，不重复数值表。

## 7. 数据字段建议

| 字段 | 含义 |
| --- | --- |
| `{field_name}` | {字段语义、来源、是否派生、是否持久化} |

字段建议是实现提示，不等同于最终数据库或代码结构。

## 8. UI 展示边界

说明普通 UI 应展示哪些决策信息，哪些 Debug / QA 信息不进入普通界面。

## 9. MVP 范围

MVP 应实现：

1. {必要规则}
2. {必要状态}

MVP 不实现：

1. {明确排除项}
2. {后续阶段内容}

## 10. 验收约束

1. {人工审核或实现验收时必须成立的规则}
2. {不能被数值、UI 或实现绕开的边界}

## 11. 待裁决与待补

| 项目 | 当前口径 | 需要裁决或补充 |
| --- | --- | --- |
| {问题} | {暂定处理} | {需要用户判断的点} |

## 12. 包内关联文档

| 文档 | 关系 |
| --- | --- |
| `{相对路径}` | {关系说明} |

## 13. 维护记录

YYYY-MM-DD：{修订摘要}。
```

系统设计文档应优先写清“谁负责什么”和“玩家如何决策”。公式、倍率和完整表格应转入数值设计文档。

## 5. 数值设计模板

适用于公式、数值模型、投放、预算、验算、配置表和调参口径。

```markdown
# 数值设计｜{主题名}

## 1. 设计定位

说明本文负责的数值问题、单位、调参目标和不负责的玩法流程。

## 2. 当前结论

1. {已稳定数值口径}
2. {已稳定公式或表结构口径}
3. {与系统设计的边界}

## 3. 文档边界

| 文档 | 负责内容 |
| --- | --- |
| `../02_系统设计/{目标文档}.md` | 玩家行动、系统规则、状态和约束 |
| 本文 | 单位、公式、表结构、倍率、预算和调参边界 |
| `08_数值验算.md` | 验算样例、曲线检查和异常测试 |

## 4. 基准、单位与输入参数

列出基础单位、时间口径、输入字段、取值范围和默认值。

## 5. 公式或模型

使用公式、伪代码或分步结算说明核心模型。公式应定义每个变量来源。

## 6. 配置表或根表

| 字段 | 含义 | 备注 |
| --- | --- | --- |
| `{field_name}` | {数值含义} | {来源、范围或调参说明} |

## 7. 结算输出

列出结果包、日志、流水、可见摘要、Debug 信息和回放所需字段。

## 8. 调参验收口径

1. {玩家体验目标}
2. {公式必须满足的边界}
3. {不能出现的漏洞或反常收益}

## 9. MVP 范围

MVP 应实现：

1. {必要表}
2. {必要公式}

MVP 不实现：

1. {复杂叠加、长期曲线或高级阶段内容}

## 10. 待裁决与待补

| 项目 | 当前口径 | 需要裁决或补充 |
| --- | --- | --- |
| {问题} | {暂定处理} | {缺失数据、曲线或样例} |

## 11. 包内关联文档

| 文档 | 关系 |
| --- | --- |
| `{相对路径}` | {关系说明} |

## 12. 维护记录

YYYY-MM-DD：{修订摘要}。
```

数值设计文档应避免重复系统设计的完整玩法描述。需要玩法前提时，用文档边界和关联表指向系统设计文档。

## 6. 交互设计模板

适用于页面、弹窗、面板、操作入口、反馈状态和信息表达规则。

```markdown
# 交互设计｜{页面或流程名}

## 1. 当前状态

说明该页面或交互当前是否为草案、已稳定约束或待补页面。

## 2. 包内关联

| 文档 | 关系 |
| --- | --- |
| `../02_系统设计/{目标文档}.md` | 提供系统规则、状态和操作边界 |
| `../03_数值设计/{目标文档}.md` | 提供进度、收益、风险或数值展示口径 |

## 3. 用户目标与入口

说明玩家为什么进入此页面、从哪里进入、完成后回到哪里。

## 4. 必须表达

1. {玩家必须看见的状态或决策信息}
2. {必须暴露的操作入口}
3. {必须提示的风险、消耗或不可用原因}

## 5. 页面区块与信息优先级

按稳定区块说明信息层级。只记录稳定 UI 决策，不记录具体像素、节点 ID 或组件坐标。

## 6. 操作流程与状态

列出正常状态、空态、禁用态、错误态、确认态、结算反馈和中断返回。

## 7. 不表达或 Debug 边界

说明普通 UI 不展示的公式追踪、内部 ID、原始倍率、QA 字段或剧透信息。

## 8. 待补

1. {需要 Figma 或人工评审补齐的布局细节}
2. {缺少的文案、状态或组件规则}

## 9. 维护记录

YYYY-MM-DD：{修订摘要}。
```

交互设计文档可以比系统和数值文档更轻，但必须写清包内关联和“必须表达”。节点级布局和组件摆放以当前 UI artifact / Figma 为准。
