# 轮回修仙项目｜开发交付整理 README

## 1. 本交付包用途

本交付包根据当前 sources 中导出的 29 份 Markdown 设计文档整理而成，目标是把原先散落在 Notion 草稿、核心体验稿、S1–S14 子系统稿、桥接草稿中的设计内容，重组为更适合开发人员阅读、拆分、实现和验收的文档结构。

本交付包不是对原文的逐字搬运，而是一次“开发口径整理”：

- 合并重复描述。
- 将体验层、规则层、数据层、实现层拆开。
- 将已定规则与未审核草稿分层标注。
- 统一系统命名、字段命名和抽象编码。
- 对明显的设定冲突、变量命名冲突给出临时标准口径。
- 将 MVP 开发切片与验收清单前置，便于进入实现阶段。

## 3. 文档优先级

后续开发引用规则时，建议采用以下优先级：

1. 本交付包中的 `03_术语表_命名规范_冲突消解.md` 和 `03_冲突决议_待确认问题_风险登记.md`：用于处理命名和冲突。
2. 顶层定案与核心体验：用于判断玩法方向是否偏离。
3. 已人工参与编辑并吸收决策的 0426–0427 桥接文档：用于补充跨系统口径。
4. S1–S14 子系统文档：用于确定系统边界和接口。
5. 标注“未人工审核”的内容：作为实现草案，不视为最终数值或最终 UI。

## 4. 关键状态说明

- `定案 / 已收束`：可以作为开发依据，但仍需在具体数值、UI、数据库 schema 阶段细化。
- `人工参与编辑 / 未最终定稿`：可作为当前推荐口径；实现前建议过一次设计确认。
- `未人工审核`：可作为系统边界草案；开发前至少确认是否接受该页的 MVP 范围。
- `草稿`：用于验证体验和事件结构；不能直接当作完整规则表。

## 6. 本交付包的开发使用建议

开发阶段不建议直接把所有原始 Notion 文档都发给程序员作为唯一依据。原始文档适合追溯设计理由；本交付包适合作为当前实现口径。若实现过程中遇到不一致，以本交付包的冲突决议为临时口径，再回到 Notion 做最终人工确认。
