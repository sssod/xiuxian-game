# 交互设计｜主棋盘规划与结算

适用范围：主棋盘上的回合状态、即时行动、隐藏规划、同步移动、行动补充输入、竞争暂停和统一结算反馈。本文只定义稳定的信息与操作边界，不裁决节点位置、视觉样式或动效。

## 1. 交互目标

玩家在任一时刻都应能够回答四个问题：

1. 当前处于哪个回合阶段；
2. 自己还可以做什么；
3. 已经承诺了什么、是否仍可修改；
4. 系统正在等待谁、为什么暂停以及下一步会发生什么。

主棋盘交互必须服务“同时规划、同步移动、统一行动结算”，不能把流程误呈现成玩家依次行动。

## 2. 回合阶段表达

主棋盘至少区分以下稳定阶段：

| 阶段 | 玩家输入 | 必须展示的信息 |
| --- | --- | --- |
| 回合开始 | 即时行动、结束即时阶段 | 当前状态、可用即时行动、每回合限次操作 |
| 隐藏规划 | 目的地、路线、移动方式、主要行动类型 | 自己的完整计划、预计资源消耗、合法性与提交状态 |
| 同步移动 | 无常规改动；只响应相关中断 | 共享移动进度、实际停留位置、相关相遇或事件 |
| 行动细节输入 | 为已承诺行动补对象、数量或投入 | 原定行动类型、当前合法参数、失败条件 |
| 统一行动结算 | 只处理相关竞争输入 | 结算队列、暂停原因、竞争参与者和恢复条件 |
| 回合末 | 通常无输入 | 修炼、恢复、炼化、寿元、世界与飞升判定结果 |

界面必须明确标识当前全局阶段，不得只依靠按钮是否可点击让玩家猜测。

## 3. 隐藏规划与提交

规划阶段不公开其他玩家的目的地、路线、移动方式或主要行动意图。玩家只看到自己的计划和其他玩家是否已经提交，不看到提交内容。

提交前必须允许玩家检查：

- 目的地与路径；
- 移动方式及预计元气成本；
- 主要行动类型；
- 当前可知的抵达与行动门槛；
- 提交后将锁定的内容。

提交后，在全员确认或阶段截止前能否撤回尚未裁决，不得由界面自行假定。规划时限、未提交默认和断线托管属于 MVP P0 阶段门。

## 4. 两段式行动输入

移动前只承诺行动类型；抵达后才首次选择对象、数量、投入等细节。交互上必须把两段输入分开，避免玩家误以为移动前已经锁定不存在的目标实例。

若玩家未抵达，原定主要行动直接失效，不再要求填写参数。若成功抵达但没有合法参数，应明确反馈：

```text
原定行动无法执行
→ 本回合主要行动失败
→ 从当前地点的途中事件池独立抽取代偿事件
```

界面不得在此时允许改选另一种主要行动。

## 5. 同步移动与局部中断

同步移动期间，应持续显示每名玩家的实际位置和已完成移动结果；其他玩家的隐藏路线只在实际移动产生可见结果时显现。

相遇或强制途中事件只中断相关玩家。无关玩家应能理解自己的移动结果已经完成或仍在演算，不应被要求重复确认。移动阶段只记录事件，选择与战斗延后到行动结算阶段处理。

## 6. 统一结算与竞争暂停

独立行动可以按既定顺序继续结算；只有涉及复数玩家的竞争才暂停全局行动结算。暂停时至少展示：

- 触发竞争的地点或目标；
- 当前参与者；
- 竞争类型，例如战斗或竞价；
- 正在等待的输入；
- 竞争结束后会从哪一项恢复结算。

连续战斗需要显示当前对阵顺序和最终结算性质，但中途不得展示尚未判定的死亡掉落结果。

## 7. 结果与可解释性

每次结算反馈至少能追溯到“来源—变化—结果”：

```text
来源：行动 / 事件 / 战斗 / 回合末效果
→ 状态或资产变化
→ 对后续行动、成长或胜利条件的影响
```

回合末应把自动修炼、持续状态、恢复、法宝炼化、寿元和世界结果分组呈现。小洞天的十个内部时间单位需要让玩家看出累计结果及中途耗尽，但不要求逐 tick 播放十次相同动画。

## 8. MVP 缺口

进入交互原型前仍需关闭：阶段时限、提交撤回、未提交安全默认、断线 / 重连 / 托管、永久退出、房主离开和对局中止。首张地图与完整主要行动表未定前，也不能锁定主棋盘页面流和信息优先级。
