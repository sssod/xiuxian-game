# 数值设计｜事件设计基准建模

## 1. 设计定位

本文负责事件节点、候选池、触发条件、事件链路由、玩法配置引用、窗口、传闻和专用事件链入口的数值建模基准。它维护事件候选生成、候选池评分排序、去重节流、事件层级、选项成本 / 风险 / 收益、隐藏后患、奖励预算、结果包输出和验算指标。

系统玩法由《随机事件玩法设计》（`../02_系统设计/15_随机事件玩法设计.md`）维护；本文只维护数值建模、调参接口和验算约束。本文不负责完整事件文本库、最终概率表、战斗伤害公式、突破轮内成功率公式、NPC AI 权重、UI 视觉布局、数据库 schema 或网络协议。

## 2. 当前结论

1. 事件数值运行在 `world_day / world_hour` 与结算区间上；N1 的结算区间通常等于 1 个 `hour_tick`，F1、后台追赶和局部时间域可以使用更长区间，但不再使用 `quarter / tick / 行动格` 作为事件主时间字段。
2. 事件候选必须由世界状态、角色状态、节点状态、行动上下文、窗口、资源预算、可见性和冷却共同生成，不做纯 UI 刷新随机。
3. 事件概率、权重、窗口出现频率和同一结算时间桶最大普通触发数量尚未定；本文只定义可验算的配置结构和首版边界。
4. 候选生成可以有随机扰动，但必须使用事件实例稳定种子或稳定排序，不能靠刷新界面改变候选。
5. 事件主配置使用 `EventNode`：事件唯一编号、事件层级、基础权重、候选池入口、玩法类型、玩法配置引用和事件链路由是核心字段；顶层可见性、时间模式、F1 处理等级、来源标签和结果强度默认从玩法类型、候选池、路由、运行时上下文和结算节点派生。
6. 使用 `local_time_stop` 的个人即时处理事件和轻遭遇都使用局部时停；C1 或其它时间追赶期间不触发新的随机个人即时处理事件、普通机缘、普通战斗、软机会事件、普通心魔或普通资源反馈，但应复用事件池压制逻辑并继续累积符合条件但未触发的伪随机压力。
7. 正式交锋和突破挑战归入同步处理事件并进入 B1；B1 的现实提交窗口、非参战世界推进和参战交锋自身结算耗时必须分开记录。
8. 事件奖励不得绕过世界产出预算、资产容器、库存来源、资源预留和结果包审计。
9. 低价值事件可以被显式托管保守处理；重大事件、正式交锋、突破挑战、不可逆选择和死亡风险不得被普通队列或自动兜底吞掉。
10. F1 中事件仍会触发；预定事件、阈值事件、危险率事件和条件事件可通过通用事件流采样进入批量摘要、F1 校验断点或 F1 中断断点。F1 处理等级为 `silent / summary / auto` 的事件默认不打断 F1。
11. 事件配置分为事件节点、候选池、条件、玩法配置、事件链路由和结算输出；移动、闭关、节点、宗门、局部时间域和世界宏观事件应复用同一套候选池与伪随机模型。

## 4. 基准、单位与输入参数

事件数值链路以 `EventNode` 为唯一事件节点配置。事件本身只描述“可从哪里进入、怎么玩、之后路由到哪里”；候选池、条件、玩法细节、运行时提案、结算输出和 Debug 回放放在外部结构。

```text
EventNode
→ EventCandidatePool / EventCondition
→ EventPlayConfig
→ EventRuntimeContext / EventCandidateScore / EventOccurrenceProposal
→ EventNode route
→ settlement EventNode
→ ResultPackage / EventBalanceSimulation
```

| 模块 | 作用 |
| --- | --- |
| `EventNode` | 定义事件节点的唯一编号、层级、基础权重、候选入口、玩法类型、玩法配置引用和链路由 |
| `EventCandidatePool` | 聚合同一语义桶、结算区间、角色、节点、行动或窗口的候选事件 |
| `EventCondition` | 配置事件进入候选池的复用条件，例如单程耗时、地形、风险、状态、冷却、预算和窗口 |
| `EventPlayConfig` | 按玩法类型承接对话选项、属性判定、战斗交锋、突破交锋、信息回读或结算效果 |
| `PoolPseudoRandomState / EventPseudoRandomState` | 分别记录候选池 / 语义桶级无事件权重和事件节点级附加权重、保底游标、短时压制和追赶压制状态 |
| `EventCandidateScore` | 运行时派生结构，对候选按基础权重、事件层级、节点等级匹配、阶段可用性和短期压制计算当前有效权重 |
| `EventOccurrenceProposal / EventOccurrenceResolution` | 运行时提案和裁决回放结构，不作为事件主配置字段 |
| `ResultPackage` | settlement 节点输出的权威结算包，包含状态变化、日志、传闻、预算和后续路由请求 |
| `EventBalanceSimulation` | 验算事件密度、打断率、奖励预算消耗、B1 / P0 频率和负反馈强度 |

`EventNode` 最少应声明：

```yaml
EventNode:
  event_id: string
  event_tier: tier_0 | tier_1 | tier_2 | tier_3 | tier_4 | tier_5
  base_weight: number
  event_pity_accrual_rate: number
  candidate_entries:
    - pool_id: string
      condition_ref: string | null
  play_type: info | choice | check | combat_clash | breakthrough_clash | settlement
  play_config_ref: string | null
  routes:
    - trigger: string
      target_event_id: string
```

`event_tier` 表示事件层级，和修为境界阶段、地图 `node_level` 属于同一类分层概念，颗粒度应比具体修为等级更粗，并用于判断事件与地图节点是否匹配。它不是 F1 处理等级、风险等级或结果强度；收益 / 损失波动上限应由事件层级、玩法类型和具体结果配置共同约束。

`base_weight` 只对能够从候选池直接进入的节点有随机意义。只能由其它事件路由进入的链内节点或结算节点可以设为 `0`，并使用空 `candidate_entries`。

`event_pity_accrual_rate` 是事件节点级配置，用于控制该事件是否享受事件节点级触发累积。高基础权重、常见、填充或不希望形成轮转感的事件可以设为 `0`；低权重但希望长期可见的事件可以设置更高值。

`candidate_entries` 表示该事件能进入哪些候选池，以及在该池内使用哪个复用条件。地形、节点、路线、行动、窗口、状态、冷却和预算等“能不能进池”的判断应优先写入 `condition_ref`，不要重复写成权重倍率。

`play_type` 表示事件节点的玩法形态。复杂事件通过多个单玩法节点串联：例如对话选择路由到属性判定，判定失败再路由到战斗交锋，最终路由到 settlement 节点。事件结果视为 `play_type = settlement` 的事件节点，是事件链的端点之一。

`play_config_ref` 连接到对应玩法系统的配置：对话选项、检定公式、战斗配置、突破配置、信息回读或结算效果包都不进入事件主字段。

`routes` 是事件链的基础可配置结构。`trigger` 可以来自选项、检定结果、战斗胜负、突破结果、默认处理、超时兜底或 Debug 入口。

由旧字段派生或迁移的口径：

| 旧字段 | 当前去向 |
| --- | --- |
| `template_id` | 改为 `event_id` |
| `EventWeightProfile.base_weight` | 上移为 `EventNode.base_weight` |
| `EventTriggerProfile.candidate_pool_refs` | 合并为 `candidate_entries.pool_id` |
| `candidate_entry_rule_refs / candidate_exit_rule_refs` | 合并为 `candidate_entries.condition_ref` |
| `gameplay_modules` | 收敛为单一 `play_type`；多玩法用多个事件节点串联 |
| `child_event_request_refs` | 迁移为 `routes` |
| `result_package_template_ref` | 迁移为 settlement 节点的 `play_config_ref` |
| `source_domain_tags` | 默认由 `candidate_entries.pool_id`、运行时上下文和日志配置派生 |
| `top_level_type` | 由 `play_type`、事件层级、运行时上下文和速度状态派生 |
| `event_time_mode` | 由 `play_type` 和运行时速度状态派生 |
| `f1_interrupt_level` | 由 `play_type`、事件层级、是否有默认路由和托管策略派生 |
| `outcome_level_baseline` | 不作为事件主字段；实际结果强度由 settlement 配置和结果包输出 |
| `visibility_policy` | 下沉到玩法配置、日志配置或 settlement 结果 |

时间、随机和上下文基准：

1. 候选生成使用 `trigger_world_day / trigger_world_hour` 和结算区间；N1 可直接对应 `hour_tick`，F1、后台追赶和局部时间域必须保留区间起止与采样种子。
2. 顶层类型、事件时间模式和 F1 处理等级是派生结果，不作为 `EventNode` 主配置字段。
3. 随机扰动必须归属 `rng_namespace`，并在事件实例或候选排序中稳定复盘。
4. 所有状态变化、预算扣减、窗口变化和日志输出必须能追溯到运行时上下文。

`EventRuntimeContext` 是运行期结构，不是事件配置表。推荐字段：

```yaml
EventRuntimeContext:
  context_id: string
  trigger_world_day: int
  trigger_world_hour: int
  trigger_type: travel_leave | travel_enter | route_hour_tick | action_hour_tick | action_complete | node_update | sect_update | window_update | contingency_trigger | death_or_reincarnation | rumor_update | manual_debug
  actor_refs: list[string]
  faction_refs: list[string]
  node_id: string | null
  node_level: tier_0 | tier_1 | tier_2 | tier_3 | tier_4 | tier_5 | null
  route_id: string | null
  route_segment_ref: string | null
  current_command_ref: string | null
  risk_level: low | medium | high | unknown | null
  domain_refs: object
  current_macro_period_id: string | null
  time_domain_scope: outer_world | local_time_domain | threshold | scheduled | conditional
  settlement_interval_ref: string | null
  local_time_domain_ref: string | null
  rng_namespace: string
```

`domain_refs` 用于承接资源槽、设施、隐藏层、后手、遗迹、窗口、传闻等上下文引用。具体系统可以在自身文档中定义子结构；事件主模型不为每一类引用固定根字段。

旧口径迁移：

| 旧字段 / 旧说法 | 当前口径 |
| --- | --- |
| `quarter` | 不作为事件主时间字段；宏观批次使用 `current_macro_period_id` |
| `tick` | 具体结算使用 `hour_tick`、`trigger_world_day`、`trigger_world_hour` |
| `danger_level` | 地图风险统一为 `risk_level`；事件自身可另有风险描述标签 |
| `route_segment` | 迁移为 `route_segment_ref` |
| 行动格消耗 | 迁移为 `consumed_hours`、行动进度变化、B1 世界推进或交锋自身结算耗时 |
| 世界刷新只在季度开始发生 | 迁移为世界小时演化 + 宏观周期批次；窗口、资源和传闻仍可按宏观周期批量显现 |

## 5. 公式或模型

### 5.1 候选池评分

候选评分不是最终概率公式，而是可用于首版实现和验算的统一接口。

```yaml
EventCandidateScore:
  candidate_id: string
  event_id: string
  runtime_context_id: string
  event_tier: tier_0 | tier_1 | tier_2 | tier_3 | tier_4 | tier_5
  node_level: tier_0 | tier_1 | tier_2 | tier_3 | tier_4 | tier_5 | null
  base_weight: number
  tier_node_match_multiplier: number
  phase_availability_multiplier: number
  short_term_suppression_multiplier: number
  effective_weight: number
  suppressed: bool
  suppression_reason: string | null
  score_reason_tags: list[string]
```

推荐起步公式：

```text
effective_weight =
  base_weight
  * tier_node_match_multiplier
  * phase_availability_multiplier
  * short_term_suppression_multiplier
```

`base_weight` 代表事件基础发生率和稀有度，通常与 `event_tier` 同向约束事件设计基准：层级越高，基础权重越低，允许的收益 / 损失波动上限越大。候选池、语义桶、地形、行动类型、路线状态和标签主要决定“能不能进池”，默认不再额外乘权重。

`tier_node_match_multiplier` 比较事件层级与地图节点等级，目标是让高等级节点提高高层级事件的相对占比，同时降低低层级杂事占比，而不是让节点越高整体事件总量越高。首版建议：

| `event_tier - node_level` | 含义 | 修正 |
| --- | --- | --- |
| `-2` 或更低 | 事件层级明显低于节点等级 | `0.25` |
| `-1` | 事件层级略低于节点等级 | `0.6` |
| `0` | 事件层级与节点等级匹配 | `1.5` |
| `+1` | 事件层级略高于节点等级 | `0.8` |
| `+2` | 事件层级明显高于节点等级 | `0.25` |
| `+3` 或更高 | 超阶段事件 | `0`，除非特殊窗口或事件链显式放行 |

规则：

1. 缺少节点等级或阶段匹配信息时默认倍率为 `1.0`，不得因为字段缺失自动放大事件概率。
2. 资源预算、可见性和安全默认主要作为进入条件、降级、延后或压制策略，不作为常规发生率倍率。
3. 冷却、重复和 C1 / 时间追赶压制统一收束为 `short_term_suppression_multiplier` 或 `suppressed`。
4. 稳定随机种子只用于抽样和同级再随机，不写成权重倍率，也不能随 UI 刷新变化。
5. 伪随机状态属于 `PoolPseudoRandomState / EventPseudoRandomState`，不作为候选评分字段；当权重随机或保底机制命中时，应生成触发提案。
6. 调试器应能展示 `score_reason_tags`、命中的条件、被压制原因和 `effective_weight`。

### 5.2 候选池节流与去重

同一结算时间桶和同一上下文中可能存在多个候选事件。N1 下结算时间桶通常等价于同一 `hour_tick`；F1、后台追赶和局部时间域下由结算区间、采样时间和回放桶共同确定。MVP 采用以下节流规则：

1. 硬移出、上下文失效或同语义重复的候选不产生触发提案。
2. 同一语义事件在同一结算时间桶和同一上下文中只触发一次。
3. 同一角色同一时刻最多只能有一个需要本人处理的局部时停事件。
4. 同一世界同一时刻最多只能有一个 P0 同步处理事件。
5. C1 或其它时间追赶期间所有新随机个人候选都必须被 `suppress`；压制期间不生成事件实例，但符合候选池硬条件的事件仍可累积伪随机状态。
6. 事件链进行中时，普通角色时间线按派生出的 `event_time_mode` 决定冻结、继续或进入交锋。
7. 事件返回后，由权威结算决定继续原计划、进入 C1、跳过指令、自动兜底或开启后续路由事件。

世界级重大事件和窗口可在自身状态机中定义容量、阶段推进和忽略后果，但不作为通用事件流的默认限量。通用事件流只保证竞态裁决可复盘，重大世界状态机另行约束：

```text
每个 active major 世界事件必须至少有一个玩家可理解的介入窗口；
忽略重大事件可以改变世界态势，但不应无预警造成毁档式损失。
```

以上规则约束重大世界状态机的设计，不等于普通事件候选池的通用触发上限。

同一结算时间桶内多个事件同时满足触发条件时，按“触发提案裁决”处理。触发提案来源和事件处理等级是两层概念：

```text
触发提案来源：forced / scheduled / threshold_crossing / weighted_hit / bucket_pity_hit / event_pity_hit
事件处理等级：silent / summary / auto / soft_interrupt / hard_interrupt / B1 / P0
```

`weighted_hit` 是正常权重随机命中；`bucket_pity_hit` 是候选池 / 语义桶级伪随机保底命中，用于避免同类事件短期总频率极端偏离预期期望；`event_pity_hit` 是事件节点级伪随机保底命中，用于避免低权重事件长期无法被抽中。保底命中只表示应产生触发提案，不代表一定立刻生成事件实例。

触发提案使用结算期内的临时结构，不要求把所有字段固化到事件节点或候选评分中：

```yaml
EventOccurrenceProposal:
  proposal_id: string
  source: forced | scheduled | threshold_crossing | weighted_hit | bucket_pity_hit | event_pity_hit
  event_id: string
  event_tier: tier_0 | tier_1 | tier_2 | tier_3 | tier_4 | tier_5
  pool_ref: string
  runtime_context_ref: string
  occurred_at: string
  pool_occurrence_mass: number
  effective_weight: number
  event_select_weight: number
  rng_ref: string | null
  block_reason: string | null
  defer_reason: string | null
```

提案裁决顺序：

1. 先按实际发生时间切桶；不同时间点按时间先后处理，同一时间点才进入竞态。
2. 同一桶内先执行硬排除和同语义去重，硬移出的候选不产生触发提案。
3. 每个有效候选池默认执行一次二段抽样：第一段判断该池本桶是否出事件，第二段只在第一段出事件时抽选具体 `event_id`。
4. 第一段使用候选池 / 语义桶级 `PoolPseudoRandomState`：`pool_occurrence_mass` 与 `no_event_current_weight` 共同决定是否出事件；若抽中无事件，则只更新候选池级伪随机状态。
5. 第二段使用事件节点级 `EventPseudoRandomState`：候选事件按 `event_select_weight = effective_weight + event_pity_bonus_weight` 抽选。事件级附加权重只影响同池事件选择，不影响候选池是否出事件。
6. 第一段因权重随机出事件时，产生 `weighted_hit` 提案；候选池 / 语义桶级无事件权重降至 0 后出事件时，产生 `bucket_pity_hit` 提案；第二段中携带事件节点级附加权重的事件被选中时，可产生或标记为 `event_pity_hit` 提案。
7. 触发来源只作为回放、审计和调试字段，不参与竞态优先级排序。
8. 多个提案同时存在时，先按 `event_tier` 裁决，高层级事件优先；同层级事件按当前 `event_select_weight` 加权再随机，稳定随机种子用于复盘抽选结果。
9. 首版通用限量只保留同一角色同一时间桶最多一个需要本人处理或局部时停的事件，以及同一世界同一时间最多一个 P0 同步处理事件。
10. 超出个人单事件限量或全世界 P0 限量的提案默认延期、保留或衰减伪随机状态；具体策略由候选池 / 事件节点或玩法配置定义。
11. 被选中的提案生成事件实例后，按候选池级和事件节点级伪随机策略重置、衰减或迁移状态。

容量上限不是概率或权重，而是防止同一结算桶爆出过多事件的结构限制。当前明确的容量类型包括：

```text
个人单事件限量：同一角色同一时间桶最多一个需要本人处理或局部时停的事件；
全世界 P0 限量：同一世界同一时间最多一个 P0 同步处理事件。
```

候选保留数量、重大世界事件容量、窗口容量、批次性能保护等不作为通用事件流的 MVP 默认裁决规则；需要时由具体事件链、世界窗口系统或 Debug / 性能保护配置单独定义。

提案裁决结果必须进入回放：

```yaml
EventOccurrenceResolution:
  time_bucket_ref: string
  proposal_refs: list[string]
  selected_proposal_refs: list[string]
  deferred_proposal_refs: list[string]
  suppressed_proposal_refs: list[string]
  capacity_limit_refs: list[string]
  stable_tie_break_seed: string
  resolution_reason_tags: list[string]
```

### 5.3 事件强度分层

事件节点层级和实际结果强度必须分开。`event_tier` 用于事件与境界阶段、地图节点等级的匹配；`outcome_level` 只用于 settlement 节点和结果包中的实际结果强度。首版可以统一使用 `outcome_level` 做结果强度：

```text
none
minor
standard
major
critical
```

| `outcome_level` | 含义 | 常见结果 |
| --- | --- | --- |
| `none` | 信息、提示或日志更新，无实质状态变化 | 传闻记录、价格提示、节点趋势 |
| `minor` | 轻量变化，不应造成长期大改动 | 小延误、少量资源消耗、低风险发现、轻微关系波动 |
| `standard` | 常规事件结果，可以改变一次行动、节点、库存、关系或传闻 | 普通移动遭遇、资源异变、节点风险、常规探索发现 |
| `major` | 高价值或高风险结果，会影响窗口、战斗、突破、宗门评价、重要资产或节点态势 | 秘境入口、正式交锋入口、高价值后手线索、控制权变化 |
| `critical` | 不可逆或接近不可逆结果，需要明确事件节点、玩法配置、安全默认或 P0 同步保护 | 死亡边缘、重大夺舍、不可逆功法路线、严重资源损毁、公共世界级事件 |

强度规则：

1. 低风险普通候选不得直接随机生成 `critical` 结果；必须经过明确事件节点、玩家选择、B1 / P0 或高风险上下文。
2. `major / critical` 结果必须写入日志、回放、可见性规则和 Debug 审计。
3. 事件奖励强度不得高于其成本、风险、窗口稀缺性和预算来源能解释的范围。
4. 失败结果也要有强度分层，不能只输出“未成功”。

事件时间成本统一通过 `EventTimeCostProfile` 表达。

```yaml

  trigger_world_day: int
  trigger_world_hour: int
```

| --- | --- |

### 5.6 候选池、权重与伪随机压力

事件配置应把“是否有资格进入池”和“进入后多容易触发”分开。进入 / 移出候选池是硬条件；权重、压制和伪随机状态只作用于已经进入候选池的事件。

候选池示例：

```yaml
EventCandidatePool:
  pool_id: travel_event_pool
  scope: travel
  clock_scope: outer_world
  default_settlement_interval: route_segment | hour | outer_day | custom
  candidate_limit_policy: weighted_top_n | all_eligible
  occurrence_resolution_policy_ref: string | null
```

移动来源候选可以复用一个 `travel_event_pool`，再通过 `EventNode.candidate_entries` 与 `EventCondition` 控制候选：

```yaml
EventNode:
  event_id: travel_ambush_intro
  event_tier: tier_1
  base_weight: 10
  event_pity_accrual_rate: 0.25
  candidate_entries:
    - pool_id: travel_event_pool
      condition_ref: travel_medium_or_high_risk_min_2h
  play_type: choice
  play_config_ref: choice_travel_ambush_intro
  routes:
    - trigger: option_negotiate
      target_event_id: travel_ambush_negotiate_check
    - trigger: option_force_breakout
      target_event_id: travel_ambush_combat
    - trigger: option_pay_toll
      target_event_id: travel_ambush_pay_settlement

EventCondition:
  condition_id: travel_medium_or_high_risk_min_2h
  require:
    min_trip_hours: 2
    terrain_any: [mountain, forest, wildland]
    route_risk_any: [medium, high]
  exclude:
    route_tags: [safe_patrolled]
    actor_states: [hidden_by_high_tier_talisman]
```

进入 / 移出条件建议支持：

```text
时间条件：单程耗时、累计行动小时、当前时辰、窗口持续时间、局部主观年；
空间条件：地形、节点、路线、区域、风险等级、控制权；
角色条件：境界、身份、状态、资源、队伍规模、隐藏标签；
行为条件：当前行动、移动方式、闭关方式、显式托管、是否 F1；
世界条件：宗门局势、市场周期、区域事件、宏观阶段；
冷却条件：同类事件间隔、角色冷却、路线冷却、区域冷却；
预算条件：奖励预算、风险预算、窗口容量、重大事件容量。
```

链内节点和结算节点不需要再次进入候选池：

```yaml
EventNode:
  event_id: travel_ambush_negotiate_check
  event_tier: tier_1
  base_weight: 0
  event_pity_accrual_rate: 0
  candidate_entries: []
  play_type: check
  play_config_ref: check_persuasion_vs_bandit
  routes:
    - trigger: check_success
      target_event_id: travel_ambush_escape_settlement
    - trigger: check_fail
      target_event_id: travel_ambush_combat
```

地形、路线风险、行动类型、节点标签等因素默认写入候选池进入 / 移出条件，不再作为常规权重倍率重复计算。若某个特殊事件确实需要非层级匹配修正，必须在事件节点或玩法配置中写明设计原因，并进入调参验算。

双保底伪随机采用二段抽样：

1. 候选池 / 语义桶级保底只回答“本池本桶是否出事件”。
2. 事件节点级保底只回答“本池已决定出事件后，具体哪个 `event_id` 被选中”。

第一段使用候选池级无事件权重：

```text
pool_occurrence_mass =
  Σ eligible_event(base_weight * tier_node_match_multiplier)

P(pool_trigger) =
  pool_occurrence_mass / (pool_occurrence_mass + no_event_current_weight)
```

`pool_occurrence_mass` 是当前池内可触发基础质量，只取已经通过硬条件的候选事件，并默认只纳入 `base_weight * tier_node_match_multiplier`。它不使用完整 `effective_weight`，也不包含事件节点级保底附加权重、短期压制倍率、随机扰动或同层级再随机结果。若后续确需纳入阶段可用性，应以 `phase_availability_multiplier` 这类稳定设计项进入，不得把临时运行时压制写入该质量。

未触发事件时：

```text
no_event_current_weight =
  max(
    0,
    no_event_current_weight
      - pool_occurrence_mass * pool_pity_decay_rate * active_hours
  )
```

若 `pool_occurrence_mass = 0`，表示当前没有真正可参与该池抽样的事件，不执行抽样，也不递减无事件权重。`no_event_current_weight` 降至 `0` 时，下一次存在可触发候选且未被速度状态压制的抽样必须产生本池事件提案。

第二段使用事件节点级附加权重：

```text
event_select_weight =
  effective_weight + event_pity_bonus_weight
```

事件级附加权重只参与第二段同池事件选择，不参与第一段候选池是否出事件。事件被实际接受并生成实例后，候选池级 `no_event_current_weight` 复原，已触发 `event_id` 的附加权重清零，同池中本次可选但未被触发的其它 `event_id` 按其可触发基础质量增加附加权重：

```text
event_pity_bonus_next =
  event_pity_bonus_weight
    + base_weight * tier_node_match_multiplier * event_pity_accrual_rate

event_pity_bonus_weight = event_pity_bonus_next
```

`event_pity_accrual_rate` 是事件节点级设计参数，而不是候选池全局常量。它控制该事件是否享受事件节点级触发累积：

| `event_pity_accrual_rate` | 含义 | 适用事件 |
| --- | --- | --- |
| `0` | 不累积事件级附加权重 | 高基础权重、常见、填充、容易形成重复感的事件 |
| `0-1` | 弱保底 | 中频事件或只需要轻度平滑的事件 |
| `1` | 按当前可触发基础质量完整累积 | 标准低频事件 |
| `>1` | 强保底 | 低权重但希望长期可见的稀有事件 |

首版不设置事件级附加权重累积上限。低权重事件在长期参与第二段选择但持续未触发时，`event_pity_bonus_weight` 会持续累积，并最终形成近似硬保底。高基础权重事件若不希望因自身基础权重大而快速累积附加权重，应将 `event_pity_accrual_rate` 设为 `0` 或低值。

伪随机状态示例：

```yaml
PoolPseudoRandomState:
  state_id: string
  pool_id: string
  semantic_bucket_ref: string
  subject_ref: character | party | route | node | sect | world | local_time_domain
  rng_cursor: string
  no_event_base_weight: number
  no_event_current_weight: number
  pool_pity_decay_rate: number
  last_pool_occurrence_mass: number
  last_trigger_world_time: string | null
  recent_trigger_suppression_until: string | null
  catchup_suppression_active: bool
  short_term_frequency_window_ref: string | null
  pressure_decay_policy: none | slow_decay | table | formula

EventPseudoRandomState:
  state_id: string
  pool_id: string
  event_id: string
  subject_ref: character | party | route | node | sect | world | local_time_domain
  rng_cursor: string
  event_pity_bonus_weight: number
  last_trigger_world_time: string | null
  recent_trigger_suppression_until: string | null
  catchup_suppression_active: bool
  pressure_decay_policy: none | slow_decay | table | formula
```

规则：

1. 硬移出候选池的事件不参与触发，也不累积伪随机状态。
2. 进入候选池但被冷却、重复、追赶、低可见性或预算策略压制的事件，可以降低第二段 `effective_weight`；是否继续更新候选池级保底状态和事件级附加权重由 `pressure_accumulation_policy` 决定，默认继续累积。
3. 触发后的短时间压制不应清空长期风险；压制期内第二段有效权重可以降低，但符合硬条件的池仍可更新候选池级保底状态。
4. C1 或其它时间追赶中的“事件不触发”复用同一压制逻辑：不实例化新的随机个人即时处理事件，不进入局部时停 / B1 / P0，但仍更新候选池级和事件节点级伪随机状态。
5. 追赶结束后不得回溯生成追赶区间内被压制的随机个人即时处理事件；累积的伪随机状态只影响后续常规结算、F1 采样或局部时间域采样。
6. 同一候选池在 N1、F1、后台追赶和局部时间域中应读取同一套 `PoolPseudoRandomState / EventPseudoRandomState`，避免 1 小时、1 天或多年区间因结算粒度不同而产生系统性偏差。
7. 候选池 / 语义桶级伪随机负责平滑同类事件总频率，既避免长期不出，也通过短期压制避免同一语义桶在短时间内过密出现。
8. 事件节点级伪随机负责避免低权重事件节点在长期符合条件、且多次参与同池第二段选择时永远不被抽中。
9. 常规权重随机命中产生 `weighted_hit` 提案；候选池级无事件权重降至 `0` 后命中产生 `bucket_pity_hit` 提案；第二段中携带 `event_pity_bonus_weight` 的事件被选中时，可产生或标记为 `event_pity_hit` 提案。三者都必须经过同一结算时间桶的事件层级裁决、同层级按 `event_select_weight` 加权再随机和限量规则。
10. 未选中的普通随机提案默认保留或衰减伪随机状态，具体由候选池策略决定；不得因为保底触发而一次性爆发多个事件。

### 5.7 通用事件流与危险率采样

事件流不是 F1 专属机制，而是任意结算区间内的事件发生模型。N1 可以用 1 小时区间，在线 F1 固定用 1 外界日区间，后台追赶 / Debug / 性能保护可以使用多日技术区间但必须切回外界日和断点，局部时间域可以用局部主观年或局部阶段区间。F1 批量结算中不逐小时全量掷骰，但事件不能被闭关承诺吞掉。事件触发方式包括：

1. 预定事件：宗门会议、洞天开放、市场刷新、行动完成，直接进入日历队列。
2. 阈值事件：资源耗尽、寿元低于阈值、心魔超过阈值、阵法燃料不足，计算 crossing time。
3. 危险率事件：闭关心魔、洞天异动、路途遭遇、宗门突发，以危险率采样下一触发时间。
4. 条件事件：进入某节点、携带某物、达到某境界、触发某关系后，在满足条件的区间内采样或排程。

F1 处理等级：

| F1 处理等级 | 是否退出 F1 | 处理方式 |
| --- | --- | --- |
| `silent` | 否 | 后台记录或仅影响数值，不打扰玩家 |
| `summary` | 否 | 写入 F1 摘要 |
| `auto` | 否 | 按玩家预设、托管策略或安全默认处理，并写入摘要 |
| `soft_interrupt` | 视情况 | 有预设或安全默认则自动处理并形成 F1 校验断点；无预设且无安全默认则退出 F1 到 N1 |
| `hard_interrupt` | 是 | 立即退出 F1，进入 N1 / B1 / P0 |

事件流采样后的处理口径：

| 采样结果 | F1 处理 |
| --- | --- |
| `silent / summary` | 写入后台记录或 F1 摘要，不形成断点 |
| `auto` | 按玩家预设、托管策略或安全默认处理，写入摘要，不形成断点 |
| `soft_interrupt` 有预设或安全默认 | 执行预设后作为 F1 校验断点，提交结果并重检是否继续 F1 |
| `soft_interrupt` 无预设且无安全默认 | 作为 F1 中断断点，退出到 N1 |
| `hard_interrupt` | 作为 F1 中断断点，立即退出到 N1 / B1 / P0 |

事件流必须保留采样随机种子、事件流引用、候选池状态、语义桶级和事件节点级伪随机状态、压制原因、日内结算分段、F1 校验断点、F1 中断断点和结果摘要，保证可复盘。

## 6. 配置表或根表

### 6.1 事件节点配置

```yaml
EventNode:
  event_id: string
  event_tier: tier_0 | tier_1 | tier_2 | tier_3 | tier_4 | tier_5
  base_weight: number
  event_pity_accrual_rate: number
  candidate_entries:
    - pool_id: string
      condition_ref: string | null
  play_type: info | choice | check | combat_clash | breakthrough_clash | settlement
  play_config_ref: string | null
  routes:
    - trigger: string
      target_event_id: string
  mvp_enabled: bool
```

字段口径：

1. `event_id` 是事件节点唯一索引编号，同一事件链中的选择、判定、交锋和结算端点都应拥有独立编号。
2. `event_tier` 用于事件与节点等级、境界阶段的匹配修正，不等于 F1 处理等级或结果强度。
3. `base_weight` 是该事件节点从候选池直接进入时的基础权重；链内节点和结算节点通常为 `0`。
4. `candidate_entries` 同时表达“能进入哪些候选池”和“在该池内是否有限制条件”。空列表表示只能从其它事件节点路由进入。
5. `play_type` 决定事件节点交给哪个玩法系统处理；多玩法事件必须拆成多个节点，通过 `routes` 串联。
6. `play_config_ref` 指向对应玩法配置。选项文本、检定公式、战斗配置、突破配置和结算效果都不进入事件节点根字段。
7. `routes` 定义事件链流转。结算节点可以没有后续路由。
8. `mvp_enabled` 用于首版内容开关，不改变事件链模型。

通用事件流可使用 `EventStream` 或等价配置：

```yaml
EventStream:
  stream_id: string
  scope: character | sect | node | market | world | local_time_domain
  applicable_states: list[string]
  settlement_cycle_scope: n1_hour | f1_outer_day | catchup_multi_day | local_time_domain | macro_period
  occurrence_model: scheduled | threshold | hazard_constant | hazard_table | hazard_formula | conditional
  candidate_pool_refs: list[string]
  base_rate_per_outer_day: number | null
  base_rate_per_inner_year: number | null
  batch_safety_limit: number | null
  pseudo_random_policy_ref: string | null
  catchup_suppression_policy: suppress_trigger_accumulate_pressure | suppress_and_no_pressure | none
  occurrence_resolution_policy_ref: string | null
```

`EventStream` 只定义采样周期、发生模型和参与采样的候选池，不重复定义事件来源、顶层类型、F1 处理等级或可见性。`batch_safety_limit` 只作为后台追赶、Debug 或性能保护用的技术保护阈值，不作为普通在线事件流的默认触发容量。后台追赶若使用更长技术批次，必须按在线 F1 的外界日边界、F1 校验断点或 F1 中断断点切分事件摘要和回放。`catchup_suppression_policy` 默认使用 `suppress_trigger_accumulate_pressure`，表示追赶期间不触发新随机个人即时处理事件但继续累积伪随机状态。

### 6.2 事件选项数值配置

`EventOptionNumericProfile` 是 `play_type = choice` 的一种 `EventPlayConfig`，定义选项成本、风险、收益、隐藏后患和路由触发名。

```yaml
EventOptionNumericProfile:
  option_id: string
  dimension: direct | unconventional | avoid | deconstruct | deceive | none
  availability_conditions: list[object]
  reveal_conditions: list[object]
  preferred_option_area: primary | overflow | auto
  time_cost_hours: int
  resource_input_refs: list[string]
  inventory_cost_refs: list[string]
  relationship_cost_profile_ref: string | null
  visibility_risk_profile_ref: string | null
  check_profile_refs: list[string]
  route_trigger: string
  outcome_level_floor: none | minor | standard | major | critical
  outcome_level_ceiling: none | minor | standard | major | critical
  reward_budget_profile_ref: string | null
  hidden_debt_tags: list[string]
  fail_tag_refs: list[string]
  preview_direction_tags: list[string]
```

五类维度的数值倾向：

| 维度 | 数值倾向 | 风险边界 |
| --- | --- | --- |
| `direct` 正面应对 | 作为事件基本解法，成本和收益最容易解释 | 条件不足时可退化为承受后果或直面失败 |
| `unconventional` 出奇制胜 | 可降低损耗、提高收益或改变事件处理模块、严重度或后续链 | 必须消耗稀缺条件、暴露能力或占用后手 |
| `avoid` 逃避推诿 | 降低即时风险和交互成本 | 常伴随奖励损失、声望下降、窗口错过或长期后果 |
| `deconstruct` 解构问题 | 改变问题成立前提，常降低事件严重度 | 失败时可能带来关系代价、越权风险或追责 |
| `deceive` 欺诈蒙骗 | 短期收益高、即时成本低 | 必须写入隐藏后患、暴露风险、追查标签或因果负担 |

常规选择事件中，每个维度最多生成 1 个候选选项。主选项区显示 1-3 个选项，超过 3 个时通过“...”进入溢出选项区；常规事件默认隐藏不可用选项。选项不直接引用后续事件，而是输出 `route_trigger`，由当前 `EventNode.routes` 解析到下一个事件节点。

### 6.3 奖励与预算

事件奖励、掉落、交易包、赔偿、宗门资源、秘境收益和后手相关资产必须接入世界产出预算、资源池或既有资产来源。

```yaml
EventRewardBudgetProfile:
  reward_profile_id: string
  reward_type: asset | resource | relationship | clue | window_access | sect_contribution | character_state | mixed
  allowed_tier_codes: list[string]
  allowed_quality_codes: list[string]
  budget_pool_refs: list[string]
  budget_value_cap: number | null
  locked_reward_policy: none | reserve_on_event_start | reserve_on_option_select | reserve_on_success
  fallback_when_budget_insufficient: downgrade | replace_with_clue | delay_refresh | create_locked_unavailable_state | trigger_contest_event | suppress_reward
  provenance_required: none | light | full
  log_level: normal | important | critical
```

预算规则：

1. 隐性候选生成不扣世界产出预算。
2. 资产进入玩家、宗门、NPC、市场、节点显性库存或事件锁定奖励时才扣预算。
3. 出售、拆解、销毁、上交、损坏或消耗不返还世界生成预算。
4. 预算不足时，不得凭空发放高价值奖励；应降品级、替换为线索、延迟刷新、生成“发现但暂不可取”的事件状态，或触发守护 / 争夺事件。
5. 高于当前阶段预算的资源只能来自先锋泄漏、剧情、强敌真实资产、正式后手、专属资源池、事件锁定奖励或明确高风险机会。
6. NPC 战利品、交易包和赠予不得在事件开始时临时生成完整库存，只能来自持久化资产、事件锁定奖励包或有预算来源的轻量资产包。

### 6.4 世界窗口频率配置

世界窗口事件是带期限的机会或危机状态，不是单独文本事件。

```yaml
EventWindowFrequencyProfile:
  window_profile_id: string
  window_type: secret_realm | node_crisis | breakthrough_resource | trade_opportunity | protection_offer | sect_assignment | custom
  region_id: string | null
  node_tag_requirements: list[string]
  stage_range: string
  min_duration_hours: int
  max_duration_hours: int
  visibility_policy: private_player | known_to_party | sect_visible | rumor_visible | public_world | hidden_world | debug_only
  active_cap_region: int | null
  active_cap_world: int | null
  cooldown_hours: int | null
  trigger_profile_refs: list[string]
  event_node_refs: list[string]
  resource_budget_refs: list[string]
  contest_policy: none | soft_contest | hard_contest | b1_contest
```

MVP 窗口范围：

```text
秘境窗口；
节点危机；
突破资源 / 名额窗口。
```

窗口开启、关闭、进入、错过、被争夺或被后手影响，都必须写入结果包和回放。窗口频率的最终数值尚未定；首版应优先验算“玩家是否能理解窗口存在、是否有时间介入、忽略后是否产生可解释世界变化”。

## 8. 调参验收口径

事件调参与实现验收至少检查：

1. 候选生成使用 `world_day / world_hour` 和结算区间，N1 可对应 `hour_tick`，F1、后台追赶和局部时间域必须保留区间起止、采样种子和回放桶，不读取 `quarter / tick` 旧字段。
2. 每个事件实例只派生一个 `top_level_type`；移动、节点、宗门、世界演化、控制权、传闻和专用链入口只作为来源或候选池入口统计。
3. 事件候选池可在 Debug 中展示候选、命中条件、移出条件、权重随机命中、语义桶级 / 事件节点级保底命中、提案裁决结果、压制原因、伪随机状态和稳定随机种子。
4. 同一语义事件在同一上下文中不会因 UI 刷新重复触发。
5. C1 或其它时间追赶期间不触发新的随机个人即时处理事件，但符合硬条件的事件池会复用压制逻辑并继续累积伪随机状态。
6. 个人即时处理事件最多产生 1 个当前角色局部时停阻塞。
7. 事件选项 1-3 个主选项加“...”溢出结构的分配结果可复盘。
8. `major / critical` 事件结果必须进入结果包、日志、回放和可见性审计。
9. 事件奖励必须能追溯预算、既有资产或事件锁定奖励来源。
10. 世界窗口事件开启、关闭、错过、进入和争夺都能写入结果包。
11. 普通玩家 UI 不显示完整候选权重、隐藏追查标签、Debug 日志或其他玩家私人事件归因。
12. F1 中资源耗尽、心魔、洞天异动、路途遭遇和宗门突发能通过通用事件流进入摘要、F1 校验断点或 F1 中断断点，不被闭关承诺吞掉。
13. 通用事件流结果可复盘采样随机种子、事件流引用、候选池状态、语义桶级 / 事件节点级伪随机状态、追赶压制、权重随机命中、保底命中、提案裁决、日内结算分段、F1 校验断点、F1 中断断点、F1 处理等级为 `auto` 的事件和中断原因。

## 9. MVP 范围

MVP 应实现：

1. `EventNode`、`EventCandidatePool`、`EventCondition`、`EventPlayConfig`、`EventRuntimeContext`、`PoolPseudoRandomState`、`EventPseudoRandomState`、`EventCandidateScore` 和候选池基础节流。
2. `world_day / world_hour / hour_tick` 与更长结算区间的时间口径和事件实例稳定随机种子。
3. C1 或其它时间追赶期间压制新随机个人候选，并对符合条件的候选池继续累积伪随机状态。
4. 个人即时处理事件的局部时停、默认处理和 C1 返回。
5. 同步处理事件中的正式交锋与突破挑战进入 B1，并拆分现实提交窗口、非参战世界推进和自身结算耗时。
6. 事件选项的 1-3 个主选项加“...”溢出结构。
7. `outcome_level`、`EventOutcome`、`ResultPackage` 和可见 / 隐藏 / Debug 日志分层。
8. 事件奖励接入预算、既有资产或事件锁定奖励来源。
9. 秘境窗口、节点危机、突破资源 / 名额窗口三类世界窗口事件。
10. 事件调试器展示候选、事件节点、进入条件、权重、权重随机命中、语义桶级 / 事件节点级保底命中、提案裁决、伪随机状态、压制原因、稳定随机种子、路由结果和结果包摘要。
11. 通用事件流基础配置、`silent / summary / auto / soft_interrupt / hard_interrupt` 五级和批量摘要输出。

MVP 不实现：

1. 完整事件文本库。
2. 最终事件概率表和所有候选基础权重。
3. 全部世界窗口事件类型和长期频率表。
4. 完整 `outcome_level` 到资源、伤势、关系、节点和传闻强度的量化表。
5. 隐藏后患追查、衰减、暴露和传闻生成的完整细表。
6. active major 世界事件的完整阶段推进策略。
7. 候选池回放文件导出。
