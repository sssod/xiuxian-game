## 13. 建议执行协议

### 第一步：建立覆盖矩阵

在开始大规模编辑前，把集中记录每个编号映射到：

```text
当前是否有效
被何编号替代（如有）
详细权威目标文档
需要摘要同步的文档
是否仍有待裁决字段
```

矩阵可以作为临时工作笔记，不必进入正式包；但不得跳过这一步直接批量复制。

### 第二步：按专题回写

一次只处理一个专题批次。每完成一批：

1. 直接检查目标正文；
2. `rg` 检查该专题旧术语；
3. 检查包内链接；
4. 运行 `git diff --check`；
5. 确认旧正式包 diff 为空；
6. 再进入下一批。

### 第三步：更新入口层

详细专题稳定后再更新：

- 核心摘要；
- 专题权威映射；
- P0 / P1 阶段门状态；
- 总索引状态；
- README 阅读顺序与维护记录；
- 必要的新专题链接。

不要先把核心入口扩写成长文，再去补专题。核心只能保留局级摘要。

### 第四步：处理集中记录

集中记录在全部回写和验收前不得删除。完成后：

1. 保留它作为本轮裁决审计账本，或按用户后续指令归档；
2. 可以增加“已回写到”状态索引，但不得擅自删除历史裁决；
3. 若用户要求收束，再生成下一份 handoff；
4. 不把集中记录继续当成未来长期详细规则的唯一维护位置。

## 14. 验收标准

整理完成必须同时满足：

1. 集中记录中的每个当前有效编号都有明确专题归属；
2. 较早失效规则未作为当前规则残留在专题正文；
3. 核心摘要与专题正文不冲突；
4. 阶段门状态反映已经关闭的大模块，不再把已裁决内容列为完全缺失；
5. 新包不依赖原 handoff、旧包或 inbox 才能解释规则；
6. 新包内链接全部有效；
7. 没有修改旧正式包；
8. 没有修改治理文件、代码或来源草案；
9. 没有丢失工作区原有修改；
10. 未决内容被显式保留，没有静默默认；
11. `git diff --check` 通过；
12. 对未跟踪集中记录与本 handoff 进行了直接内容检查，而不只依赖 Git diff。

建议最终检查：

```text
git status --short
```

对 `rg` 命中逐条判断：维护记录、历史说明或明确失效段可以保留；活跃规则必须修正。
