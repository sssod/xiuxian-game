# 系统设计｜资源槽附属设施通用规则

## 1. 设计定位

资源槽附属设施是建立、维护或运营在合法资源槽上的功能形态。设施和建筑不是与资源并列的第二套槽位；它们必须能追溯到资源槽、节点隐藏层或明确的节点承载记录。

本文负责维护设施的通用字段、设施类别、一槽一设施类别、建设、维护、升级、改造和交通 / 市场 / 宗门公共设施的挂载规则。修炼加成、洞天福地、个人洞府和藏宝等专题文档可以在本文规则之上继续细化。

## 2. 当前结论

1. MVP 阶段，能建造、升级、运行或维护的生产、修炼、加工、防护、交通、市场、宗门行政等设施，必须附属于合法资源槽或由专题文档声明的合法隐藏层承载记录。
2. 同一个资源槽同时只能承载一类设施。设施的规模、等级、维护状态和产能可以变化，但设施类别不能在同一槽内并存。
3. 资源槽模板声明可建设施类别、初始规模上限、最终规模上限和升级条件；节点等级可提高或压低这些上限。
4. 设施效果必须通过行动、权限、资源消耗、资产流水和结果包进入结算，不能作为无来源全局倍率。
5. 更换设施类别必须走拆除、迁移、废弃、污染修复或事件改造流程。

## 4. 核心循环或触发入口

设施由建设行动、宗门持续行动、事件结果、节点模板、旧设施遗留、洞府 / 藏宝设置、交通建设或特殊机会窗口生成。

设施运行循环：

```text
建设或接管设施
→ 校验资源槽类别、规模、权限、占用、改造口径和建设材料
→ 写入设施实例、资源槽占用和资产流水
→ 按 world_hour 维护设施状态、产能、损坏、封锁或停摆
→ 输出 facility_delta、resource_slot_delta、ledger_entries、rumor_entries 和日志
```

## 5. 规则与状态

设施实例建议最少表达：

```yaml
FacilityState:
  facility_id: string
  node_id: string
  resource_slot_id: string | null
  hidden_layer_id: string | null
  facility_class: string
  facility_template_id: string
  owner_faction_id: string | null
  owner_character_id: string | null
  controller_ref: string | null
  facility_scale: int
  facility_level: int
  facility_scale_cap: int
  status: planning | active | idle | damaged | locked | abandoned | contested | dismantling
  maintenance_state: normal | underfunded | overloaded | polluted | sealed | offline
  permission_policy: object
  input_refs: list[string]
  output_refs: list[string]
  result_package_refs: list[string]
  last_updated_world_day: int
  last_updated_world_hour: int
```

设施字段口径：

| 字段 | 含义 |
| --- | --- |
| `resource_slot_id` | 常规设施必须绑定的资源槽；专题文档允许隐藏层承载时才可为空 |
| `hidden_layer_id` | 洞府、藏宝、隐藏入口等由专题规则允许的隐藏层承载 |
| `facility_class` | 设施类别，一槽一类别约束读取该字段 |
| `facility_scale` | 当前设施规模 |
| `facility_level` | 当前设施等级 |
| `facility_scale_cap` | 所在资源槽和模板共同限制的设施规模上限 |
| `status` | 设施生命周期和可用状态 |
| `maintenance_state` | 维护、污染、超载、封禁或离线状态 |
| `permission_policy` | 使用、建设、维护、拆除、进入和收益权限 |
| `input_refs` / `output_refs` | 资源投入、库存、产出、加工或行动结果引用 |

MVP 设施类别可先按功能大类维护：

| 设施类别 | 常见承载资源槽 | 主要功能 |
| --- | --- | --- |
| `cultivation` | `aura_node`、模板允许的 `space_site`、受限 `blessed_land` | 修炼房、静室、聚灵阵、突破场地、护法阵 |
| `production` | `aura_node`、`material_deposit`、`ecology_site` | 灵田、药园、采矿场、狩猎营地、驯养栏 |
| `processing` | `aura_node`、`material_deposit`、`space_site` | 炼矿、炼丹前置、灵石 → 聚灵石等加工 |
| `defense` | `aura_node`、`space_site`、`special` | 阵法、防护、封禁、看守点 |
| `transport` | `aura_node`、`space_site`、`special` | 传送阵、渡口、关隘、入口维护 |
| `market` | `aura_node`、`space_site`、`special` | 坊市、店铺、摊位、交易入口 |
| `sect_administration` | `aura_node`、`space_site`、`special` | 宗门大殿、执事处、库房入口、清点与权限管理 |
| `personal_cave` | 模板允许的自然资源槽或隐藏层 | 个人洞府、闭关、储物、防护、隐蔽 |
| `personal_cave_complex` | 模板允许的自然资源槽、宗门设施群或隐藏层 | 宗门分配洞府区、批量洞府单元 |
| `treasure_cache` | 模板允许的自然资源槽或隐藏层 | 普通藏宝、封存储物、一次性取出 |
| `preserve_or_seal` | `blessed_land`、`special` | 洞天福地保全、封禁、参悟、入口维护 |

设施附属规则：

1. 同一个资源槽同时只能承载一类设施。设施规模、等级、维护状态和产能可以变化，但设施类别不能在同一槽内并存。
2. 资源槽模板声明可建设施类别、初始规模上限、最终规模上限和升级条件；节点等级可提高或压低这些上限。
3. 更换设施类别必须走拆除、迁移、废弃、污染修复或事件改造流程，不能直接把已建灵田瞬间改成矿场、传送阵或市场。
4. 不易改造资源槽可以禁止常规建设，只允许封禁、维护、参悟、争夺、探索或机会窗口类操作。
5. 交通设施、坊市入口、宗门行政建筑等不依赖自然产出的公共设施，也必须绑定到 `aura_node`、`space_site` 或 `special` 等广义资源槽，不能绕过资源槽规模限制。
6. 设施的维护、人力、材料、权限和产出必须写入资产流水、节点日志或宗门可见摘要。
7. 停摆、封锁、污染、损坏、失守、废弃和争夺必须能反向影响资源槽占用、路线条件、产出和 UI 可见摘要。

## 6. 资源、角色、地图、事件或 NPC 接口

| 接口 | 设施读写内容 |
| --- | --- |
| 资源槽 | 读取可建设类别、规模上限、当前占用、改造口径、灵气和特殊属性 |
| 路线 | 传送阵、渡口、关隘等设施可改变 `RouteState.requirements`、`passability`、`risk_tags` 和 `current_cost_hours` |
| 经济 | 设施产出进入资源池、节点库存、宗门库存、事件锁定库存或合法资产容器 |
| 修炼 / 突破 | 修炼设施输出环境修正、资源输入接口、席位、护法和突破场地条件 |
| 事件 | 设施可作为事件入口、封锁目标、争夺目标、破坏目标或机会窗口来源 |
| 宗门 | 宗门设施读取建设权、维护来源、清点权、收益权和权限政策 |
| 洞府 / 藏宝 | `personal_cave`、`personal_cave_complex`、`treasure_cache` 读取专题文档的资产和开启规则 |

## 8. UI 展示边界

普通 UI 可展示设施名称、类别、规模、等级、状态、维护摘要、权限摘要、产出摘要、是否占用资源槽、是否阻塞改造和可见风险。普通 UI 不显示隐藏层真实归属、其他玩家私人建设来源、未公开库存、`hidden_world` 或 `debug_only` 信息。

## 9. MVP 范围

MVP 应实现：

1. 设施绑定资源槽或专题允许的隐藏层承载。
2. 一槽一设施类别。
3. 设施规模、等级、维护状态、权限和产出引用。
4. 建设、维护、升级、拆除、迁移、废弃和事件改造的最小状态。
5. 交通、市场、宗门行政等公共设施不得绕过资源槽规模限制。

MVP 不实现：

1. 同一资源槽多类设施堆叠。
2. 无来源全局倍率设施。
3. 不记录资产流水的设施产出。
4. 常规人工扩展直接制造洞天福地、秘境入口、矿脉或灵泉。

## 10. 验收约束

1. 资源槽附属设施遵守一槽一设施类别、单槽规模上限、等级调整和维护状态。
2. 若一个资源槽已有设施、个人洞府或普通藏宝占用，其他设施建设必须失败，直到完成清理、迁移、拆除或事件处理。
3. 传送阵、渡口、关隘等公共交通设施必须有资源槽或合法隐藏层承载，并能被路线读取。
4. 设施效果必须通过行动、权限、资源消耗、资产流水和结果包进入结算。
5. 设施变化进入结果包和回放。

## 11. 待裁决与待补

| 项目 | 当前口径 | 需要裁决或补充 |
| --- | --- | --- |
| 设施模板表 | 已确定 MVP 设施大类 | 需要补各类设施模板、建设条件、规模上限、升级条件和维护项 |
| 维护成本 | 要求写入资产流水 | 需要补材料、人力、灵石、聚灵石、宗门资源等成本公式 |
| 设施产能 | 由资源槽规模、设施规模、等级、维护和权限决定 | 需要补产能公式与数值验算 |
| 设施替换流程 | 需要拆除、迁移、废弃、污染修复或事件改造 | 需要补每类替换的耗时、损失和日志 |

旧口径迁移：

| 旧口径或冲突点 | 当前采用口径 | 裁决原因 |
| --- | --- | --- |
| 同一资源槽堆叠多类建筑 | 同一资源槽只能建造一类设施，规模和等级可变 | 避免一个灵气节点同时无限承载修炼房、炼丹房、矿场和市场，破坏地图资源稀缺性 |
| 设施和建筑作为独立建筑槽 | 设施必须追溯到资源槽、节点隐藏层或专题文档声明的承载记录 | 设施效果需要来源、规模和维护约束 |
| 公共设施不依赖资源槽 | 交通、坊市入口、宗门行政等公共设施也必须绑定广义资源槽或合法隐藏层承载 | 避免绕过资源槽规模和地图稀缺性 |
