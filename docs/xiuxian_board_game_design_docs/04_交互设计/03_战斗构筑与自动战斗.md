# 交互设计｜战斗构筑与自动战斗

适用范围：战前招式构筑、自动释放顺序、战斗状态、逃遁、连续战斗和战后结果的玩家可见信息。本文不规定战斗画面的节点布局与视觉表现。

## 1. 构筑入口

战斗构筑需要让玩家看见四类来源：

1. 当前主修道功的已解锁招式；
2. 最多 `5` 个已装配法门招式；
3. 攻击法宝招式；
4. 防御法宝招式。

飞遁法宝只显示常驻被动和逃遁加成，不进入循环招式列表。法宝炼化度不高于 `50` 时，其加成和招式必须明确标为未生效。

所有有效来源合并为一个玩家手动排序的列表。排序从左到右表示同一角色多个招式同刻可用时的尝试优先级，而不是一次性施放序列。

## 2. 招式条目必须解释的内容

每个招式至少需要表达：

- 来源与当前解锁 / 装配状态；
- 基础冷却和当前冷却；
- 元气消耗或自损成本；
- 伤害、护盾或 Buff 类型；
- 当前受掌握阶段或法宝炼化影响后的有效数值；
- 无法释放时的条件原因。

知识来源招式读取掌握阶段倍率；法宝招式不读取知识掌握倍率。涉及固定元气损伤与吸收时，应分别展示固定损伤 `D` 与吸收比例 `K3`，避免玩家误解为同一个百分比效果。

## 3. 自动战斗时间轴

开战后全部冷却招式先等待一次完整基础冷却。战斗中应持续展示：

- 双方生机、元气、神念；
- 只保护生机的当前护盾；
- 招式剩余冷却；
- 当前 Buff 层数与共享持续时间；
- 战斗已用时间与 `60` 秒上限；
- 下一次允许逃遁尝试的时间。

招式资源不足、条件不成立或没有合法目标时会被跳过且不阻塞右侧。元气不足的已就绪招式保持等待。反馈应区分“仍在冷却”“等待资源”“条件不成立”和“本次扫描被跳过”。

双方同刻触发的相对先后由战斗随机种子决定。界面只需让结果可追溯，不需要向玩家暴露种子本身。

## 4. 伤害、护盾与 Buff 反馈

单次直接伤害至少应能展开查看：

```text
有效修为与自损形成基础威力
→ 通用增伤 / 减伤 Buff
→ 生机伤害先扣护盾，或神念伤害绕过护盾
→ 目标属性减伤
→ 最终属性变化
```

护盾每场从 `0` 开始且战后清空，连续战斗也不继承。多个护盾来源相加；受到伤害时优先消耗剩余持续时间最短的来源。

可变数值 Buff 最大 `1` 层，新值无条件替代旧值并刷新共享持续时间，不比较来源或强弱。普通可叠层 Buff 需要展示当前层数、最大层数和共享剩余时间。

## 5. 逃遁操作

普通逃遁是无需装配的通用能力，每 `5` 秒可尝试一次；渡劫战斗禁止逃遁。按钮或操作入口至少展示：

- 当前是否允许尝试；
- 冷却剩余；
- 按大境界差得到的基础率；
- 飞遁法宝经炼化缩放后的百分点加成；
- 最终成功率，最高 `100%`。

失败后所有招式当前剩余冷却增加 `1` 秒，必须同步反映在冷却显示中。每次尝试独立判定，不显示失败累计补偿。

## 6. 结束、连续战斗与结果

生机归零为死亡，神念归零为重伤，`60` 秒到时为平局。元气归零本身不结束战斗。

多人连续战斗要展示当前参战顺序、保留的生机 / 元气 / 神念 / 持续状态，以及每场重置的护盾。中间不结算死亡掉落；整段结束后才显示最终胜者、每件独立判定的战利品和系统回收结果。

平局应明确说明双方无胜负、相关行动失败、目标无人获得且不能开始飞升，不能只显示“超时”。

## 7. MVP 缺口

首批招式与敌人配置、基础冷却、成本、`C1/C2/K1_ref`、战斗日志颗粒度和高速 / 跳过表现尚未完成。交互层可以先固定信息职责，但不得在正式数值配置前伪造具体战斗预览值。
