# 系统设计｜宗门系统设计

## 1. 设计定位

宗门是玩家长期成长的平台、组织资源入口和沙盒世界演化主体，但不是玩家本体，也不变成玩家直接排程的城市建设面板。

宗门系统负责身份、职位、贡献、门内声望、资源申请、库存预留、常规运营指令、宗门持续行动、宗门日志、NPC 协作，以及宗门对地图节点、资源槽和世界演化的影响。

宗门库存底层容器规则由《库存系统》（`06_储物空间系统设计/03_库存系统.md`）维护；宗门内商店买卖规则由《交易系统》（`03_经济系统设计/04_交易系统.md`）维护；宗门页面表达由《宗门页面设计》（`../04_交互设计/08_宗门页面设计.md`）承接。本文只维护宗门层面的组织规则、权限边界、资源申请、预留、常规运营、支出、审计和可见性。

## 2. 当前结论

1. 宗门是组织资源平台与世界演化实体；玩家死亡或转世后，宗门仍可由 AI 托管并继续演化。
2. 每个宗门同一时间最多只有一个 active `SectContinuousActionState`，代表宗门当前需要组织取舍的重点持续行动。
3. 常规运营指令是高层 / 职位玩法入口，用于调整日常运营策略、预算倾向、权限归属和常态资源使用边界；它不占用个人行动队列，也不占用宗门唯一持续行动槽。
4. 宗门发放资源必须来自真实库存或合法预留；贡献、职位、声望、关系和身份只影响申请资格、审批优先级与权限，不允许绕过库存检查。
5. 常规运营指令必须延迟到宗门运营生效窗口校验并生效，避免即时切换权限、抢占库存、绕过 NPC 协作或制造多人冲突。
6. MVP 阶段角色和 NPC 同时只能有一个明确所属组织，该所属组织为宗门或空；家族、帮派、商会、王朝官署等非宗门组织不进入 MVP。
7. 宗门库存、宗门职责、洞天席位、宗门时间阵、宗门会议和资源审批读取外界日历；玩家洞天内主观时间不刷新宗门资源。
8. 低风险宗门职责可作为 F1 候选，宗门重大事件、公共决策、席位争夺和资源归属冲突应中断 F1。

## 4. 核心循环或触发入口

宗门系统的玩家入口主要来自宗门页面、行动指令、事件选项、突破准备、宗门任务、NPC 关系和地图节点事务。

核心循环：

1. 角色获得或失去宗门身份、职位、权限、贡献和门内声望。
2. 玩家或 NPC 根据身份和职位发起资源申请、宗门任务、常规运营指令、权限委托或宗门持续行动建议。
3. 系统检查宗门库存、已有预留、节点状态、宗门当前持续行动、事件压力、NPC 支持和宗门 AI 策略。
4. 宗门生成批准、部分批准、拒绝、待生效、覆盖、过期或撤销结果，并写入宗门审计日志与结果包。
5. 资源进入合法容器、行动输入、事件支持、突破支持、设施时段或导师 / 护法支持；未消耗资源按规则释放、过期或失败。
6. 宗门持续行动、常态运营、节点控制、库存维护、任务派发和事件反馈继续改变宗门库存、节点状态、成员机会和世界传闻。

关键中断点：

1. 权限失效、职位变化、宗门状态变化、库存不足或资源已被预留。
2. 事件中断、节点压力变化、宗门 AI 安全边界拒绝或高权限覆盖。
3. 多人房中其他玩家已先占用同一资源、同一窗口或同一职责范围。
4. 行动开始前、事件选项生效前、突破轮消耗前或运营生效窗口前的复校验失败。

## 5. 规则与状态

### 5.1 组织形态边界

1. 宗门与家族属于同级组织概念；家族不是宗门下级组织，也不是宗门之后的备用归属。
2. MVP 阶段不开发家族、帮派、商会、王朝官署等非宗门组织。
3. 文档中保留的 `faction_ref`、`owner_faction_id`、`controlling_faction_ref` 等泛组织字段仅为未来扩展占位；MVP 运行规则不得据此生成第二所属组织或非宗门组织系统。
4. 宗主、掌门、太上长老等多权限主体可作为 NPC 高层或后续阶段扩展职位存在；MVP 不开放玩家宗主。

### 5.2 身份、职位与权限

MVP 身份序列：

```text
外门弟子 → 内门弟子 → 真传弟子 → 执事 → 长老
```

M3 或第三大境界起点后进入长老序列或等价高层决策体验。身份层级含义：

1. 外门弟子：入门身份，主要获得基础功法、基础任务、最低宗门保护和个人资源申请入口。
2. 内门弟子：稳定修行身份，解锁更好的修炼设施、任务层级和宗门关系入口。
3. 真传弟子：重点培养身份，可接触高价值资源、护法、突破名额、核心任务和部分建议权。
4. 执事：组织执行层，可管理局部资源、节点事务、任务分派或低到中级运营指令。
5. 长老：宗门高层，可管理更完整的库存、预留、培养方向、节点控制、护法支持和重大运营指令。

权限可来自宗门身份、具体职位、门内声望、贡献记录、关键 NPC 支持、特殊事件授权、高层权限委托或收回。

权限标签示例：

```text
request_resources
use_training_site
request_breakthrough_support
lead_task
access_inner_archive
manage_node_affairs
assign_guard_or_support
view_sect_inventory_summary
view_resource_reservations
submit_operation_suggestion
issue_operation_command
manage_operation_authority
view_operation_audit
```

贡献是历史凭证，不是货币。门内声望是宗门内部对可靠性、潜力与影响力的综合评价。资源申请可读取贡献与声望，但最终仍必须校验真实库存、权限、地点和宗门当前状态。

### 5.3 权限委托

1. 多权限主体可以将某一类运营权限设为由具体职位负责人自行决断，例如让执事堂负责人调整低阶任务派发，让药园执事调整药田维护优先级。
2. 权限委托对象是职位或职责范围，不是玩家账号本身；同一规则可由玩家角色、NPC 或多人房中的其他玩家角色持有。
3. 设置、转移或收回权限即时生效：新负责人立即获得提交或审批资格，被收回者立即失去提交新指令、审批新指令和查看超出权限细节的资格。
4. 权限变化不即时改写已经生效的运营结果；运营指令的实际更新仍按延迟生效规则进入下一次运营生效窗口。
5. 未到生效窗口的待生效运营指令必须在生效前重新校验权限。提交者或职位在生效前失去对应权限时，该指令转为 `rejected`、`expired` 或待新负责人复核。

### 5.4 宗门资源与库存

宗门追踪五类抽象资源：

1. 灵石。
2. 修炼资源。
3. 材料 / 矿材。
4. 人力 / 弟子规模。
5. 声望 / 影响力。

宗门库存可包含灵石、丹药、灵材、符箓、法器、完整功法载体、残页 / 章节、任务物、节点产出资源、宗门遗产清点接管物、宗门个人洞府清点物、突破支持资源、设施时段与导师支持名额。

库存规则：

1. `SectInventory` 是宗门侧库存摘要，底层物品持久化仍由资产容器与物品系统承载。
2. `sect_reputation` 是宗门整体资源口径，不等同于节点影响力。
3. `manpower` 是组织人力规模，不是可放入行囊的物品。
4. 抽象资源在需要成为具体道具、奖励、突破资源或后手封存物时，再由物品系统实例化。
5. 世界产出预算只提高宗门资源可得性，不自动批准玩家申请。
6. 宗门资源成熟、库存刷新、宗门时间阵开放、洞天席位和审批窗口读取外界世界日历，不读取角色在洞天内经历的主观年。
7. 高于当前预算境界的宗门资源默认不稳定生成，除非来自先锋泄漏、宗门重大事件、宗门自身专属资源池或已完成清点的合法遗产接管。
8. 遗产接管只适用于有原持有人且需要分配、继承、清点或回收的资产，例如 NPC 死亡后的随身物品、NPC 洞府库存、宗门管辖个人洞府库存、宗门托管 / 职务资产。

### 5.5 宗门资源来源

MVP 来源：

1. 控制节点的基础产出。
2. 宗门持续行动结果。
3. 玩家上交资源。
4. 节点来源事件奖励。
5. 宗门声望带来的外部供给。
6. 特殊秘境、机会窗口或隐藏层。
7. 宗门个人洞府清点、NPC 死亡后的宗门相关遗产接管、宗门托管 / 职务资产回收。
8. 宗门商店、资源槽附属设施、部门或生产链产出。

所有来源都应进入 `sect_storage`、宗门库存摘要、审计日志或结果包，不应直接表现为玩家无来源获得物品。

宗门建设和生产必须读取地图资源槽。MVP 阶段同一资源槽只能建设一类设施；宗门可以升级设施规模、等级和维护状态，但不能在同一资源槽上叠加多类产出设施。设施规模上限由资源类型、资源品级、节点等级、地形、控制权和特殊事件决定。

宗门不能把宗门外个人洞府、普通藏宝或真灵藏宝直接写成宗门资源来源。宗门外个人洞府和普通藏宝是无主遗留设施，必须满足钥匙、功法、线索、位置、事件条件或破阵结果后才能进入 / 取出；真灵藏宝作为正式后手由同一真灵跨世感应和开启，受设置数量和单个容量限制，不进入遗产分配、继承或回收。

### 5.6 宗门资源支出

MVP 支出：

1. 发放弟子培养资源。
2. 支持玩家或 NPC 突破。
3. 宗门持续行动消耗。
4. 节点建设与修复。
5. 驻守、远征、探索的人力占用。
6. 应对节点危机。
7. 维护宗门核心建筑、节点公共设施或资源槽附属设施。
8. 发放俸禄。
9. 宗门内商店、任务奖励和设施支持。

宗门俸禄口径：

```text
境界基数 + 职位绝对值
→ 宗门财政状态修正
→ 最终发放额
```

所有宗门采用同一套基础标准，宗门财政状态只作为发放修正。俸禄进入角色随身资产或合法个人容器时，必须写入资产流水。

### 5.7 资源申请

资源申请可以作为 `Command.command_type=apply_resource`，也可以作为事件选项进入系统。

申请流程：

```text
贡献 / 门内声望 / 身份 / 权限 / 请求用途
→ 是否允许申请
→ 检查宗门库存与既有预留
→ 检查宗门当前行动、节点压力、事件状态和 NPC 支持
→ 生成资源预留、部分批准、拒绝或过期
→ 写入宗门审计日志与结果包
```

审批依据：

1. 身份与职位。
2. 贡献。
3. 门内声望。
4. 库存与预留状态。
5. 宗门当前持续行动。
6. 关键 NPC 支持。
7. 节点压力。
8. 事件状态。
9. 请求用途。
10. 公开影响。
11. 宗门 AI 策略。

资源申请通过后：

1. 高价值资源应生成资源预留。
2. 丹药、灵材、符箓等在进入个人行动或事件选项时，必须作为行动资源输入消耗。
3. 设施时段、导师指点、护法支持进入行动、事件或突破模板修正，并记录来源。
4. 行动开始或事件选项生效前仍需执行前校验。
5. 消耗、释放、过期和拒绝都必须写入宗门审计日志与结果包。

### 5.8 资源预留

资源预留用于避免宗门库存被多系统重复使用。

预留规则：

1. 被预留资源不能被宗门持续行动、商店售卖、其他玩家申请或事件奖励重复消耗。
2. 预留可以绑定角色、命令、事件或系统用途。
3. 预留到期、行动失败、请求撤销、宗门状态变化或事件中断时，应释放、过期或失败。
4. 资源预留结果默认只对本人、相关宗门权限层和 Debug 可见。
5. 多人房中，宗门库存被申请会影响其他玩家机会，但不直接公开私人申请详情。

示例：玩家申请突破支持后，宗门同意预留一批修炼资源。突破开始则消耗；事件取消则释放、过期或部分损耗。

### 5.9 宗门内商店与资源申请边界

宗门内商店和资源申请是两条路径。

| 路径 | 支付 / 判断 | 来源 | 结果 |
| --- | --- | --- | --- |
| 宗门内商店购买 | 灵石、价格、身份折扣、货架权限 | 宗门商店 `shop_stock` | 物品进入行囊或合法库存 |
| 宗门资源申请 | 身份、贡献、声望、用途、审批、真实库存 | 宗门库存 `sect_storage` | 预留、行动资源绑定、事件支持或拒绝 |
| 上交宗门 | 宗门需求程度、物品价值、事件状态 | 玩家行囊或合法来源库存 | 资产进入 `sect_storage`，角色获得贡献、声望或权限修正 |

宗门内商店的买卖、出售物保留和店铺库存规则见《交易系统》（`03_经济系统设计/04_交易系统.md`）。资源申请、预留、消耗和审计以本文为准。

### 5.10 宗门持续行动

每个宗门同一时间最多拥有一个 active `SectContinuousActionState`。

持续行动类型：

```text
开采 / 资源介入；
驻守 / 控制强化；
探索；
远征；
建设；
培养。
```

宗门持续行动可以改变宗门库存、节点资源、资源槽附属设施状态、节点公共设施状态、宗门影响力、控制权事件、玩家贡献与声望、秘境窗口、宗门遗产清点结果或宗门外洞府 / 普通藏宝等无主遗留设施的线索窗口。

宗门持续行动消耗必须来自宗门库存、资源预留、节点资源、抽象人力或事件明确提供的输入，不得绕过库存与预留。

常态运营不占用唯一持续行动槽：

```text
已控制矿场 / 药田的基础产出；
已建成基础设施的稳定效果；
已建立驻守状态的持续安全修正；
宗门俸禄或基础供给；
宗门库存维护；
已完成培养体系的基础弟子成长；
宗门商店基础补货倾向；
常规任务派发与低阶人力轮换。
```

这些内容仍按 `world_hour` 或宗门运营结算窗口常态结算，但不得被计为第二个 `SectContinuousActionState`。

低风险宗门职责可作为 F1 eligible state，例如驻守、低风险资源看护、宗门日常事务、低风险加工或疗养护持。宗门重大事件、公共决策、洞天席位争夺、资源归属冲突、叛宗、强 PvP 或会决定他人利益的公共选择必须退出 F1 或进入 P0 / B1。

### 5.11 宗门常规运营指令

常规运营指令是职位权限对宗门日常运转参数的调整，不是宗门主行动输入，也不是个人行动队列。它允许玩家在安排自己角色的普通行动队列之外，参与宗门更细节的运营。

可覆盖的运营范围：

1. 资源预算倾向：培养、维护、驻守、商店、突破支持、任务奖励之间的低到中级预算比例。
2. 库存与预留政策：低阶资源保底线、高价值资源申请门槛、过期预留释放策略、商店补货优先级。
3. 节点与设施维护：已控制资源槽、公共设施、宗门核心建筑的维护优先级和风险阈值。
4. 人力与职务安排：驻守轮换、低阶任务分派、护法名额、导师时段、执事职责范围。
5. 培养与招收倾向：弟子培养方向、低阶功法开放范围、重点培养名额倾向。
6. 情报与档案访问：不同身份能看到的库存摘要、节点摘要、宗门日志和档案层级。
7. 常规危机响应：节点压力、库存短缺、外部威胁或设施损坏时的默认处理优先级。

不得通过常规运营指令直接完成的事项：

1. 发起第二个宗门持续行动。
2. 绕过宗门库存、预留、位置、权限、节点状态或事件状态校验。
3. 即时转移高价值资源给玩家、NPC 或私人容器。
4. 直接迫害同宗玩家、锁死其他玩家长期体验或泄露私人事件归因。
5. 替玩家角色移动、战斗、修炼、突破或处理需要亲自到场的事件。
6. 把个人即时处理事件选项、正式交锋轮内策略或突破挑战轮内选择预先写成自动脚本。

延迟生效规则：

1. 常规运营指令提交后先进入 `pending_effective`，只记录意图、权限来源、目标范围和预计影响。
2. 指令在下一个宗门运营生效窗口统一校验并生效。MVP 默认生效窗口为下一个宗门日结窗口；若需要更细粒度，可配置为固定 `sect_operation_command_delay_hours`，但不得同小时即时生效。
3. 生效前必须重新校验职位、权限、宗门库存、已有预留、节点状态、事件状态、其他待生效指令和宗门 AI 安全边界。
4. 校验失败时，指令不得部分偷跑；只能生成拒绝、过期、等待复核或被上级新指令覆盖的结果。
5. 高权限主体可以提交覆盖指令，但覆盖指令本身仍延迟生效。权限收回可以即时阻断资格，但不能即时制造一个新的运营结果。
6. 同一职责范围在同一生效窗口存在多条互斥指令时，按有效权限、职位负责人、上级覆盖、提交时间、门内声望、贡献记录和宗门 AI 安全边界裁定。
7. 指令生效后只改变后续常态运营参数，不回滚已经完成的库存消耗、事件结果或玩家个人行动结果。

协作规则：

1. 玩家与 NPC 使用同一套职位、权限、待生效指令和审计日志。
2. NPC 负责人可以按宗门 AI 策略提交运营指令；玩家负责人可以提交显式指令；双方冲突时按权限委托、职位范围和宗门 AI 安全边界处理。
3. 多人房中，同宗玩家不走强制投票。玩家之间的运营协作通过职位负责人、上级覆盖、权限委托、资源申请、个人行动、事件结果和可见日志表达。
4. 同一职位若允许多名角色共同持有，必须有一个当前负责人或明确的复核规则；否则只能作为建议来源，不能自行决断运营指令。
5. 运营指令只公开到对应权限层。无权限成员可看到公开结果或传闻，但不能看到完整库存、私人申请、隐秘后手或其他玩家的私人归因。

### 5.12 日志与可见性

宗门输出日志分层：

```text
本人可见；
宗门成员可见；
权限层可见；
公开传闻；
隐藏世界日志；
Debug 日志。
```

可见性规则：

1. 宗门库存变更、资源申请结果、功法载体发放、NPC 支持、交易、护法、导师指点和设施支持来源都应可回放。
2. 常规运营指令应记录待生效、已生效、被覆盖、被拒绝、过期和撤销状态。
3. 权限层可见信息应包含生效窗口、提交者职位、权限来源、影响范围和权限层可见的校验摘要。
4. 权限委托与收回应即时反馈；对应运营指令仍显示其自身的待生效或失效结果。
5. 私人申请、隐秘后手、其他玩家私人归因和 Debug 级完整库存不得对普通成员公开。

## 8. UI 展示边界

普通宗门页面应展示：

1. 宗门概览、身份、职位、权限标签、贡献和门内声望摘要。
2. 宗门五类抽象资源：灵石、修炼资源、材料 / 矿材、人力 / 弟子规模、声望 / 影响力。
3. 宗门库存详情、资源申请入口、预留状态、用途、过期时间、消耗 / 释放 / 失败 / 拒绝结果。
4. 当前宗门持续行动、常态运营摘要、宗门任务、节点压力和公开事件反馈。
5. 常规运营指令的待生效、已生效、被覆盖、被拒绝、过期和撤销状态。
6. 权限委托与收回结果，以及可见范围内的审计摘要。
7. 宗门库存变更、资源申请、功法载体发放、NPC 支持、交易、护法、导师指点和设施支持来源的可回放日志。

普通 UI 不展示：

1. 调试级完整库存、内部 ID、原始倍率、完整 AI 权重和隐藏世界日志。
2. 无权限成员不应看到的私人申请详情、隐秘后手、其他玩家私人归因和完整库存细节。
3. 事件尚未暴露的隐藏选项、正式交锋轮内对手策略、突破挑战轮内未揭露选择。
4. 节点级 UI 布局、组件坐标和 Figma 节点 ID；这些只在当前 UI artifact / Figma 中维护。

## 9. MVP 范围

MVP 应实现：

1. 宗门身份序列：外门弟子、内门弟子、真传弟子、执事、长老。
2. 宗门或空的单一所属组织口径。
3. 宗门五类抽象资源和 `sect_storage` 底层容器引用。
4. 宗门资源申请、部分批准、拒绝、过期、预留、消耗、释放和审计。
5. 宗门内商店与资源申请的路径分离。
6. 每个宗门同一时间最多一个 active `SectContinuousActionState`。
7. 常规运营指令、权限委托、延迟生效窗口和生效前复校验。
8. 玩家与 NPC 共用职位、权限、待生效指令和审计日志。
9. 多人房中的权限层可见性、私人申请隔离和机会占用反馈。
10. 宗门页面的概览、库存摘要、资源申请、预留、持续行动、常规运营指令和日志入口。

MVP 不实现：

1. 宗门内部派系 / 山头变量。
2. 玩家直接夺宗主位。
3. 复杂同宗议会或强制投票。
4. 家族、帮派、商会、王朝官署等非宗门组织系统。
5. 通过宗门持续行动直接迫害同宗玩家长期体验。
6. 贡献作为可自由消费货币。
7. 资源申请绕过真实库存。
8. 宗门库存直接挂在宗主、长老或管事个人身上。
9. 玩家直接排多个宗门持续行动。
10. 常规运营指令即时生效。
11. 用常规运营指令替代个人行动、事件选择、正式交锋或突破挑战。
12. 将宗门外个人洞府、普通藏宝或真灵藏宝直接写成宗门资源来源。

## 10. 验收约束

1. 宗门系统不得把玩家本体、真灵本体或宗门组织混为同一实体。
2. 任一角色和 NPC 在 MVP 阶段不得同时拥有第二个明确所属组织。
3. 宗门发放给玩家或 NPC 的资源必须能追溯到真实库存、合法预留、事件输入或明确结果包。
4. 贡献、职位、声望、关系和身份不得绕过库存、预留、地点、权限、节点状态或事件状态校验。
5. 同一宗门同一时间不得存在两个 active `SectContinuousActionState`。
6. 常规运营指令不得占用个人行动队列，也不得被当作第二个宗门持续行动槽。
7. 常规运营指令提交、覆盖和更新不得同小时即时生效，必须进入待生效状态并在生效窗口前重新校验。
8. 权限设置、转移和收回可即时影响资格，但不得即时制造新的运营结果或回滚既成结果。
9. 资源预留必须阻止同一批资源被宗门持续行动、商店售卖、其他玩家申请或事件奖励重复消耗。
10. 多人房中，宗门库存被申请可以影响其他玩家机会，但私人申请详情不得无权限公开。
11. 宗门外个人洞府、普通藏宝和真灵藏宝不得被系统自动归并为宗门库存来源。
12. 宗门库存、资源申请、预留、运营指令、权限变更和关键发放必须写入审计日志或结果包。
13. 玩家洞天内主观时间不得刷新宗门库存、宗门时间阵名额、资源审批或宗门会议。
14. 低风险宗门职责可参与 F1，但宗门重大事件、公共决策、席位争夺和资源归属冲突必须退出 F1 或进入 P0 / B1。

| 宗门内商店库存 | 商店购买与资源申请分离 | 商店是否共享宗门库存短缺惩罚，还是拥有独立货架缓冲 |
| 常规运营默认延迟 | MVP 默认下一个宗门日结窗口，且不得同小时即时生效 | 是否固定 24 小时或按指令类型配置不同延迟 |
| 同一职位多人持有 | 必须有当前负责人或明确复核规则，否则只能作为建议来源 | 负责人、复核人和覆盖规则是否进一步细分 |
| 玩家宗主 | MVP 不开放玩家宗主 | 宗主或等价多权限玩家是否进入后续版本 |
| 运营权限 UI 粒度 | 支持按职责范围展示权限和日志 | 按大类显示，还是展开到每个节点、设施、商店、培养名额和资源类型 |
| 宗门俸禄公式 | 使用“境界基数 + 职位绝对值 → 宗门财政状态修正 → 最终发放额” | 境界基数、职位绝对值和财政修正表需要数值化 |
| 宗门时间阵与洞天席位 | 已确认读取外界日历并可作为资源年来源 | 需要补名额、贡献成本、库存成本、开放周期和风险表 |
| F1 宗门职责 | 低风险职责可参与 F1 | 需要补职责标签、自动摘要和中断事件列表 |
