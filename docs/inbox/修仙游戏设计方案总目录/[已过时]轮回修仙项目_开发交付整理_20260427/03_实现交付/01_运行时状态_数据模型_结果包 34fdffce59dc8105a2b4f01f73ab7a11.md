# 运行时状态、数据模型与结果包

## 0. 文档定位

本文是给开发人员的运行时结构整理，用于把各系统的设计案落到统一的数据对象和结果包。

它不是最终数据库 schema，但可作为 Godot 资源、JSON、SQLite 表结构或 GDScript class 的起点。

## 1. 总体原则

1. 客户端提交意图。
2. 服务端校验意图。
3. 服务端生成时间轴。
4. 系统只输出结果包。
5. S1 合并结果包并回写状态。
6. 所有高价值变化写日志。
7. 存档保存状态，不保存临时 UI。
8. 文案与规则分离。

## 13. Delta 合并规则

S1 回写前应合并结果包。

推荐原则：

1. 同一角色状态变化按系统优先级和时间顺序合并。
2. 库存扣减优先校验预留和容器。
3. 节点控制权变化必须通过事件或宗门行动结果，不接受孤立 delta。
4. 后手状态变化必须带原因链。
5. 日志不可丢失，可按可见性过滤展示。
6. 若多个结果包冲突，进入 debug error 或待人工规则补充，不静默覆盖。

## 16. 开发注意事项

- 不要让 UI 直接改状态。
- 不要在事件脚本里直接修改库存。
- 不要把字符串包装名作为规则判断。
- 不要让 NPC 战斗开始时生成完整背包。
- 不要让托管执行重大不可逆操作。
- 不要把世界日志全部展示给玩家。
- 不要把正式后手无原因删除。
- 不要让同一资源被多个系统重复消费。

## 17. 最小实现建议

第一版可以先实现：

1. `RuntimeWorldState` 内存状态。
2. JSON 或 Resource 配置。
3. 简化存档序列化。
4. 统一 `ResultPackage`。
5. 资产容器基础接口。
6. 角色、节点、宗门最小状态。
7. 事件、战斗、突破可先使用模板 id + 条件 + 结果包。
8. Debug 面板显示当前状态和本季度结果包。
