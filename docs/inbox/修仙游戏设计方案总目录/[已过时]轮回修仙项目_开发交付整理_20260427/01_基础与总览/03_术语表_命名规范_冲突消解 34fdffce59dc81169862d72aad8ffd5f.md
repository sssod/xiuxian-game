# 术语表、命名规范与冲突消解

## 0. 文档定位

本文是开发实现的命名标准。若旧文档中的字段、术语或包装名与本文冲突，开发阶段暂以本文为准。

原则：

1. 规则层使用抽象、可扩展、可本地化的命名。
2. UI 层可以使用修仙包装名。
3. 数据层不直接写死世界观名。
4. 同一概念只保留一个规则字段名。
5. 同一中文词在不同语境下若含义不同，必须拆成不同内部字段。

```

## 2. 境界、阶级、里程碑

### 2.1 境界阶段 Stage

规则层统一使用：

```
A-1, A-2, A-3
B-1, B-2, B-3
C-1, C-2, C-3
```

推荐字段：

```
CultivationStage {
  code: String,          # "B-2"
  major_code: String,    # "B"
  minor_index: int,      # 2
  major_order: int,      # 2
  absolute_order: int,   # 202
  display_name_key: String
}
```

禁止：

```
用 lianqi / zhuji / jindan 做规则判断
用中文境界名做数据库主键
用字符串排序判断阶段高低
```

### 2.2 MVP 里程碑 Milestone

M0–M3 是体验里程碑，不等于境界编码。

| 里程碑 | 含义 | 常见阶段映射 |
| --- | --- | --- |
| M0 | 开局与入门 | 凡人 / A-0 前后 |
| M1 | 第一阶段修行闭环，准备第一次大突破 | A 阶圆满 |
| M2 | 第二大境界起点 | B-1 |
| M3 | 第三大境界起点 | C-1 |

冲突决议：M3 不是 `C-3`。

### 2.3 物品 / 功法 / 资质阶级 Tier

物品、功法、资质子项、建筑、资源槽等可评级对象统一采用：

```
tier_code: A / B / C / ...
tier_order: 1 / 2 / 3 / ...
```

UI 显示原则上与修炼阶级包装对齐，例如 A 阶显示为“炼气阶”。少数系统如灵根可使用独立包装，但底层仍映射到统一评级或价值模型。

### 2.4 品级 Quality

统一 5 档：

```
Q1：下品
Q2：中品
Q3：上品
Q4：极品
Q5：绝品
```

推荐字段：

```
QualityProfile {
  quality_code: String,     # Q1 ~ Q5
  quality_order: int,
  display_key: String,
  value_multiplier: float,
  random_affix_budget: int,
  instability_modifier: float
}
```

## 3. 时间与行动术语

| 中文术语 | 规则含义 | 推荐字段 |
| --- | --- | --- |
| 季度 | 世界推进基本回合 | `quarter` |
| 朔望行动格 | 每季度 6 个时间预算格 | `action_slot` |
| tick | 结算内部时间步，默认对应 1 个朔望行动格 | `tick_index` |
| 宗门行动阶段 | 玩家影响宗门主行动的阶段 | `sect_decision_phase` |
| 角色行动阶段 | 玩家规划本角色行动格的阶段 | `character_decision_phase` |
| 插入事件链 | 暂停普通时间轴的高价值事件 | `inserted_event_chain` |

冲突决议：

- 统一使用“6 个朔望行动格”，不使用“朔望月行动格”。
- tick 是结算时间单位，不是统一收益公式。
- 移动、持续行动、事件消耗都通过 action slot / tick 表达。

## 4. 角色属性命名冲突处理

旧文档中“精力”和“元气”容易在英文字段上都被写成 `energy`；同时，“悟性”曾被误写为 `base_comprehension`，容易被理解为基础属性。开发口径如下：

| 中文显示 | 规则含义 | 推荐内部字段 |
| --- | --- | --- |
| 体魄 | 基础属性，影响肉身承载与生机 | `base_physique` |
| 精力 | 基础属性，影响气力底子与恢复承受 | `base_vigor` |
| 根骨 | 资质子项，影响承载、修炼基础、突破准备 | `aptitude_bone` |
| 悟性 | 资质子项，影响理解、学习、参悟和技艺成长 | `aptitude_comprehension` |
| 灵根 | 资质子项，影响灵气亲和与功法适配 | `aptitude_root` |
| 生机 | 持久状态条，生命 / 健康 | `bar_vitality` |
| 元气 | 持久状态条，法力 / 气力 / 可支配能量 | `bar_qi` |
| 神念 | 持久状态条，心神 / 神识 / 灵魂稳定 | `bar_mind` |

冲突决议：

- 不再用 `energy` 同时表示“精力”和“元气”。
- 不再使用 `base_comprehension`；“悟性”统一归入资质子项并使用 `aptitude_comprehension`。
- 战斗指令消耗应读取 `bar_qi`，不是 `base_vigor`。
- 持续行动疲劳和恢复可以同时读取 `base_vigor` 与 `bar_qi`，但语义必须区分。

## 5. 功法、道功、法门

| 中文术语 | 含义 | 推荐字段 / 类型 |
| --- | --- | --- |
| 功法 | 泛称，不建议作为精确规则类型 | `MethodBase` |
| 道功 | 可推动修为增长，可设为主修 | `DaoMethod` |
| 法门 | 不直接推动修为，提供技能 / 技艺 / 事件能力 | `TechniqueMethod` |
| 主修道功 | 当前大境界修炼路线核心 | `main_dao_method_ref` |
| 术法 / 神通 | 可生成战斗或事件指令的能力 | `SkillCommandSource` |

规则：

- 同一时间只能有一个主修道功。
- 只有道功可设为主修。
- 主修道功只在 A-1 / B-1 / C-1 等大境界第一小阶段窗口内允许无行动格替换。
- 离开该大境界第一小阶段后，本大境界主修路线锁定。
- 每个大境界记录最终锁定的主修道功，用于突破模板和固化根基。

## 6. 宗门、声望、影响力命名

旧文档中“声望 / 影响力”同时作为宗门资源、节点影响力、玩家门内评价使用。开发口径拆分如下：

| 中文显示 | 规则含义 | 推荐字段 |
| --- | --- | --- |
| 宗门声望 | 宗门整体外部评价 / 组织资源 | `sect_reputation` |
| 门内声望 | 玩家在宗门内部的可靠性 / 影响评价 | `member_reputation` |
| 节点影响力 | 某势力在节点上的影响度 | `node_influence_by_faction` |
| 节点控制权 | 当前主控制势力 | `control_owner_faction_id` |
| 玩家贡献记录 | 历史凭证，不是货币 | `contribution_records` |

冲突决议：

- 贡献不是货币，不能绕过宗门真实库存。
- 宗门声望不是通用兑换资源。
- 节点影响力不等同于宗门库存中的声望资源。

## 7. 库存、资产、位置

推荐统一使用“资产容器”模型，而不是直接问物品属于谁。

```
AssetContainerRef {
  container_type: String,  # character / sect / node / shop / market / legacy / event_locked
  container_id: String
}
```

常用容器类型：

| 容器 | 含义 |
| --- | --- |
| `CharacterInventory` | 当前角色随身或个人储藏 |
| `SectStorage` | 宗门库存 |
| `NodeStorage` | 节点储藏 |
| `ShopStock` | 商店库存 |
| `MarketListing` | 市场挂牌 |
| `SealedLegacy` | 正式后手 / 遗产封存 |
| `EventLockedReward` | 事件锁定奖励包 |
| `ResourcePool` | 节点自然资源池 |

冲突决议：

- 商店库存优先属于 `ShopStock` / `MarketListing`，不是掌柜个人背包。
- 战斗开始时不得临时初始化 NPC 完整库存。
- 正式后手不是物品来源，而是显性资产的一种封存状态。

## 8. 物品堆叠与实例

不设计“半可堆叠”。

规则层只允许：

```
可堆叠物品 ItemStack
独立实例物品 ItemInstance
```

建议堆叠键：

```
StackKey {
  item_template_id,
  tier_code,
  quality_code,
  key_state_tags,
  bind_state,
  owner_restriction
}
```

如果某字段影响战斗、突破、交易、后手、消耗结果，则进入堆叠键；若只是风味来源，不应拆分堆叠。

## 9. 货币与高密度资源

| 中文 | 规则含义 | 字段 / 类型 |
| --- | --- | --- |
| 灵石 | 修行世界核心通货，不分等级 | `SpiritStoneStack` |
| 铜钱 / 银两 | 凡人阶段与特殊情境货币，不进入长期主循环 | `MundaneCurrencyStack` |
| 聚灵石 | 高密度灵气物品，有阶级与品级，不是灵石面额 | `CondensedSpiritStoneItem` |

冲突决议：

- 不做“中品灵石 / 上品灵石”货币面额。
- 高阶灵气需求通过聚灵石、阵法、设施、特殊资源表达。
- MVP 灵石加工只打通“灵石 → 聚灵石”路径。

## 10. 事件和结果包

统一口径：

```
ResultPackage：所有系统结果包的通用称呼。
EventOutcome：事件链产生的 ResultPackage 子类型。
CombatOutcome：战斗链产生的 ResultPackage 子类型。
BreakthroughOutcome：突破链产生的 ResultPackage 子类型。
```

所有结果包必须交给 S1 统一回写，不允许事件、战斗、突破直接改写最终世界状态。

## 11. 可见性等级

统一可见性等级：

```
private
local_visible
sect_visible
rumor_visible
world_visible
debug_only
```

规则：

- 世界日志默认玩家不可见。
- 玩家看到的是角色日志、宗门摘要、轮回账本和传闻。
- 传闻不是全知日志，可以延迟、模糊、不完整。

## 12. NPC 分层命名

| 层级 | 名称 | 实现口径 |
| --- | --- | --- |
| N0 | 抽象人群 / 劳力池 | 无独立身份或库存 |
| N1 | 轻量身份 NPC | 身份持久化，通常无库存 |
| N2 | 功能服务 NPC | 服务入口，库存归机构 |
| N3 | 关键角色 NPC | 状态、库存、宏观行动持久化 |
| N4 | 世界轴心 NPC / 势力代理 | 高优先级宏观行动 + 事件链 |

冲突决议：

- 不设置 N2.5。
- N3 以上默认持久化个人库存。
- N4 每季度必须有个人宏观行动，但不得无条件增加宗门主行动数量。

```

## 14. 最小命名检查清单

开发提交前检查：

- 是否用中文境界名做了规则判断？
- 是否把精力和元气都命名成 energy？
- 是否误用 `base_comprehension`，或把悟性放进基础属性？
- 是否把贡献当货币使用？
- 是否让商店库存属于掌柜个人？
- 是否让 NPC 战斗开始时生成完整库存？
- 是否让事件直接改写世界状态而绕过 S1？
- 是否把正式后手当成凭空产出来源？
- 是否在 MVP 中引入了背包重量、装备栏、宗门内派系、强 PvP 或深度 NPC 生态？
