# 数值设计｜战斗公式与数值设计

## 1. 设计定位

本文负责战斗与突破交锋的数值层口径，包括 B1 时间记账字段、交锋叙事耗时、参战记账耗时、生机 / 元气 / 神念三条战斗属性条、法力出力基础、基础克制公式边界、结果包字段和后续调参待补。

当前战斗系统仍明确不展开完整伤害公式、技能数值表、法宝品质数值和 AI 权重。因此本文只沉淀已经稳定的公式结构、单位和验收边界，不把待补数值伪装成定稿。

## 2. 当前结论

1. 战斗数值层当前只确定公式框架和结算字段，不维护完整伤害、命中、技能倍率、法宝品质或 AI 权重表。
2. 生机、元气、神念是战斗读取和回写的三条持久状态条，不是进入战斗后临时生成并自动回满的资源。
3. 战斗出力主要读取法力，不直接读取 CP；法力由修炼公式按 `CP × 纯度 × 道功放大系数` 派生。
4. 正式战斗采用 5 格指令预输入；常规战斗 1 个战斗回合为 5 个交锋格，叙事耗时 10 分钟，常规 3 回合共 30 分钟，不足 1 游戏小时按 1 游戏小时记账。
5. B1 现实提交窗口、B1 世界推进和参战交锋自身结算耗时必须分开记录；每 60 秒现实提交窗口默认对应非参战玩家和世界推进 1 游戏小时。
6. 突破交锋复用 B1 提交窗口和结果包，但每阶段只输入 1 个交锋格，阶段耗时由突破模板声明，总耗时暂定 1～6 游戏小时。
7. 基础克制关系为“攻击克制 Buff、防御克制攻击、Buff 克制防御”；攻击 vs 攻击采用有效威力抵消后由差值造成影响。
8. MVP 丹药没有即时生效类型，不允许在战斗 / 突破交锋中作为即时指令使用；符箓、法宝、阵盘或护符等持续效果按交锋结算耗时扣减剩余持续时间。

## 5. 公式或模型

### 5.1 B1 时间记账

B1 时间字段必须区分现实提交窗口、世界推进和参战交锋耗时：

```text
submit_windows_resolved =
  已进入并完成结算的 B1 提交窗口数量

b1_world_elapsed_hours =
  submit_windows_resolved * b1_hours_per_submit_window

nonparticipant_progress_hours =
  b1_world_elapsed_hours
```

常规战斗交锋：

```text
encounter_scene_elapsed_minutes =
  combat_rounds_used * 10

encounter_accounting_hours =
  max(ceil(encounter_scene_elapsed_minutes / 60), minimum_accounting_hours)
```

其中 `minimum_accounting_hours` 在常规战斗中为 1。常规战斗 3 回合时，`encounter_scene_elapsed_minutes = 30`，`encounter_accounting_hours = 1`。

突破交锋：

```text
encounter_accounting_hours =
  sum(breakthrough_stage_accounting_hours)
```

各阶段耗时由突破模板声明，总耗时暂定 1～6 游戏小时。突破阶段耗时不仅用于叙事，也参与资源、持续效果和时间结算。

参战差值字段：

```text
participant_gap_hours =
  b1_world_elapsed_hours - encounter_accounting_hours
```

战斗 / 突破交锋沿用行动系统的 gap 最大 1 游戏日限制；本文不额外增加实现层时间预算限制。

### 5.2 交锋格结算框架

战斗出力基础建议使用法力因子，而不是直接使用 CP：

```text
combat_power =
  base_attribute_score
  * realm_multiplier
  * minor_stage_multiplier
  * mana_factor
  * state_factor
  + equipment_spell_bonus
```

其中：

```text
mana_factor = f(total_mana 或 current_major_realm_mana)
```

`mana_factor` 的具体曲线待补。MVP 只要求它读取法力结果，不能直接把 `cultivation_points` 当作战斗力。纯度、道功放大系数和巩固修为对战斗的影响通过法力间接体现。

每个交锋格至少按以下顺序结算：

```text
读取双方当前状态与可用指令
→ 校验资源、状态封锁和使用条件
→ 资源不足时替换为低效守势 / 喘息 / 空过
→ 计算己方主动消耗、恢复、蓄势或自损
→ 按指令类型与 counter_profile 计算克制、抵消或打断
→ 写入生机 / 元气 / 神念变化和状态标签
→ 检查结束条件
→ 记录交锋格摘要与失败原因
```

每格结算后都必须检查结束条件，不为了填满 5 格或达到预设轮数强行继续。

### 5.3 基础克制框架

基础三角关系：

```text
攻击克制 Buff
防御克制攻击
Buff 克制防御
```

攻击 vs 攻击：

```text
effective_delta =
  attacker_effective_power - defender_effective_power

if effective_delta > 0:
  威力较高方按差值造成影响
else:
  双方攻击互相抵消或被压制
```

防御 vs 攻击：

```text
defense_effective_value 通常高于同层级 attack_effective_power
defense_resource_cost 通常低于同层级 attack_resource_cost
attack_overflow = max(attack_effective_power - defense_effective_value, 0)
```

攻击 vs Buff：

```text
Buff 通常不提供即时防护
攻击方可造成接近完整攻击风险
impact_value 超过模板阈值时，Buff 被打断或效果降低
```

Buff vs 防御：

```text
防御未遭遇攻击时价值下降
Buff 方获得蓄势、恢复、观察、强化或后续优势
```

以上变量的具体倍率、命中、随机、打断阈值和状态封锁公式仍待补齐。

### 5.4 属性条变化框架

生机、元气、神念按当前持久状态读取，按可用容量约束回写：

```text
bar_available_max =
  bar_max - bar_reserved_value

bar_after =
  clamp(
    bar_before
    + recovery_value
    - active_cost
    - damage_value
    - special_loss,
    0,
    bar_available_max
  )
```

规则：

1. 主动消耗、对方造成的伤害和特殊损失必须在日志中区分。
2. 战斗结束条件默认只统计对方造成的伤害；特殊模板可以例外。
3. 战后不自动回满，后续恢复、疗伤、调息或持续效果由对应系统处理。
4. 生机、元气、神念上限与保留值口径由《角色属性与派生状态数值设计》（`09_角色属性与派生状态数值设计.md`）维护。

### 5.5 持续效果扣减

符箓、法宝、阵盘、护符或提前生效的资源效果若在交锋中持续存在，按交锋结算耗时扣减剩余时间：

```text
effect_remaining_hours_after =
  max(effect_remaining_hours_before - encounter_accounting_hours, 0)
```

MVP 丹药没有即时生效类型，不进入战斗 / 突破交锋即时指令池。提前服用并已经处在炼化过程中的丹药或资源效果，是否在突破阶段累计耗时中生效，由丹药、持续状态和突破模板共同决定。

## 6. 配置表或根表

## 7. 结算输出

战斗 / 突破交锋输出结果包，由父事件链决定后续行动、位置、状态、日志、奖励、惩罚或转世结果。战斗失败可造成伤势、资源损耗、声望损失、事件失败、窗口错过或短期修炼受阻，不应高频制造修为倒退或长期毁灭性惩罚。

结果包必须区分：

```text
b1_world_elapsed_hours
nonparticipant_progress_hours
encounter_scene_elapsed_minutes
encounter_accounting_hours
participant_gap_hours
combat_rounds_used
breakthrough_stages_resolved
slots_resolved
```

结果包还应至少输出：

| 输出 | 用途 |
| --- | --- |
| `bar_delta_summary` | 展示生机、元气、神念的消耗、伤害、恢复和特殊损失 |
| `mana_factor_used` | 展示本次交锋读取的法力出力因子，普通 UI 可只包装为法力充沛 / 法力偏虚 |
| `consumed_resources` | 记录符箓、法宝充能、阵盘、护符或其他资源消耗 |
| `artifact_state_delta` | 记录法宝破损、失灵、充能下降或战后修复需求 |
| `status_tags_added` / `status_tags_removed` | 记录伤势、震荡、封锁、护盾、持续状态等变化 |
| `slot_logs` | 逐格交锋摘要、失败原因、克制结果和结束条件检查 |
| `visible_log_entries` | 玩家可见日志、战斗摘要和突破报告素材 |
| `debug_trace` | QA 使用的公式追踪、隐藏权重和随机信息，不进入普通 UI |

## 8. 调参验收口径

1. 常规战斗应保持短促、高强度；普通斗法不得因 B1 世界推进被错误解释为每回合自身消耗 1 游戏小时。
2. B1 世界推进、非参战推进、交锋叙事耗时和参战记账耗时必须分别记录，不能被合并成单一耗时字段。
3. 生机、元气、神念必须读取当前持久状态并回写变化，战后不能自动回满。
4. 战斗出力读取法力，不直接读取 CP；同 CP 下纯度和道功放大系数不同应导致法力出力差异。
5. 防御在同层级下应比攻击更省且有效值更高，但不得让防御成为无成本最优策略。
6. Buff 在没有被攻击打断时应能获得后续优势，但不能在遭遇攻击时默认拥有完整即时防护。
7. 攻击 vs 攻击必须体现有效威力抵消和差值影响，避免双方完整伤害同时生效导致低层级战斗过快崩盘。
8. 每个交锋格都必须检查结束条件，提前结束时不继续结算剩余格子。
9. 符箓、法宝、阵盘、护符或提前生效资源的持续时间必须按交锋记账耗时扣减。
10. MVP 丹药不得在战斗 / 突破交锋中作为即时指令使用。
11. 普通 UI 不展示完整伤害公式、原始倍率、AI 权重、随机种子、未公开敌方未来指令或 Debug 字段。

## 9. MVP 范围

MVP 应实现：

1. `SceneTimeProfile`、`CommandNumericProfile`、`CounterProfile` 和结果包字段的最小配置结构。
2. 常规战斗 5 格预输入、每回合 10 分钟叙事耗时、常规 3 回合 30 分钟且不足 1 小时按 1 小时记账。
3. B1 提交窗口、B1 世界推进、非参战推进、交锋叙事耗时和参战记账耗时分离。
4. 生机、元气、神念当前值读取、消耗 / 伤害 / 恢复回写和可用上限裁剪。
5. 法力出力因子字段，读取总法力或当前大境界法力。
6. 攻击、防御、Buff 的基础三角克制，以及攻击 vs 攻击的有效威力差值。
7. 资源不足、状态封锁和未提交时的低效兜底指令。
8. 符箓、法宝、阵盘或护符等持续效果按交锋记账耗时扣减剩余时间。
9. 逐格交锋日志、失败原因、结果包引用和可回放摘要。

MVP 不实现：

1. 完整伤害公式、命中公式、暴击公式或复杂随机曲线。
2. 完整技能数值表、全部法宝品质数值、耐久曲线和修复经济。
3. 高级 combo、连锁反制、多段打断和复杂多人协同公式。
4. 完整 AI 搜索、AI 权重表和按玩家锁定结果作弊式逐格改指令。
5. 战斗 / 突破交锋中的即时生效丹药。

| 战斗日志与回放 | 只确定逐格摘要、失败原因和结果包字段 | 需要补齐公开 / 私密可见性、公式追踪字段和回放展示规则 |
