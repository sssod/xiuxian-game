# 数值设计｜事件设计基准建模

## 1. 设计定位

本文负责事件顶层类型、来源标签、候选池、窗口、传闻和专用事件链入口的数值建模基准。它维护事件候选生成、候选池评分排序、去重节流、事件强度、选项成本 / 风险 / 收益、隐藏后患、奖励预算、结果包输出和验算指标。

系统玩法由《随机事件玩法设计》（`../02_系统设计/15_随机事件玩法设计.md`）维护；本文只维护数值建模、调参接口和验算约束。本文不负责完整事件文本库、最终概率表、战斗伤害公式、突破轮内成功率公式、NPC AI 权重、UI 视觉布局、数据库 schema 或网络协议。

## 2. 当前结论

1. 事件数值运行在 `world_day / world_hour` 与结算区间上；N1 的结算区间通常等于 1 个 `hour_tick`，F1、后台追赶和局部时间域可以使用更长区间，但不再使用 `quarter / tick / 行动格` 作为事件主时间字段。
2. 事件候选必须由世界状态、角色状态、节点状态、行动上下文、窗口、资源预算、可见性和冷却共同生成，不做纯 UI 刷新随机。
3. 事件概率、权重、窗口出现频率和同一结算时间桶最大普通触发数量尚未定；本文只定义可验算的配置结构和首版边界。
4. 候选生成可以有随机扰动，但必须使用事件实例稳定种子或稳定排序，不能靠刷新界面改变候选。
5. 数值配置必须写入互斥 `top_level_type`：后台结算、信息回读、个人即时处理、世界窗口或同步处理；移动、节点、宗门、世界演化、控制权、传闻和专用链入口只作为 `source_domain_tags` 或触发入口。
6. 普通个人选择事件和轻遭遇归入个人即时处理事件并使用局部时停；C1 或其它时间追赶期间不触发新的随机个人即时处理事件、普通机缘、普通战斗、软机会事件、普通心魔或普通资源反馈，但应复用事件池压制逻辑并继续累积符合条件但未触发的伪随机压力。
7. 正式交锋和突破挑战归入同步处理事件并进入 B1；B1 的现实提交窗口、非参战世界推进和参战交锋自身结算耗时必须分开记录。
8. 事件奖励不得绕过世界产出预算、资产容器、库存来源、资源预留和结果包审计。
9. 低价值事件可以被显式托管保守处理；重大事件、正式交锋、突破挑战、不可逆选择和死亡风险不得被普通队列或自动兜底吞掉。
10. F1 中事件仍会触发；预定事件、阈值事件、危险率事件和条件事件可通过通用事件流采样进入批量摘要、F1 校验断点或 F1 中断断点。`silent / summary / auto` 事件默认不打断 F1。
11. 事件配置分为事件本体、触发入口、候选池、进入 / 移出条件、权重倍率、伪随机状态和结算策略；移动、闭关、节点、宗门、局部时间域和世界宏观事件应复用同一套候选池与伪随机压力模型。

## 4. 基准、单位与输入参数

事件数值链路分为触发、候选、实例、选项、结果和验算六层：

```text
EventTemplate
→ EventTriggerProfile
→ EventCandidatePool / CandidateEntryRule / CandidateExitRule
→ EventWeightProfile / EventPseudoRandomState
→ EventCandidateScore
→ EventInstance / EventChain
→ EventOptionNumericProfile / EventCheckProfile
→ EventOutcome / ResultPackage
→ EventBalanceSimulation
```

| 模块 | 作用 |
| --- | --- |
| `EventTemplate` | 定义事件本体、互斥顶层类型、时间模式、强度、标签、安全默认和结果包模板，不直接决定何时触发 |
| `EventTriggerProfile` | 定义某类事件在什么触发源、节点、状态和时间条件下进入候选池 |
| `EventCandidatePool` | 聚合同一结算区间、同一角色、同一节点、同一行动或同一窗口的候选事件 |
| `CandidateEntryRule / CandidateExitRule` | 配置事件进入或移出候选池的硬条件，例如单程耗时、地形、风险、状态、冷却、预算和窗口 |
| `EventWeightProfile` | 定义进入候选池后的基础权重、条件倍率、重复惩罚、冷却压制和区间尺度倍率 |
| `EventPseudoRandomState` | 记录候选池伪随机游标、未触发压力、触发后短时压制和追赶压制状态 |
| `EventCandidateScore` | 对候选按上下文匹配、风险、压力、预算、冷却和随机扰动排序 |
| `EventInstance / EventChain` | 固化事件实例、候选选项、稳定随机种子、阶段和状态 |
| `EventOptionNumericProfile` | 定义选项成本、风险、收益强度、时间成本、资源输入和隐藏标签 |
| `EventCheckProfile` | 定义低交互检定、暴露、发现、抵消、追查和失败标签判定 |
| `EventOutcome / ResultPackage` | 输出权威结算所需的时间、状态变化、日志、传闻、预算和子事件请求 |
| `EventBalanceSimulation` | 验算事件密度、打断率、奖励预算消耗、B1 / P0 频率和负反馈强度 |

`EventTemplate` 最少应声明：

```yaml
EventTemplate:
  template_id: string
  top_level_type: background_settlement | information_readback | personal_immediate | world_window | synchronized_resolution
  source_domain_tags: list[string]
  event_time_mode: info | local_time_stop | light_encounter | formal_encounter_b1 | breakthrough_b1 | global_pause_p0
  gameplay_modules: list[choice | check | investment | clash | discovery | window | aftermath | arbitration]
  f1_interrupt_level: silent | summary | auto | soft_interrupt | hard_interrupt
  outcome_level_baseline: none | minor | standard | major | critical
  visibility_policy: private_player | known_to_party | sect_visible | rumor_visible | public_world | hidden_world | debug_only
  result_package_template_ref: string
```

`top_level_type` 必须互斥；`source_domain_tags` 可以复数存在，用于候选池、预算和回放检索。

时间、随机和上下文基准：

1. 候选生成使用 `trigger_world_day / trigger_world_hour` 和结算区间；N1 可直接对应 `hour_tick`，F1、后台追赶和局部时间域必须保留区间起止与采样种子。
2. 顶层类型使用 `top_level_type` 区分后台结算、信息回读、个人即时处理、世界窗口和同步处理；来源使用 `source_domain_tags` 表达，不作为顶层类型。
3. 事件模式使用 `event_time_mode` 区分信息、局部时停、轻遭遇、正式交锋、突破挑战和全局暂停。
4. 随机扰动必须归属 `rng_namespace`，并在事件实例或候选排序中稳定复盘。
5. 所有状态变化、预算扣减、窗口变化和日志输出必须能追溯到事件上下文。

`EventContext` 推荐字段：

```yaml
EventContext:
  context_id: string
  trigger_world_day: int
  trigger_world_hour: int
  top_level_type: background_settlement | information_readback | personal_immediate | world_window | synchronized_resolution
  source_domain_tags: list[string]
  trigger_type: travel_leave | travel_enter | route_hour_tick | action_hour_tick | action_complete | node_update | sect_update | window_update | contingency_trigger | death_or_reincarnation | rumor_update | manual_debug
  event_time_mode: info | local_time_stop | light_encounter | formal_encounter_b1 | breakthrough_b1 | global_pause_p0
  actor_refs: list[string]
  faction_refs: list[string]
  node_id: string | null
  route_id: string | null
  route_segment_ref: string | null
  current_command_ref: string | null
  action_context: object
  visibility_context: object
  risk_level: low | medium | high | unknown | null
  resource_slot_refs: list[string]
  facility_refs: list[string]
  hidden_layer_refs: list[string]
  contingency_refs: list[string]
  remnant_site_refs: list[string]
  opportunity_window_refs: list[string]
  rumor_refs: list[string]
  current_macro_period_id: string | null
  time_domain_scope: outer_world | local_time_domain | threshold | scheduled | conditional
  settlement_interval_ref: string | null
  local_time_domain_ref: string | null
  rng_namespace: string
```

旧口径迁移：

| 旧字段 / 旧说法 | 当前口径 |
| --- | --- |
| `quarter` | 不作为事件主时间字段；宏观批次使用 `current_macro_period_id` |
| `tick` | 具体结算使用 `hour_tick`、`trigger_world_day`、`trigger_world_hour` |
| `danger_level` | 地图风险统一为 `risk_level`；事件自身可另有风险描述标签 |
| `route_segment` | 迁移为 `route_segment_ref` |
| 行动格消耗 | 迁移为 `consumed_hours`、行动进度变化、B1 世界推进或交锋自身结算耗时 |
| 世界刷新只在季度开始发生 | 迁移为世界小时演化 + 宏观周期批次；窗口、资源和传闻仍可按宏观周期批量显现 |

## 5. 公式或模型

### 5.1 候选池评分

候选评分不是最终概率公式，而是可用于首版实现和验算的统一接口。

```yaml
EventCandidateScore:
  candidate_id: string
  template_id: string
  context_id: string
  base_weight: number
  context_fit_multiplier: number
  realm_fit_multiplier: number
  node_risk_multiplier: number
  pressure_multiplier: number
  resource_budget_multiplier: number
  visibility_multiplier: number
  cooldown_multiplier: number
  repeat_penalty_multiplier: number
  priority_override: force | high | normal | low | suppress | null
  stable_rng_jitter: number
  final_score: number
  score_reason_tags: list[string]
```

推荐起步公式：

```text
final_score =
  base_weight
  * context_fit_multiplier
  * realm_fit_multiplier
  * node_risk_multiplier
  * pressure_multiplier
  * resource_budget_multiplier
  * visibility_multiplier
  * cooldown_multiplier
  * repeat_penalty_multiplier
  * stable_rng_jitter
```

规则：

1. 缺少匹配信息时默认倍率为 `1.0`，不得因为字段缺失自动放大事件概率。
2. `priority_override = force` 的强制事件优先结算，但仍必须写明触发原因。
3. `priority_override = suppress` 用于冷却、C1、不可见、预算不足或状态已失效的候选。
4. `stable_rng_jitter` 只能在事件实例稳定种子下生成，不能随 UI 刷新变化。
5. 未触发压力属于 `EventPseudoRandomState`，不作为候选评分的核心字段；当权重随机或保底机制命中时，应生成触发提案。
6. 调试器应能展示 `score_reason_tags`、命中的条件、被压制原因和排序结果。

### 5.2 候选池节流与去重

同一结算时间桶和同一上下文中可能存在多个候选事件。N1 下结算时间桶通常等价于同一 `hour_tick`；F1、后台追赶和局部时间域下由结算区间、采样时间和回放桶共同确定。MVP 采用以下节流规则：

1. 强制事件优先于普通事件。
2. 专用事件链入口优先于普通传闻。
3. 已经进入 B1 或 P0 的事件优先锁定对应速度状态。
4. 同一语义事件在同一结算时间桶和同一上下文中只触发一次。
5. 同一角色同一时刻最多只能有一个需要本人处理的局部时停事件。
6. C1 或其它时间追赶期间所有新随机个人候选都必须被 `suppress`；压制期间不生成事件实例，但符合候选池硬条件的事件仍可累积未触发压力。
7. 事件链进行中时，普通角色时间线按 `event_time_mode` 决定冻结、继续或进入交锋。
8. 事件返回后，由权威结算决定继续原计划、进入 C1、跳过指令、自动兜底或开启子事件。

首版世界级重大事件容量建议：

```text
同一区域同时最多 1 个 active major 世界事件；
世界全局同时不超过 2 个 active major 世界事件；
每个 active major 世界事件必须至少有一个玩家可理解的介入窗口；
忽略重大事件可以改变世界态势，但不应无预警造成毁档式损失。
```

以上容量只约束重大世界状态机，不等于普通事件候选池的最终触发上限。

同一结算时间桶内多个事件同时满足触发条件时，按“触发提案裁决”处理。触发提案来源和事件处理等级是两层概念：

```text
触发提案来源：forced / scheduled / threshold_crossing / weighted_hit / pity_hit
事件处理等级：silent / summary / auto / soft_interrupt / hard_interrupt / B1 / P0
```

`weighted_hit` 是正常权重随机命中；`pity_hit` 是长期未触发后的保底命中。保底命中只表示该候选应产生触发提案，不代表一定立刻生成事件实例。

触发提案使用结算期内的临时结构，不要求把所有字段固化到事件模板或候选评分中：

```yaml
EventOccurrenceProposal:
  proposal_id: string
  source: forced | scheduled | threshold_crossing | weighted_hit | pity_hit
  event_template_ref: string
  pool_ref: string
  context_ref: string
  occurred_at: string
  final_score: number
  rng_ref: string | null
  block_reason: string | null
  defer_reason: string | null
```

提案裁决顺序：

1. 先按实际发生时间切桶；不同时间点按时间先后处理，同一时间点才进入竞态。
2. 同一桶内先执行硬排除和同语义去重，硬移出的候选不产生触发提案。
3. 对有效候选先执行常规权重随机，命中者产生 `weighted_hit` 提案；未命中者按策略累积未触发压力。
4. 未触发压力达到保底阈值时，产生 `pity_hit` 提案。
5. `forced / scheduled / threshold_crossing` 提案来自系统入口、日历或阈值 crossing，不与 `hard_interrupt / B1 / P0` 直接并列排序；后者只在提案被选中后决定处理方式和速度状态。
6. 多个提案同时存在时，先按显式模板优先级、触发来源、发生时间、候选评分和稳定随机种子裁决；具体优先级参数仍需后续补表。
7. 达到容量上限或速度状态锁定后，普通随机提案不得强行生成事件实例；默认按策略保留未触发压力或延期到下一可结算时间桶。
8. 硬中断、公共保护或不可静默延后的重大提案若无法立刻处理，必须形成待处理原因、F1 中断断点、P0 保护或 Debug 审计记录之一。
9. 被选中的提案生成事件实例后，按事件模板重置、衰减或迁移其伪随机压力。

容量上限不是概率或权重，而是防止同一结算桶爆出过多事件的结构限制。当前明确的容量类型包括：

```text
候选容量：最多保留多少候选用于排序、调试和回放；
触发容量：同一池 / 同一角色 / 同一节点 / 同一时间桶最多生成多少事件实例；
交互容量：同一角色当前最多一个局部时停事件；
房间速度容量：同一时间只能存在一个主 B1 / P0 阻塞；
重大事件容量：active major 世界事件同时数量上限；
批次容量：F1 一天或后台追赶批次中最多解析多少事件。
```

提案裁决结果必须进入回放：

```yaml
EventOccurrenceResolution:
  time_bucket_ref: string
  proposal_refs: list[string]
  selected_proposal_refs: list[string]
  deferred_proposal_refs: list[string]
  suppressed_proposal_refs: list[string]
  capacity_limit_refs: list[string]
  stable_tie_break_seed: string
  resolution_reason_tags: list[string]
```

### 5.3 事件强度分层

事件实例和结果包应区分事件模板强度与实际结果强度。首版可以统一使用 `outcome_level` 做结果强度：

```text
none
minor
standard
major
critical
```

| `outcome_level` | 含义 | 常见结果 |
| --- | --- | --- |
| `none` | 信息、提示或日志更新，无实质状态变化 | 传闻记录、价格提示、节点趋势 |
| `minor` | 轻量变化，不应造成长期大改动 | 小延误、少量资源消耗、低风险发现、轻微关系波动 |
| `standard` | 常规事件结果，可以改变一次行动、节点、库存、关系或传闻 | 普通移动遭遇、资源异变、节点风险、常规探索发现 |
| `major` | 高价值或高风险结果，会影响窗口、战斗、突破、宗门评价、重要资产或节点态势 | 秘境入口、正式交锋入口、高价值后手线索、控制权变化 |
| `critical` | 不可逆或接近不可逆结果，需要明确模板、安全默认或 P0 同步保护 | 死亡边缘、重大夺舍、不可逆功法路线、严重资源损毁、公共世界级事件 |

强度规则：

1. 低风险普通候选不得直接随机生成 `critical` 结果；必须经过明确模板、玩家选择、B1 / P0 或高风险上下文。
2. `major / critical` 结果必须写入日志、回放、可见性规则和 Debug 审计。
3. 事件奖励强度不得高于其成本、风险、窗口稀缺性和预算来源能解释的范围。
4. 失败结果也要有强度分层，不能只输出“未成功”。

### 5.4 时间成本模型

事件时间成本统一通过 `EventTimeCostProfile` 表达。

```yaml
EventTimeCostProfile:
  event_id: string
  event_time_mode: info | local_time_stop | light_encounter | formal_encounter_b1 | breakthrough_b1 | global_pause_p0
  trigger_world_day: int
  trigger_world_hour: int
  frozen_character_world_day: int | null
  frozen_character_world_hour: int | null
  option_declared_hours: int
  consumed_hours: int
  b1_world_elapsed_hours: int | null
  nonparticipant_progress_hours: int | null
  encounter_scene_elapsed_minutes: int | null
  encounter_accounting_hours: int | null
  participant_gap_hours: int | null
  catchup_required: bool
  default_resolution_used: bool
```

| 场景 | 时间处理 |
| --- | --- |
| 信息事件 | 通常 `consumed_hours = 0`，不打断 |
| 普通个人选择事件 | `option_declared_hours` 从触发 `world_hour` 开始回填；结束后按需 C1 |
| 轻遭遇 | 按普通个人选择事件处理，除非升级为正式交锋 |
| 正式交锋 | B1 负责现实提交窗口与非参战世界推进；交锋自身耗时由战斗结果包返回 |
| 突破挑战 | B1 负责现实提交窗口与非参战世界推进；突破自身耗时由突破阶段模板累计 |
| 全局公共暂停 | P0 中游戏时间不流动，解除后由权威结算恢复速度 |

`consumed_hours` 在事件层表示本事件对角色、行动或追赶结算的最终可记账小时。B1 事件必须额外保留 `b1_world_elapsed_hours / encounter_accounting_hours` 等细分字段，避免把现实提交窗口、世界慢速推进和交锋叙事耗时混成一个数。

### 5.5 检定模型

检定事件用于低交互判定、暴露、发现、抵消、追查、被动法宝受损、NPC 察觉等场景。

```text
  actor_fit

  + item_or_resource_support
```

### 5.6 候选池、权重与伪随机压力

事件配置应把“是否有资格进入池”和“进入后多容易触发”分开。进入 / 移出候选池是硬条件；权重、压制和未触发压力只作用于已经进入候选池的事件。

候选池示例：

```yaml
EventCandidatePool:
  pool_id: travel_event_pool
  scope: travel
  clock_scope: outer_world
  default_settlement_interval: route_segment | hour | outer_day | custom
  candidate_limit_policy: weighted_top_n | all_eligible
  max_resolved_per_time_bucket: int | null
  occurrence_resolution_policy_ref: string | null
```

移动来源候选可以复用一个 `travel_event_pool`，再通过进入 / 移出条件控制候选：

```yaml
CandidateEntryRule:
  event_id: travel_ambush_low
  pool_id: travel_event_pool
  require:
    min_trip_hours: 2
    terrain_any: [mountain, forest, wildland]
    route_risk_any: [medium, high]
  exclude:
    route_tags: [safe_patrolled]
    actor_states: [hidden_by_high_tier_talisman]
```

进入 / 移出条件建议支持：

```text
时间条件：单程耗时、累计行动小时、当前时辰、窗口持续时间、局部主观年；
空间条件：地形、节点、路线、区域、风险等级、控制权；
角色条件：境界、身份、状态、资源、队伍规模、隐藏标签；
行为条件：当前行动、移动方式、闭关方式、显式托管、是否 F1；
世界条件：宗门局势、市场周期、区域事件、宏观阶段；
冷却条件：同类事件间隔、角色冷却、路线冷却、区域冷却；
预算条件：奖励预算、风险预算、窗口容量、重大事件容量。
```

权重配置示例：

```yaml
EventWeightProfile:
  event_id: travel_ambush_low
  pool_id: travel_event_pool
  base_weight: 10
  multipliers:
    terrain:
      mountain: 1.2
      forest: 1.1
      plain: 0.7
    route_risk:
      low: 0.3
      medium: 1.0
      high: 2.0
    trip_hours:
      0_2: 0.0
      2_6: 0.8
      6_12: 1.2
      12_plus: 1.6
  cooldown_suppression_multiplier: 0.2
  catchup_suppression_multiplier: 0.0
  repeat_penalty_multiplier: 0.5
```

伪随机状态示例：

```yaml
EventPseudoRandomState:
  state_id: string
  pool_id: string
  subject_ref: character | party | route | node | sect | world | local_time_domain
  rng_cursor: string
  accumulated_miss_pressure: number
  last_trigger_world_time: string | null
  recent_trigger_suppression_until: string | null
  catchup_suppression_active: bool
  pressure_decay_policy: none | slow_decay | table | formula
```

规则：

1. 硬移出候选池的事件不参与触发，也不累积未触发压力。
2. 进入候选池但被冷却、重复、追赶、低可见性或预算策略压制的事件，可以降低有效触发权重；是否继续累积未触发压力由 `pressure_accumulation_policy` 决定，默认继续累积。
3. 触发后的短时间压制不应清空长期风险；压制期内有效权重可以降低，但符合硬条件的池仍可累积未触发压力。
4. C1 或其它时间追赶中的“事件不触发”复用同一压制逻辑：不实例化新的随机个人即时处理事件，不进入局部时停 / B1 / P0，但仍更新候选池伪随机状态和未触发压力。
5. 追赶结束后不得回溯生成追赶区间内被压制的随机个人即时处理事件；累积压力只影响后续常规结算、F1 采样或局部时间域采样。
6. 同一候选池在 N1、F1、后台追赶和局部时间域中应读取同一个 `EventPseudoRandomState`，避免 1 小时、1 天或多年区间因结算粒度不同而产生系统性偏差。
7. 常规权重随机命中产生 `weighted_hit` 提案；长期未触发压力达到阈值时产生 `pity_hit` 提案。二者都必须经过同一结算时间桶的提案裁决和容量上限。
8. 未选中的普通随机提案默认保留或衰减未触发压力，具体由候选池策略决定；不得因为保底触发而一次性爆发多个事件。

### 5.7 通用事件流与危险率采样

事件流不是 F1 专属机制，而是任意结算区间内的事件发生模型。N1 可以用 1 小时区间，在线 F1 固定用 1 外界日区间，后台追赶 / Debug / 性能保护可以使用多日技术区间但必须切回外界日和断点，局部时间域可以用局部主观年或局部阶段区间。F1 批量结算中不逐小时全量掷骰，但事件不能被闭关承诺吞掉。事件触发方式包括：

1. 预定事件：宗门会议、洞天开放、市场刷新、行动完成，直接进入日历队列。
2. 阈值事件：资源耗尽、寿元低于阈值、心魔超过阈值、阵法燃料不足，计算 crossing time。
3. 危险率事件：闭关心魔、洞天异动、路途遭遇、宗门突发，以危险率采样下一触发时间。
4. 条件事件：进入某节点、携带某物、达到某境界、触发某关系后，在满足条件的区间内采样或排程。

事件等级：

| 事件等级 | 是否退出 F1 | 处理方式 |
| --- | --- | --- |
| `silent` | 否 | 后台记录或仅影响数值，不打扰玩家 |
| `summary` | 否 | 写入 F1 摘要 |
| `auto` | 否 | 按玩家预设、托管策略或安全默认处理，并写入摘要 |
| `soft_interrupt` | 视情况 | 有预设或安全默认则自动处理并形成 F1 校验断点；无预设且无安全默认则退出 F1 到 N1 |
| `hard_interrupt` | 是 | 立即退出 F1，进入 N1 / B1 / P0 |

事件流采样后的处理口径：

| 采样结果 | F1 处理 |
| --- | --- |
| `silent / summary` | 写入后台记录或 F1 摘要，不形成断点 |
| `auto` | 按玩家预设、托管策略或安全默认处理，写入摘要，不形成断点 |
| `soft_interrupt` 有预设或安全默认 | 执行预设后作为 F1 校验断点，提交结果并重检是否继续 F1 |
| `soft_interrupt` 无预设且无安全默认 | 作为 F1 中断断点，退出到 N1 |
| `hard_interrupt` | 作为 F1 中断断点，立即退出到 N1 / B1 / P0 |

事件流必须保留采样随机种子、事件流引用、候选池状态、未触发压力、压制原因、日内结算分段、F1 校验断点、F1 中断断点和结果摘要，保证可复盘。

## 6. 配置表或根表

### 6.1 事件触发配置

`EventTriggerProfile` 是事件候选进入系统的根配置。

```yaml
EventTriggerProfile:
  trigger_profile_id: string
  trigger_scope: travel | node | action | sect | world | window | contingency | rumor | debug
  source_domain_tags: list[string]
  eligible_top_level_types: list[string]
  trigger_type: travel_leave | travel_enter | route_hour_tick | action_hour_tick | action_complete | node_update | sect_update | window_update | contingency_trigger | death_or_reincarnation | rumor_update | manual_debug
  event_template_refs: list[string]
  candidate_pool_refs: list[string]
  candidate_entry_rule_refs: list[string]
  candidate_exit_rule_refs: list[string]
  eligible_time_modes: list[string]
  required_context_tags: list[string]
  excluded_context_tags: list[string]
  recommended_stage_range: string | null
  required_node_tags: list[string]
  required_risk_levels: list[string]
  required_window_types: list[string]
  resource_budget_refs: list[string]
  base_trigger_weight: number | null
  weight_profile_ref: string | null
  pseudo_random_state_scope: actor | party | route | node | sect | world | local_time_domain | null
  pressure_accumulation_policy: disabled | eligible_only | eligible_even_when_suppressed
  suppression_policy_refs: list[string]
  min_world_gap_hours: int | null
  min_actor_gap_hours: int | null
  cooldown_tags: list[string]
  repeat_penalty_profile_id: string | null
  max_candidates_per_context: int | null
  max_resolved_per_time_bucket: int | null
  mvp_enabled: bool
```

字段口径：

1. `source_domain_tags / eligible_top_level_types` 用于把触发入口约束到来源和互斥顶层类型；来源标签可以复数，顶层类型在事件实例上只能命中一个。
2. `candidate_pool_refs` 表示该触发入口会把事件本体投放到哪些候选池；移动、节点、宗门、闭关和局部时间域应优先复用池配置，而不是在代码里写死概率。
3. `candidate_entry_rule_refs / candidate_exit_rule_refs` 是硬条件；硬移出后不触发也不累积未触发压力。
4. `base_trigger_weight / weight_profile_ref` 是排序和验算参数，不代表最终概率已经定稿。
5. `pseudo_random_state_scope` 决定未触发压力和压制状态挂在角色、队伍、路线、节点、宗门、世界还是局部时间域上。
6. `pressure_accumulation_policy = eligible_even_when_suppressed` 表示事件已进入候选池但被冷却、重复、追赶或短时压制时仍继续累积未触发压力；这是 C1 / 时间追赶默认口径。
7. `min_world_gap_hours / min_actor_gap_hours` 用于防止同类事件短期重复打断。
8. `max_candidates_per_context / max_resolved_per_time_bucket` 必须可配置；首版可以保守设置，但具体数值仍需实测。
9. `resource_budget_refs` 只表示该事件可能读取或消耗哪些预算，不表示候选生成时立即扣预算。
10. `trigger_scope = debug` 只能用于调试器或 QA，不进入正常玩家流程。

通用事件流可使用 `EventStream` 或等价配置：

```yaml
EventStream:
  stream_id: string
  scope: character | sect | node | market | world | local_time_domain
  allowed_top_level_types: list[string]
  source_domain_tags: list[string]
  applicable_states: list[string]
  settlement_cycle_scope: n1_hour | f1_outer_day | catchup_multi_day | local_time_domain | macro_period
  occurrence_model: scheduled | threshold | hazard_constant | hazard_table | hazard_formula | conditional
  candidate_pool_refs: list[string]
  base_rate_per_outer_day: number | null
  base_rate_per_inner_year: number | null
  f1_interrupt_level: silent | summary | auto | soft_interrupt | hard_interrupt
  default_resolution_policy: string | null
  max_triggers_per_batch: number
  cooldown_policy: string
  pseudo_random_policy_ref: string | null
  catchup_suppression_policy: suppress_trigger_accumulate_pressure | suppress_and_no_pressure | none
  occurrence_resolution_policy_ref: string | null
  visibility_policy: string
```

`max_triggers_per_batch` 中的 `batch` 由 `settlement_cycle_scope` 决定：N1 为小时，在线 F1 为 1 外界日，后台追赶 / Debug / 性能保护可为多日技术区间，局部时间域可为局部主观年或局部阶段。后台追赶若使用更长技术批次，必须按在线 F1 的外界日边界、F1 校验断点或 F1 中断断点切分事件摘要和回放。`catchup_suppression_policy` 默认使用 `suppress_trigger_accumulate_pressure`，表示追赶期间不触发新随机个人即时处理事件但继续累积未触发压力。

### 6.2 事件选项数值配置

`EventOptionNumericProfile` 定义事件选项的成本、风险、收益和隐藏后患。

```yaml
EventOptionNumericProfile:
  option_id: string
  dimension: direct | unconventional | avoid | deconstruct | deceive | none
  availability_conditions: list[object]
  reveal_conditions: list[object]
  preferred_option_area: primary | overflow | auto
  time_cost_hours: int
  resource_input_refs: list[string]
  inventory_cost_refs: list[string]
  relationship_cost_profile_ref: string | null
  visibility_risk_profile_ref: string | null
  check_profile_refs: list[string]
  child_event_request_refs: list[string]
  outcome_level_floor: none | minor | standard | major | critical
  outcome_level_ceiling: none | minor | standard | major | critical
  reward_budget_profile_ref: string | null
  hidden_debt_tags: list[string]
  fail_tag_refs: list[string]
  preview_direction_tags: list[string]
```

五类维度的数值倾向：

| 维度 | 数值倾向 | 风险边界 |
| --- | --- | --- |
| `direct` 正面应对 | 作为事件基本解法，成本和收益最容易解释 | 条件不足时可退化为承受后果或直面失败 |
| `unconventional` 出奇制胜 | 可降低损耗、提高收益或改变事件处理模块、严重度或后续链 | 必须消耗稀缺条件、暴露能力或占用后手 |
| `avoid` 逃避推诿 | 降低即时风险和交互成本 | 常伴随奖励损失、声望下降、窗口错过或长期后果 |
| `deconstruct` 解构问题 | 改变问题成立前提，常降低事件严重度 | 失败时可能带来关系代价、越权风险或追责 |
| `deceive` 欺诈蒙骗 | 短期收益高、即时成本低 | 必须写入隐藏后患、暴露风险、追查标签或因果负担 |

常规选择事件中，每个维度最多生成 1 个候选选项。主选项区显示 1-3 个选项，超过 3 个时通过“...”进入溢出选项区；常规事件默认隐藏不可用选项。

### 6.3 奖励与预算

事件奖励、掉落、交易包、赔偿、宗门资源、秘境收益和后手相关资产必须接入世界产出预算、资源池或既有资产来源。

```yaml

  reward_profile_id: string
```

预算规则：

1. 隐性候选生成不扣世界产出预算。
2. 资产进入玩家、宗门、NPC、市场、节点显性库存或事件锁定奖励时才扣预算。
3. 出售、拆解、销毁、上交、损坏或消耗不返还世界生成预算。
4. 预算不足时，不得凭空发放高价值奖励；应降品级、替换为线索、延迟刷新、生成“发现但暂不可取”的事件状态，或触发守护 / 争夺事件。
5. 高于当前阶段预算的资源只能来自先锋泄漏、剧情、强敌真实资产、正式后手、专属资源池、事件锁定奖励或明确高风险机会。
6. NPC 战利品、交易包和赠予不得在事件开始时临时生成完整库存，只能来自持久化资产、事件锁定奖励包或有预算来源的轻量资产包。

## 8. 调参验收口径

事件调参与实现验收至少检查：

1. 候选生成使用 `world_day / world_hour` 和结算区间，N1 可对应 `hour_tick`，F1、后台追赶和局部时间域必须保留区间起止、采样种子和回放桶，不读取 `quarter / tick` 旧字段。
2. 每个事件实例只命中一个 `top_level_type`；移动、节点、宗门、世界演化、控制权、传闻和专用链入口只作为来源标签统计。
3. 事件候选池可在 Debug 中展示候选、命中条件、移出条件、权重随机命中、保底命中、提案裁决结果、压制原因、未触发压力和稳定随机种子。
4. 同一语义事件在同一上下文中不会因 UI 刷新重复触发。
5. C1 或其它时间追赶期间不触发新的随机个人即时处理事件，但符合硬条件的事件池会复用压制逻辑并继续累积未触发压力。
6. 个人即时处理事件最多产生 1 个当前角色局部时停阻塞。
7. 事件选项 1-3 个主选项加“...”溢出结构的分配结果可复盘。
8. `major / critical` 事件结果必须进入结果包、日志、回放和可见性审计。
9. 事件奖励必须能追溯预算、既有资产或事件锁定奖励来源。
10. 世界窗口事件开启、关闭、错过、进入和争夺都能写入结果包。
11. 普通玩家 UI 不显示完整候选权重、隐藏追查标签、Debug 日志或其他玩家私人事件归因。
12. F1 中资源耗尽、心魔、洞天异动、路途遭遇和宗门突发能通过通用事件流进入摘要、F1 校验断点或 F1 中断断点，不被闭关承诺吞掉。
13. 通用事件流结果可复盘采样随机种子、事件流引用、候选池状态、未触发压力、追赶压制、权重随机命中、保底命中、提案裁决、日内结算分段、F1 校验断点、F1 中断断点、自动处理事件和中断原因。

必测场景：

## 9. MVP 范围

MVP 应实现：

1. `EventTemplate`、`EventTriggerProfile`、`EventContext`、`EventCandidatePool`、`EventWeightProfile`、`EventPseudoRandomState`、`EventCandidateScore` 和候选池基础节流，并支持互斥 `top_level_type` 与可复数 `source_domain_tags`。
2. `world_day / world_hour / hour_tick` 与更长结算区间的时间口径和事件实例稳定随机种子。
3. C1 或其它时间追赶期间压制新随机个人候选，并对符合条件的候选池继续累积未触发压力。
4. 个人即时处理事件的局部时停、默认处理和 C1 返回。
5. 同步处理事件中的正式交锋与突破挑战进入 B1，并拆分现实提交窗口、非参战世界推进和自身结算耗时。
6. 事件选项的 1-3 个主选项加“...”溢出结构。
7. `outcome_level`、`EventOutcome`、`ResultPackage` 和可见 / 隐藏 / Debug 日志分层。
8. 事件奖励接入预算、既有资产或事件锁定奖励来源。
9. 秘境窗口、节点危机、突破资源 / 名额窗口三类世界窗口事件。
10. 事件调试器展示候选、进入 / 移出条件、权重、权重随机命中、保底命中、提案裁决、未触发压力、压制原因、稳定随机种子和结果包摘要。
11. 通用事件流基础配置、`silent / summary / auto / soft_interrupt / hard_interrupt` 五级和批量摘要输出。

MVP 不实现：

1. 完整事件文本库。
2. 最终事件概率表和所有候选基础权重。
3. 全部世界窗口事件类型和长期频率表。
4. 完整 `outcome_level` 到资源、伤势、关系、节点和传闻强度的量化表。
5. 隐藏后患追查、衰减、暴露和传闻生成的完整细表。
6. active major 世界事件的完整阶段推进策略。
7. 候选池回放文件导出。
