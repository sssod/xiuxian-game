# 数值设计｜修炼公式与数值设计

## 1. 设计定位

本文负责修炼数值公式、境界段表结构、资源输入结算、状态压力、修为绝对值映射和修炼 tick 输出。它回答的是“每个兼容小时如何结算、数值表如何调参、结果包应输出哪些明细”。

修为绝对值表示角色当前累计修为规模，字段名为 `cultivation_points`。表格字段和公式字段可使用 `cp_` 前缀表示 cultivation points，但正文优先写“修为绝对值”。小境界修为绝对值上下界的唯一信源是 `docs/inbox/xiuxian_design_reorganized_md/03_数值设计/01_修为境界与期望游玩时间建模.md`。本文只引用该信源，不另行维护小境界比例表或具体上下界表。

文档边界：

| 文档 | 负责内容 |
| --- | --- |
| `docs/inbox/xiuxian_design_reorganized_md/02_系统设计/02_角色与真灵设计/03_角色修为与境界.md` | 境界结构、大小境界分工、角色修炼状态和字段迁移 |
| `docs/inbox/xiuxian_design_reorganized_md/02_系统设计/11_修炼玩法设计.md` | 修炼行动类型、资源输入交互、残余效果提示、F1 消化和玩家反馈 |
| 本文 | 境界段数值、每小时公式、资源输入公式、效率裁剪、tick 明细和调参边界 |

本文不定义玩家界面布局、不定义完整行动模板文案、不定义每个资源的最终投放数量。

## 2. 数值主路径

修炼数值不从“1 小时给多少修为”开始，而是从境界段目标和玩家体验时长反推。

```text
RealmSegmentBalance
→ RealmBenchmarkRate
→ ActionCultivationProfile
→ RealmInputFitMatrix
→ ResourceEffectBalance / NodeRealmSupport / SectSupportBalance
→ StatePressureModel
→ BreakthroughScoreBalance
→ ReincarnationEfficiencyPolicy
→ 模拟验证
```

含义：

| 模块 | 作用 |
| --- | --- |
| `RealmSegmentBalance` | 定义当前境界段目标时间、进度需求、修为绝对值映射和效率上下限 |
| `RealmBenchmarkRate` | 由境界段目标反推每兼容小时基准收益 |
| `ActionCultivationProfile` | 定义主动吐纳、自动运转、闭关、托管等行动相对效率 |
| `RealmInputFitMatrix` | 定义功法、资源、设施、节点和宗门支持对当前境界段是否适配 |
| `ResourceEffectBalance` | 定价丹药、灵材、临时增益和残余药性 |
| `NodeRealmSupport` | 定义节点灵气、容量、再生、风险和机会窗口 |
| `SectSupportBalance` | 定义宗门资源、护法、设施、权限和库存支持 |
| `StatePressureModel` | 处理经脉压力、伤势、心魔、寿元压力和强行冲修副作用 |
| `BreakthroughScoreBalance` | 把准备质量转成突破挑战初始分和质量修正 |
| `ReincarnationEfficiencyPolicy` | 判断当前世代效率是否低于境界段基准 |

## 3. 境界段根表

`RealmSegmentBalance` 是修炼数值模型根表。境界段可以表示小境界推进、瓶颈、突破准备或巩固阶段。

```text
RealmSegmentBalance {
  segment_id: String
  realm_from: String
  minor_stage_from: String
  realm_to: String
  minor_stage_to: String
  segment_type: minor_progress | bottleneck | major_breakthrough | consolidation
  target_elapsed_hours_standard: number
  target_elapsed_hours_safe: number
  target_elapsed_hours_risk: number
  target_elapsed_hours_resource: number
  target_elapsed_hours_sect: number
  expected_cultivation_hour_ratio: number
  required_normalized_progress: number
  cp_lower_bound: number
  cp_upper_bound: number
  raw_cultivation_required: number
  required_method_mastery_norm: number
  required_foundation_min: number
  allowed_meridian_pressure_max: number
  allowed_injury_max: number
  allowed_mental_risk_max: number
  expected_breakthrough_rounds: int | null
  breakthrough_template_id: String | null
  min_efficiency_ratio: number
  max_efficiency_ratio: number
  low_efficiency_threshold: number
  high_efficiency_threshold: number
  reincarnation_hint_policy: String
}
```

字段口径：

1. `target_elapsed_hours_standard` 是境界段基准，不是 `hour_tick` 本身。
2. `expected_cultivation_hour_ratio` 表示日历小时中有多少小时是真正有效修炼兼容小时。
3. `cp_lower_bound / cp_upper_bound` 引用修为境界与期望游玩时间建模文档中的小境界修为绝对值上下界。
4. `raw_cultivation_required` 默认可由 `cp_upper_bound - cp_lower_bound` 派生，用于修为绝对值表现和日志映射，不直接等同战斗力。
5. `min_efficiency_ratio / max_efficiency_ratio` 是段级裁剪边界，防止倍率爆炸。
6. 轮回效率阈值跟随段配置，不做全局固定值。

## 4. 标准化进度与修为绝对值

`normalized_segment_progress` 是当前境界段的调参进度。

建议范围：

```text
0.0 = 当前境界段刚开始
1.0 = 达到该境界段推进目标，具备进入下一阶段或开启突破资格
>1.0 = 超额准备，可转化为突破初始优势、品质修正或稳定性修正
```

`cultivation_points` 是表现值、阈值和日志映射。它可以用于境界膨胀感、调试面板、NPC 成长速度校准和玩家高级详情展示，但不能直接线性换算成战斗力。

每个小阶段都有独立修为绝对值上下界。玩家界面显示该小阶段自身进度 `0%-100%`，不显示跨阶段总进度比例：

```text
minor_stage_display_progress =
  clamp(
    (cultivation_points - cp_lower_bound)
    / (cp_upper_bound - cp_lower_bound),
    0,
    1
  )
```

具体 `cp_lower_bound / cp_upper_bound` 配置见修为境界与期望游玩时间建模文档。本文只消费这些上下界，用于公式、tick 和结果包。

修为绝对值映射：

```text
cultivation_points_gain = normalized_gain * raw_cultivation_required_s
```

因此炼气、筑基、金丹可以拥有不同量级修为绝对值；同一大境界内，不同小阶段也可以拥有不同修为绝对值跨度。调参时同时查看小阶段显示进度、修为绝对值上下界和 `normalized_segment_progress`。

## 5. 基准收益反推

设：

```text
s = 当前 RealmSegment
T_s = target_elapsed_hours_standard_s
H_s = expected_cultivation_hour_ratio_s
P_s = required_normalized_progress_s
```

则：

```text
compatible_hour_benchmark_rate_s = P_s / (T_s * H_s)
```

这表示一个标准修士在当前境界段中，每个有效修炼兼容小时应获得的标准化进度。

如果某段设计为：

```text
target_elapsed_hours_standard = 720
expected_cultivation_hour_ratio = 0.25
required_normalized_progress = 1.0
```

则有效兼容小时为 180 小时，每兼容小时基准收益约为：

```text
1.0 / 180 = 0.00556
```

## 6. 每小时修炼结算

每个兼容小时的核心公式：

```text
normalized_gain_per_compatible_hour =
  B_s
  * A_action
  * Q_aptitude
  * M_method
  * K_mastery
  * N_node_aura
  * F_facility
  * R_resource
  * S_sect_support
  * P_state_penalty
  * C_competition_or_window
```

其中：

```text
B_s = compatible_hour_benchmark_rate_s
```

修正项：

| 项 | 含义 |
| --- | --- |
| `A_action` | 当前行动类型效率，例如主动吐纳、闭关、自动运转、显式托管 |
| `Q_aptitude` | 资质、根骨、灵根等角色底层修正 |
| `M_method` | 主修道功对当前境界段的适配度 |
| `K_mastery` | 功法掌握度修正 |
| `N_node_aura` | 地图节点灵气对当前境界段的适配度 |
| `F_facility` | 资源槽附属设施支持，例如洞府、静室、阵法、灵液池维护设施等 |
| `R_resource` | 丹药、灵材、符箓、`ActiveResourceEffect` 等资源效果 |
| `S_sect_support` | 宗门资源、护法、权限、库存支持 |
| `P_state_penalty` | 伤势、心魔、经脉压力、寿元压力等惩罚 |
| `C_competition_or_window` | 秘境窗口、节点争夺、资源枯竭等动态影响 |

所有修正项先计算原始效率倍率，再按当前境界段边界裁剪：

```text
efficiency_ratio_raw =
  A_action
  * Q_aptitude
  * M_method
  * K_mastery
  * N_node_aura
  * F_facility
  * R_resource
  * S_sect_support
  * P_state_penalty
  * C_competition_or_window

efficiency_ratio = clamp(
  efficiency_ratio_raw,
  min_efficiency_ratio_s,
  max_efficiency_ratio_s
)

normalized_gain = B_s * efficiency_ratio * compatible_hours
cultivation_points_gain = normalized_gain * raw_cultivation_required_s
```

## 7. 行动相对效率

行动类型不直接写死 raw 修为收益，只提供相对当前境界段基准的效率倍率。

```text
ActionCultivationProfile {
  action_type: String
  source: explicit_player | timeout_managed | system_fallback
  valid_segment_tags: Array
  compatible_hour_policy: full | partial | none
  base_efficiency_ratio: number
  f1_eligible: bool
  can_trigger_minor_stage_advance: bool
  can_trigger_major_breakthrough: bool
  pressure_profile_id: String
  resource_input_policy_id: String
}
```

建议口径：

| 行动 | 相对效率口径 | 边界 |
| --- | --- | --- |
| 主动吐纳 | 主要修为推进基准 | 可挂载修为丹药和灵气类资源 |
| 闭关修炼 | 主动吐纳的长时段低交互版本 | 可进入 F1；仍按兼容小时结算 |
| 自动运转 | 低额保底收益 | 可触发小境界，不能触发大境界突破 |
| 巩固根基 | 以压力、纯度、根基稳定为主 | 不把残余修为药性转化为修为 |
| 显式托管 | 低收益低风险 | 不主动执行高风险突破 |

## 8. 资源输入公式

行动资源输入项是挂载在行动或事件选项上的额外资源。它不改变行动类型，只在兼容语境中按有效小时释放。

基础模型：

```text
resource_effect_total = unit_effect_rate * max_effective_hours
applied_resource_effect =
  unit_effect_rate
  * applied_effective_hours
  * resource_quality_factor
  * state_factor
```

修为资源输入：

```text
cultivation_resource_aura_input =
  Σ(unit_aura_rate_i * applied_effective_hours_i * resource_quality_factor_i)
```

主动吐纳合流：

```text
raw_aura_input =
  environment_aura_input
  + cultivation_resource_aura_input
```

环境灵气流受节点灵气、资源槽、资源槽附属设施、道功吸收速度和角色状态限制；修为丹药资源流是丹药自身提供的定额灵气包，跳过道功吸收速度，但仍进入转化、承载和压力结算。

## 10. 残余效果

当资源未在本次行动中消耗完，生成 `ActiveResourceEffect`。

```text
ActiveResourceEffect {
  effect_id: String
  character_id: String
  resource_effect_template_id: String
  remaining_effective_hours: number
  residual_policy: stable_suspend | slow_decay | stimulating_decay | forced_release
  residual_stability_hours_remaining: number
  compatible_action_tags: Array
  can_be_settled_by_consolidation: bool
  settlement_policy: none | suppress_side_effect | release_without_progress
  source_command_id: String
  created_world_day: int
  created_world_hour: int
  log_refs: Array
}
```

结算规则：

1. 行动未开始，不消耗资源。
2. 行动已开始，只消耗实际兼容小时。
3. 决策阶段不推进药性衰减。
4. 服务器结算阶段、世界小时实际推进时，才增加 idle 或 decay 相关计数。
5. `stable_suspend` 可保留给后续兼容行动继续承接。
6. `stimulating_decay` 和 `forced_release` 应更容易造成散逸、压力或副作用。
7. 巩固根基可选择性收束残余修为药性，但收束不产生修为进度。

## 11. 状态压力模型

高效率修炼、跨阶资源、污染环境、带伤冲修和长时间强行闭关都可能带来状态压力。

```text
StatePressureModel {
  pressure_model_id: String
  valid_segment_tags: Array
  meridian_pressure_gain_curve: String
  injury_risk_curve: String
  mental_risk_curve: String
  purity_delta_curve: String
  foundation_quality_delta_curve: String
  pressure_recovery_actions: Array
  hard_limit_policy: warn | block | allow_with_penalty
}
```

状态压力至少影响：

1. `meridian_pressure`。
2. `injury_state`。
3. `mental_state` 或心魔风险。
4. `foundation_quality`。
5. 修为纯度。
6. 大境界突破开启条件和突破质量。

压力模型不应只作为失败惩罚存在；它也需要给巩固根基、疗伤、提纯、换地点、宗门护法和保守修炼留下明确修正入口。

## 12. 突破承接

修炼数值只负责把准备质量转为突破挑战的初始输入。大境界突破最终成败仍由 B1 轮内策略、轮内资源消耗、状态变化和模板结局共同决定。

```text
BreakthroughScoreBalance {
  breakthrough_template_id: String
  segment_id: String
  base_success_score: number
  base_quality_score: number
  required_rounds: int
  success_threshold: number
  quality_thresholds: Dictionary
  foundation_weight: number
  method_mastery_weight: number
  node_fit_weight: number
  resource_weight: number
  pressure_penalty_weight: number
  injury_penalty_weight: number
  round_decision_modifier_refs: Array
  failure_tags: Array
}
```

开启条件可读取：

```text
normalized_segment_progress >= 1.0
method_mastery_norm >= required_method_mastery_norm
foundation_quality >= required_foundation_min
meridian_pressure <= allowed_meridian_pressure_max
injury <= allowed_injury_max
mental_risk <= allowed_mental_risk_max
location_allows_breakthrough == true
method_template_available == true
required_resource_available == true
```

## 13. 修炼 tick 输出

每次修炼结算应输出 `CultivationTickResult` 或等价明细。

```text
CultivationTickResult {
  world_day: int
  world_hour: int
  segment_id: String
  command_id: String
  compatible_hours: number
  base_benchmark_rate: number
  raw_efficiency_ratio: number
  clamped_efficiency_ratio: number
  normalized_gain: number
  cultivation_points_gain: number
  normalized_segment_progress_before: number
  normalized_segment_progress_after: number
  meridian_pressure_delta: number
  method_mastery_delta: number
  resource_effects_consumed: Array
  active_resource_effect_delta: Array
  node_aura_effect: Dictionary
  facility_effect: Dictionary
  sect_support_effect: Dictionary
  state_pressure_delta: Dictionary
  visible_summary: String
  debug_formula_trace: Dictionary
}
```

普通玩家 UI 读取 `visible_summary` 和关键摘要；Debug / QA 面板可以读取 `debug_formula_trace`、裁剪前后效率倍率和内部境界段 ID。

## 14. 调参验收口径

修炼数值调参至少验证：

1. 玩家看到的每个小阶段都能从自身 0%-100% 推进。
2. 小阶段之间的修为绝对值跨度、有效修炼小时和资源需求可以不同。
3. 主动吐纳是主要修为来源，自动运转不会替代玩家规划。
4. 修为丹药不会成为即时经验药。
5. 高倍率资源必须受到境界适配、状态压力和段级效率上限约束。
6. F1 只压缩现实等待，不改变世界小时和兼容小时结算。
7. 小境界升级可以轻量触发，大境界突破不能只靠修为绝对值达标自动完成。
8. 结果包能复盘收益、资源消耗、压力变化、残余效果和可见摘要。
