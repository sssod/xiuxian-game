# 宗门系统设计

## 1. 当前定位

宗门是玩家长期成长的平台与沙盒世界演化主体，但不是玩家本体。玩家死亡或转世后，宗门仍由 AI 托管并继续演化。

宗门负责身份、职位、贡献、门内声望、资源申请、库存预留、宗门持续行动、宗门日志、宗门 NPC 支持和宗门对节点与世界演化的影响。

宗门库存的底层容器规则见《06_储物空间系统设计/03_库存系统》。宗门内商店的买卖规则见《03_经济系统设计/04_交易系统》。本页负责宗门资源申请、预留、支出、审计和权限。

## 2. 身份与权限

MVP 身份序列：

```text
外门弟子 → 内门弟子 → 真传弟子 → 执事 → 长老
```

MVP 不开放宗主。M3 或第三大境界起点后进入长老序列或等价高层决策体验。

权限标签示例：

```text
request_resources
use_training_site
request_breakthrough_support
propose_sect_action
decide_sect_action
lead_task
access_inner_archive
manage_node_affairs
assign_guard_or_support
view_sect_inventory_summary
view_resource_reservations
```

贡献是历史凭证，不是货币。门内声望是宗门内部对可靠性、潜力与影响力的综合评价。资源申请可读取贡献与声望，但最终仍必须校验真实库存、权限、地点和宗门当前状态。

## 3. 宗门资源与库存

宗门追踪五类抽象资源：

1. 灵石。
2. 修炼资源。
3. 材料 / 矿材。
4. 人力 / 弟子规模。
5. 声望 / 影响力。

宗门发放给玩家或 NPC 的资源必须来自真实库存。贡献、职位、声望、关系和身份只能影响权限、优先级和审批概率，不能绕过库存检查。

`SectInventory` 是宗门侧库存摘要，底层物品持久化仍由资产容器与物品系统承载。

```yaml
SectInventory:
  sect_id: string
  container_id: string
  spirit_stones: number
  cultivation_resources: number
  material_stock: number
  manpower: number
  sect_reputation: number
  material_items: list
  method_carriers: list
  pills: list
  talismans: list
  reserved_resources: list
  public_access_policy: object
  audit_log_refs: list
```

宗门库存可包含：

```text
灵石；
丹药；
灵材；
符箓；
法器；
完整功法载体；
残页 / 章节；
任务物；
节点产出资源；
后手回收物；
突破支持资源；
设施时段与导师支持名额。
```

注意：

1. `sect_reputation` 是宗门整体资源口径，不等同于节点影响力。
2. `manpower` 是组织人力规模，不是可放入行囊的物品。
3. 抽象资源在需要成为具体道具、奖励、突破资源或后手封存物时，再由物品系统实例化。
4. 世界产出预算只提高宗门资源可得性，不自动批准玩家申请。
5. 高于当前预算境界的宗门资源默认不稳定生成，除非来自先锋泄漏、宗门重大事件、后手或专属资源池。

## 4. 宗门资源来源

MVP 来源：

1. 控制节点的基础产出。
2. 宗门持续行动结果。
3. 玩家上交资源。
4. 节点事件奖励。
5. 宗门声望带来的外部供给。
6. 特殊秘境、机会窗口或隐藏层。
7. 后手回收或普通遗产接管。
8. 宗门商店、设施、部门或生产链产出。

所有来源都应进入 `sect_storage`、宗门库存摘要、审计日志或结果包，不应直接表现为玩家无来源获得物品。

## 5. 宗门资源支出

MVP 支出：

1. 发放弟子培养资源。
2. 支持玩家或 NPC 突破。
3. 宗门持续行动消耗。
4. 节点建设与修复。
5. 驻守、远征、探索的人力占用。
6. 应对节点危机。
7. 维护宗门核心建筑或设施。
8. 发放俸禄。
9. 宗门内商店、任务奖励和设施支持。

宗门俸禄口径：

```text
境界基数 + 职位绝对值
→ 宗门财政状态修正
→ 最终发放额
```

所有宗门采用同一套基础标准，宗门财政状态只作为发放修正。俸禄进入角色随身资产或合法个人容器时，必须写入资产流水。

## 6. 资源申请

资源申请可以作为 `Command.command_type=apply_resource`，也可以作为事件选项进入系统。

```yaml
SectResourceRequest:
  request_id: string
  character_id: string
  sect_id: string
  requested_resource_refs: list
  purpose_command_ref: string | null
  submitted_world_day: int
  submitted_world_hour: int
  status: pending | approved | rejected | partial | expired
  result_package_refs: list
```

申请流程：

```text
贡献 / 门内声望 / 身份 / 权限 / 请求用途
→ 是否允许申请
→ 检查宗门库存与既有预留
→ 检查宗门当前行动、节点压力、事件状态和 NPC 支持
→ 生成资源预留、部分批准、拒绝或过期
→ 写入宗门审计日志与结果包
```

审批依据：

1. 身份与职位。
2. 贡献。
3. 门内声望。
4. 库存与预留状态。
5. 宗门当前持续行动。
6. 关键 NPC 支持。
7. 节点压力。
8. 事件状态。
9. 请求用途。
10. 公开影响。
11. 宗门 AI 策略。

资源申请通过后：

1. 高价值资源应生成资源预留。
2. 丹药、灵材、符箓等在进入个人行动或事件选项时，必须作为行动资源输入消耗。
3. 设施时段、导师指点、护法支持进入行动、事件或突破模板修正，并记录来源。
4. 行动开始或事件选项生效前仍需执行前校验。
5. 消耗、释放、过期和拒绝都必须写入宗门审计日志与结果包。

## 7. 资源预留

资源预留用于避免宗门库存被多系统重复使用。

```yaml
SectResourceReservation:
  reservation_id: string
  sect_id: string
  source_container_id: string
  reserved_resource_refs: list
  reserved_for_character_id: string | null
  reserved_for_system: string
  bound_request_id: string | null
  bound_command_id: string | null
  created_world_day: int
  created_world_hour: int
  expires_world_day: int | null
  expires_world_hour: int | null
  status: active | consumed | released | expired | failed
  log_refs: list
```

示例：玩家申请突破支持后，宗门同意预留一批修炼资源。突破开始则消耗；事件取消则释放、过期或部分损耗。

预留规则：

1. 被预留资源不能被宗门持续行动、商店售卖、其他玩家申请或事件奖励重复消耗。
2. 预留可以绑定角色、命令、事件或系统用途。
3. 预留到期、行动失败、请求撤销、宗门状态变化或事件中断时，应释放、过期或失败。
4. 资源预留结果默认只对本人、相关宗门权限层和 Debug 可见。
5. 多人房中，宗门库存被申请会影响其他玩家机会，但不直接公开私人申请详情。

## 8. 宗门内商店与资源申请边界

宗门内商店和资源申请是两条路径。

| 路径 | 支付 / 判断 | 来源 | 结果 |
| --- | --- | --- | --- |
| 宗门内商店购买 | 灵石、价格、身份折扣、货架权限 | 宗门商店 `shop_stock` | 物品进入行囊或合法库存 |
| 宗门资源申请 | 身份、贡献、声望、用途、审批、真实库存 | 宗门库存 `sect_storage` | 预留、行动资源绑定、事件支持或拒绝 |
| 上交宗门 | 宗门需求程度、物品价值、事件状态 | 玩家行囊或合法来源库存 | 资产进入 `sect_storage`，角色获得贡献、声望或权限修正 |

宗门内商店的买卖、出售物保留和店铺库存规则见《03_经济系统设计/04_交易系统》。资源申请、预留、消耗和审计以本页为准。

## 9. 宗门持续行动

每个宗门同一时间最多拥有一个 active `SectContinuousActionState`。持续行动类型：

```text
开采 / 资源介入；
驻守 / 控制强化；
探索；
远征；
建设；
培养。
```

宗门持续行动可以改变宗门库存、节点资源、建筑状态、宗门影响力、控制权事件、玩家贡献与声望、秘境或后手窗口。

宗门持续行动消耗必须来自宗门库存、资源预留、节点资源、抽象人力或事件明确提供的输入，不得绕过库存与预留。

## 10. 日志、可见性与宗门页面

宗门输出日志分层：

```text
本人可见；
宗门成员可见；
权限层可见；
公开传闻；
隐藏世界日志；
Debug 日志。
```

宗门页面稳定表达：

1. 宗门概览、经营命令、当前持续行动、库存权限和反馈。
2. 宗门库存首页显示五类抽象资源。
3. 详情区显示具体资产、资源申请、预留状态、过期时间、用途、是否已消耗、释放、失败或拒绝。
4. 不同身份、职位和权限看到不同摘要，不展示调试级完整库存。
5. 宗门库存变更、资源申请结果、功法载体发放、NPC 支持、交易、护法、导师指点和设施支持来源都应可回放。

## 11. MVP 不做

1. 宗门内部派系 / 山头变量。
2. 玩家直接夺宗主位。
3. 复杂同宗议会。
4. 通过宗门持续行动直接迫害同宗玩家长期体验。
5. 贡献作为可自由消费货币。
6. 资源申请绕过真实库存。
7. 宗门库存直接挂在宗主、长老或管事个人身上。

## 12. 待决策项目

1. 宗门资源申请的数值阈值、贡献消耗或声望影响公式。
2. 资源申请是否允许同一玩家多项并行，以及并行上限。
3. 预留过期时间是按世界日历、宏观周期还是事件阶段配置。
4. 宗门库存首页五类抽象资源与具体资产列表的 UI 层级。
5. 宗门内商店是否共享宗门库存短缺惩罚，还是拥有独立货架缓冲。
