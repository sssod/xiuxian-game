# 01_房间回合推进_权威结算_v2.1

# 房间、回合推进与权威结算（v2.1）

## 0. 文档定位

本文整理房间运行、回合阶段机、玩家锁定 / 超时、权威服务器、插入事件链、结果回写、日志与存档交接规则。

开发实现时，S1 应作为全项目结算总线。任何玩法系统都不应绕过 S1 直接写最终状态。

---

## 1. MVP 目标

房间与结算系统必须支持：

1. 本地单人测试房间。
2. 私人服务器部署房间。
3. 至少 3 名玩家共玩。
4. 保存、暂停、恢复、续开。
5. 无人在线时世界不自动推进。
6. 全员锁定或超时后自动结算。
7. 结算过程可回放、可调试、可写入日志。
8. 回合时长可配置，当前默认 5 个游戏天。
9. 决策阶段倒计时可配置，当前默认 2 分钟。

---

## 2. 房间状态

建议最小结构：

```
RoomState {
  room_id: String,
  world_seed: int,

  current_turn_id: int,
  current_year: int,
  current_world_day: int,
  current_world_hour: int,
  current_macro_period_id: String,

  turn_config: TurnConfig,
  current_phase: String,

  player_slots: Array,
  active_players: Array,
  ai_controlled_factions: Array,

  world_state_version: int,
  pending_player_decisions: Dictionary,
  settlement_status: String,
  save_version: String
}
```

```
TurnConfig {
  turn_duration_days: int,              # 默认 5
  decision_countdown_seconds: int,      # 默认 120
  internal_tick_unit: String,           # hour
  visible_time_unit: String             # day
}
```

说明：

- `current_turn_id` 是最小同步回合编号。
- `current_world_day` / `current_world_hour` 是世界绝对时间。
- `current_macro_period_id` 用于资源再生、宗门战略、世界大刷新等非玩家最小回合的周期。
- 旧 `current_quarter` 不再作为玩家最小回合字段使用。

## 3. 标准回合阶段机

```
加载 / 创建房间
→ 回合开始
→ 上一回合报告生成 / 展示
→ 信息处理与个人即时行动
→ 个人行动指令预输入
→ 锁定 / 超时等待
→ 服务端统一结算
→ 插入事件链处理
→ 结果回写与日志生成
→ 存档写入
→ 下一回合
```

推荐 `current_phase` 枚举：

```
room_loading
turn_start
report_review
instant_personal
personal_action_planning
waiting_lock
settlement
inserted_event
writeback
turn_end
```

新版不再包含以下阶段：

```
sect_decision
sect_feedback
waiting_sect_feedback
```

宗门由 AI 在结算阶段自行推进，不要求玩家先提交宗门主行动建议或决策。

## 4. 回合开始与报告展示

回合开始时，游戏内时间暂停。客户端显示上一回合汇总报告，重点帮助玩家判断：

```
我是否要延续上一回合计划？
是否有高风险变化影响本回合行动？
当前位置、资源、宗门、后手、目标是否发生了关键变化？
```

报告优先级：

1. 死亡、重伤、大境界突破、转世等 P0 结果。
2. 当前行动完成、中断、跨回合延续或受阻。
3. 当前位置、路线、节点状态变化。
4. 关键资源、库存、后手状态变化。
5. 宗门当前持续行动进展。
6. 传闻、目标相关变化和普通日志入口。

---

## 5. 权威服务器原则

规则：

1. 客户端只提交意图，不直接改写世界状态。
2. 服务端校验所有角色行动、资源消耗、位置、权限与事件触发。
3. 客户端显示的预估收益、预估耗时、预计结束位置都不是最终结果。
4. 本地单人测试也走同一套权威结算流程，只是服务端可以在本地进程中运行。
5. 服务端必须记录足够的输入、随机命名空间、校验结果和结果包，用于调试与回放。
6. 宗门 AI 行动、节点变化、事件结果不得绕过 S1 直接回写。

## 6. 玩家锁定、超时与托管

### 6.1 结算触发方式

```
全员锁定
或
部分玩家超时后由托管生成行动
→ 自动进入服务器统一结算
```

房主手动确认可以作为后续房间设置预留，但不是 MVP 默认规则。

### 6.2 锁定

玩家锁定后：

- 不再修改本回合行动。
- 可以查看自己的已锁定预案。
- 可以等待其他玩家。
- 不展示其他玩家详细输入。
- 若事件链在结算中要求响应，再进入对应事件响应界面。

### 6.3 超时

玩家超时后：

- S12 / 托管模块生成稳健托管计划。
- 托管计划必须走 S3 行动合法性校验。
- 托管不得主动执行重大不可逆选择。

### 6.4 托管优先级

```
保命 / 避险
> 不暴露核心后手
> 延续安全连续状态
> 巩固修炼或基础修炼
> 低风险资源处理
> 休整 / 警戒 / 停留
```

托管禁止主动执行：

- 高风险大境界突破。
- 主动死亡 / 转世选择。
- 主动暴露核心后手。
- 主动进入高危秘境。
- 主动消耗稀有不可逆资源。

## 7. 结算主循环

服务器结算采用固定顺序，避免跨系统互相抢改状态。

```
读取本回合锁定指令
→ 校验个人行动指令队列
→ 生成小时级时间线
→ 推进玩家行动、移动、持续行动与事件判定
→ 推进宗门 AI 当前持续行动与常态运营
→ 推进节点、资源、传闻和世界候选变化
→ 遇到插入事件链则被动挂起普通时间线
→ 接收事件链结果包
→ 合并结果包并回写角色、宗门、节点、资源、日志
→ 生成回合结束状态与“原计划 vs 实际结果”
→ 写入存档
```

### 7.1 时间线基本参数

```
turn_total_hours = turn_duration_days * 24
turn_start_world_hour = current_world_hour
turn_end_world_hour = turn_start_world_hour + turn_total_hours
```

### 7.2 指令推进伪代码

```
remaining_hours = turn_duration_days * 24
current_world_hour = turn_start_world_hour

for player in active_players:
    load locked_instruction_queue

while current_world_hour < turn_end_world_hour:
    execute next eligible instruction segment
    validate position / resource / permission / status before segment start
    advance by consumed_hours
    check movement events / node events / status events / sect AI events
    if event triggers:
        handle EventOutcome
        apply consumed_hours
        if interrupt_plan:
            pause or modify instruction queue according to policies
    collect ResultPackages

merge result packages through S1 writeback
```

## 8. 插入事件链

插入事件链包括：

- 大境界突破。
- 战斗 / 斗法。
- 死亡 / 转世。
- 前世后手回收。
- 秘境关键节点。
- 节点危机。
- 重大宗门事件。

S3 提供触发上下文：

```
TimelineInterruptContext {
  turn_id: int,
  world_day: int,
  world_hour: int,
  local_hour_in_turn: int,
  character_id: String,
  node_id: String,
  route_segment_id: String,
  current_instruction_id: String,
  current_action_state: Dictionary,
  remaining_hours: int,
  autopilot_state: String,
  exposure_context: Dictionary
}
```

事件链返回：

```
ResultPackage {
  package_id: String,
  source_system: String,
  turn_id: int,
  world_hour: int,
  character_delta: Dictionary,
  inventory_delta: Dictionary,
  node_delta: Dictionary,
  sect_delta: Dictionary,
  route_delta: Dictionary,
  consumed_hours: int,
  interrupt_plan: bool,
  triggered_child_events: Array,
  ledger_entries: Array,
  visible_log_entries: Array,
  hidden_world_log_entries: Array
}
```

结算阶段不允许玩家主动暂停。只有插入事件链或多人交叉事件链可以被动挂起。

## 9. 结果回写规则

所有结果包交给 S1 统一回写。

禁止：

- 事件链直接修改角色最终状态。
- 战斗链直接修改节点控制权。
- 宗门 AI 绕过库存预留直接消耗资源。
- 物品系统直接绕过日志和资产容器。
- 后手系统无日志改变封存资产状态。

推荐回写顺序：

1. 校验结果包来源和版本。
2. 合并角色状态变化。
3. 合并库存和资产容器变化。
4. 合并节点、路线和地图变化。
5. 合并宗门库存、当前持续行动和常态运营变化。
6. 合并后手、遗产和轮回账本变化。
7. 写入可见日志、世界日志、Debug 日志。
8. 更新可见性、传闻和目标提示。
9. 写入存档。

## 10. 回合结束报告

回合结束必须生成：

```
OriginalVsActualSummary
```

最小结构：

```
OriginalVsActualSummary {
  turn_id: int,
  character_id: String,
  planned_timeline: Array,
  actual_timeline: Array,
  time_shift_entries: Array,
  skipped_or_interrupted_instructions: Array,
  carried_over_instructions: Array,
  key_results: Array,
  next_turn_attention: Array
}
```

报告应解释：

- 原计划是什么。
- 实际执行了什么。
- 哪些事件消耗了时间。
- 哪些指令被推迟、中断、跳过或跨回合延续。
- 资源、位置、状态、节点、宗门发生了哪些变化。

---

## 11. 宗门 AI 在 S1 中的位置

宗门 AI 不再有玩家输入阶段。S1 在结算主循环中调用宗门 AI：

```
if sect.active_continuous_action exists:
    advance progress
    check resources / manpower / node state / interruption
else:
    select new SectContinuousActionState by AI
```

宗门 AI 输出普通 `ResultPackage`，由 S1 回写。

宗门 AI 不得跳过：

- 宗门库存预留。
- 节点权限与状态检查。
- 世界日志。
- 玩家可见摘要规则。

## 12. 回放与调试

旧 `QuarterReplay` 改为：

```
TurnReplay {
  room_id: String,
  turn_id: int,
  initial_state_hash: String,
  submitted_instruction_queues: Array,
  autopilot_plans: Array,
  sect_ai_steps: Array,
  rng_trace: Array,
  settlement_steps: Array,
  event_outcomes: Array,
  result_packages: Array,
  original_vs_actual_summary: Dictionary,
  final_state_hash: String,
  debug_notes: Array
}
```

回放目标：

- 复现 bug。
- 验证权威结算一致性。
- 调试事件触发。
- 追查资产来源。
- 检查后手失效原因。
- 评估多人可见性。
- 验证宗门 AI 选择和资源消耗是否可信。
